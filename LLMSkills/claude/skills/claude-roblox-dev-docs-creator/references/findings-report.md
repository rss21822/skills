# 所見の記録

## 監査報告書の位置づけ

報告書は**状態記録**であり正本ではない。冒頭に明記する。これがないと、後から報告書の記述と正本が食い違ったときにどちらを信じるか分からなくなる。

```markdown
| 項目 | 内容 |
|---|---|
| 位置づけ | 本書は状態記録であり正本ではない。矛盾時は各正本文書が優先する |
| 更新規則 | 監査の再実施時、または所見の状態変化（決定・解消）時に改訂する |
```

## 構成

```markdown
# <PREFIX> D4 <lane> <candidate-id> r<N> — 受入監査報告書

| 項目 | 内容 |
|---|---|
| 文書ID / 版 / 日付 | `<id>` / `<version>` / `<date>` |
| lane | consistency / roblox-readiness / clean-room |
| candidate / run | `D4-CAND-n` または `P0-CAND-n` / `r<N>` |
| 監査対象 | `D4-CAND-n` または `P0-CAND-n`、candidate manifest hash、対象ファイル |
| 監査方式 | 読み取り専用。実施者 |
| 位置づけ | 状態記録であり正本ではない |
| 発端 | 誰の何という依頼か |

## 1. 総評
（2〜4文。初回は `D4合格 / P0着手資格あり（人間P0開始承認待ち）` または `D4不合格 / D0〜D3是正へ`、post-P0 は `post-P0 D4合格 / B1昇格可 / D5提示可能` または `post-P0 D4不合格 / P0是正へ`。実装開始可能とは書かない）

## 2. 重大所見（対処必須）
| # | Severity | 所見 | 確信度 | 根拠 | 対処 |
|---|---|---|---|---|---|

## 3. 軽微所見（D0〜D3是正候補。D4では未修正）
| # | 所見 | 確信度 | 根拠 | 対処 |
|---|---|---|---|---|

## 4. 観察（対処不要・記録のみ）

## 5. ギャップマップ
| 標準文書 | 状態 | 所在 |
|---|---|---|

## 6. 決定要求（ユーザー宛て）
| ID | 決定内容 | 選択肢 | 推奨 |
|---|---|---|---|

## 7. 実行環境実測
（[FACT] として、実際に測定した環境情報）
```

各 lane は上の構成で独立出力し、`docs/audits/` の raw report として無編集保存する。3系統を横断する verdict / promotion record では重複所見を根本原因単位へ統合してよいが、raw report を編集・置換しない。反証・severity 変更には audit capsule 内の根拠を付け、多数決で Critical / Major を消さない。

## 2つのラベル体系

確信度ラベルと状態タグは別物。混同すると「未検証の推測」と「未承認の提案」が同じ列に並ぶ。

| 体系 | 付ける対象 | 答える問い | 定義 |
|---|---|---|---|
| 確信度ラベル | 個々の所見、readiness 項目 | その記述をどこまで確認したか | `audit-dimensions.md` §確信度ラベル |
| 状態タグ | 決定・未決・提案 | 誰がまだ決めていないか | 本書 §状態タグ |

1つの所見が両方を持つことがある。例:「性能予算の計測方法が未定義」は確信度 `Missing`、かつ決定要求として `[OPEN blocking: no]`。

## 根拠の書き方

**節参照を使う。行番号は使わない。** 改訂のたびに行がずれて、根拠が別の内容を指すようになる。実運用で、監査書自身の改訂によって自分の根拠参照が腐った。

良い: `docs/OVL_WORKFLOW.md §4.2`
悪い: `docs/OVL_WORKFLOW.md:220`

## ギャップマップの「分散所有」

標準的な文書体系に対して何が欠けているかを表にする。ただし**「独立文書が無い＝欠落」ではない**。

| 状態 | 意味 |
|---|---|
| 存在 | 専用文書がある |
| 分散所有 | 独立文書は無いが、既存正本が機能を分担している。**新設しない**（二重正本になる） |
| 部分的 | 一部だけ存在する。何が足りないかを書く |
| 欠落 | どこにも無い。新設が要る |

分散所有の例: 「人間専用作業の一覧」は、運用文書の実行責任表＋キックオフチェックリスト＋進捗記録のブロッカー欄が分担していることがある。ここに `HUMAN_ACTIONS.md` を新設すると、同じ事実が2箇所に生まれる。

## 決定要求

ユーザーが決めないと進めない項目は、**選択肢と推奨を添えて**出す。「どうしますか」だけでは判断材料が足りない。

```markdown
| ID | 決定内容 | 選択肢 | 推奨 |
|----|----------|--------|------|
| D-A2 | P0実行プラットフォーム | (a) Windows機で現仕様のまま / (b) macOSで実施し該当節を改訂 / (c) 両対応 | [PROPOSAL] (b)。実開発機・ツール類が現にmacOSにあり、目的は代替手段で担保可能。ただし(b)採用時も<代替の必須条件>を課す |
```

推奨には `[PROPOSAL]` を付ける。承認前の提案であることを明示する。

## 状態タグ

| タグ | 意味 |
|---|---|
| `[FACT]` | 確認済みの事実。測定方法も書く |
| `[DECISION]` | 人間本人が直接承認済み。委任AIは作成しない |
| `[AI-APPROVED]` | 人間の委任決定の範囲内でAIが承認した工程内状態。Gate 1・P0 start・最終P0 contract・D5・formal document昇格の代替ではない |
| `[PROPOSAL]` | AI提案、未承認 |
| `[OPEN blocking: yes\|no]` | 未決。blocking:yes は進捗記録のblocker欄にも登録 |
| `[HUMAN]` | 人間だけが実行可能。AI実行候補へ付けない |
| `[AI-ACTION]` | AIが現在の権限・能力内で実行可能。HUMAN_ACTIONSには入れない |

`blocking: yes` の項目は必ず二重登録する（文書内の注記＋ブロッカー台帳）。片方だけだと、文書を読んだ人と進捗を見た人で認識がずれる。

## 差し戻しと再監査

D4はfindings-only／read-onlyで、軽微所見も正本文書へ直接反映しない。各所見にD0〜D3の該当執筆工程向け修正方向を書く。

初回 D4 で Critical／Major があれば `D4不合格 / D0〜D3是正へ`、post-P0 D4 なら `post-P0 D4不合格 / P0是正へ` とし、所有工程へ是正を依頼する。改訂後はいずれも過去所見を渡さずfresh clean contextの3系統を使う。初回は毎回full D4、post-P0は `audit-d4.md` §6 のcandidate-derived delta（escalation条件ならfull）を再実行し、どちらも文書単位residual-onlyにはしない。初回の3系統が Critical 0 / Major 0 の場合だけ `D4合格 / P0着手資格あり（人間P0開始承認待ち）` とする。post-P0 は合格時だけ `post-P0 D4合格 / B1昇格可 / D5提示可能` とする。

## 監査記録の保存

判定に関わらず全巡を保存する。差し戻しの記録にこそ価値がある（何を避けたかが残る）。読み取り専用で走らせた監査は自分で保存できないので、**呼び出し側が本文を改変せず保存する**。ヘッダ（対象・日付・判定）を足すのは構わない。

合格 candidate を B0/B1 へ昇格しても raw report の candidate ID を baseline 名へ書き換えない。別の昇格記録で `promotedFrom` と同一 file-set hash を証明する。

**D4 保存先**: `docs/audits/<PREFIX>_d4_<lane>_<candidate-id>_r<N>.md`。接頭辞の慣行が無ければ `d4_<lane>_<candidate-id>_r<N>.md`。lane は `consistency` / `roblox-readiness` / `clean-room` の固定語彙。candidate と run を必ず含め、**前の巡を上書きしない**。

BROWNFIELD の事前 Repository Audit は別 artifact。D4 report を `<PREFIX>_repository_audit.md` や `docs/handoffs/out/` に保存せず、両者を同じ履歴へ混ぜない。
