# gate 設計

P0 の手戻りの半分がここから出る。gate とは「何が成立したら次へ進めるか」の定義であり、`[OPEN]`・closure evidence・承認条件・遷移条件がすべて gate である。

P0 改訂を許可する開始 gate は `templates/p0_start_handoff.md` で B0 ID/hash と scope を人間本人へ提示し、D5 と異なる承認 ID で記録する。開始 gate は契約決定、formal document の `Approved` 昇格、W0 authorization を兼ねない。

## 1. 循環を作らない

### 循環はこう生まれる

契約を承認する条件に、**その契約がないと作れないもの**を入れると循環する。

```
§2.3 の P0契約承認条件
  └─ 「実 tree との逐条照合」「project file の build 成功」
       └─ 実 tree を作るのは W0 実装
            └─ W0 は D5 承認が要る
                 └─ D5 は §2.3 の契約承認を要求する  ← 振り出し
```

書いている最中は自然に見える。「契約どおりに実装されているか確かめてから承認する」は正しく聞こえるからである。**しかし実装は承認の後にしか始まらない。**

### 対処 — 承認を2段に割る

| 段 | 名称 | 条件 | 性質 |
|---|---|---|---|
| **A** | 契約としての承認 | 現在の文書と実測だけで検証できる項目 | 実体の存在を条件に**しない** |
| **B** | 実装後の適合確認 | 実 tree との照合、build、runner 解決 | **A の前提ではない** |

B の節に「**未実施、未完了、または実体が存在しないことを理由に A の昇格を差し戻さない**」と明記する。これがないと、読んだ人が B を A の条件だと解釈して循環が復活する。

### B を空文にしない

A/B に割ると、B が「書いてあるだけで効力がない」状態になりやすい。**B の実施を実装側の完了条件へ接続する**（→ §3 配線）。

### 他の循環パターン

- **gate の取り違え**: P0 の Work Package の `Authorized by` が「D5 承認」だったが、P0 は D5 到達のための前提作業だった。→ **gate を分ける**（D4の `D4合格 / P0着手資格あり（人間P0開始承認待ち）`、B0を対象とする人間P0開始承認、P0の `[DECISION]`／`[AI-APPROVED]`、post-P0 D4、人間D5承認は別物）
- **profile の時系列矛盾**: 計測用の暫定値を、計測完了後の製品ビルドで再利用する設計。→ **一方向契約を明記**（measurement で計測 → 確定 → production を正本化。逆流禁止）

### 見分け方

承認条件を1項ずつ読み、「**今これを満たせるか。満たせないなら、満たすには何が要るか**」を辿る。辿った先に自分が出てきたら循環である。

## 2. open の粒度

### 粒度過大の症状

確定できるものと計測待ちのものが同じ `[OPEN]` に入っていると、**確定済みの分も閉じられない**。

実例: 4つの entry file を1つの open にまとめた。うち2つは W0 用で確定可能、2つは Lobby／Match 用で配信方式の実測待ちだった。結果、W0 側だけを割り当てても closure に到達できず、W0 範囲の契約承認が実測待ちに巻き込まれた。

### 設計規則

**closure 条件が違うものを同じ open に入れない。**

open を立てる時点で、対象ごとに「これは何を待っているか」を書く。待ち先が違えば分ける。

```
悪い: [OPEN] entry file 4件の担当 WP が未定
      closure evidence: 4件すべての担当 WP 指定と一致確認

良い: [OPEN] W0 entry 2件の担当 WP が未定
      closure evidence: 2件の担当 WP 指定、Work Packages の実改訂、一致確認、承認
      （本 open は配信方式の open にも実測結果にも依存しない）

      [OPEN] Lobby／Match entry 2件の担当 WP が未定
      closure evidence: 上記に加えて配信方式の確定と実測結果
```

**依存の非依存性を明示する**のが要点。「この open は別の open に依存しない」と書いてあると、下流が安心して先へ進める。

### 分割は早いほうがよい

後から分割できるが、下流文書が「この open が閉じない」を前提に書き始めると、分割時に下流も直すことになる。

## 3. 配線 — 規定を効力へ接続する

### 症状

「実装後にこれを検査する」と書いたが、**どの Work Package の完了条件にも入っていない**。規定は存在するが効力がない。

実プロジェクトでは、規定を書いた本人が「各 WP への追記が未了の間は、本段の要求は実装 WP の完了を止める効力を持たない」と正直に書いていた。ところがその追記を担うはずの Change Request の改訂 inventory にも実施手順にも入っておらず、**CR を最後まで実行しても配線されない経路**が残っていた。照合2巡を要した。

### 対処

規定を書く handoff の中で、次を同時に決める。

1. **適用対象の判別規則**（どの WP がこの規定の対象か）。規定側が所有し、CR や WP 側で列挙し直さない
2. **記録先**（対象 WP の `Evidence output` に何を残すか）
3. **遷移禁止条項**（未実施・不一致未処理のまま `Verified` へ遷移しない）
4. **追記作業を担う CR の改訂 inventory への登録**

4 を忘れると 1〜3 が空文になる。

### 照合での検査

照合依頼に「**経路を最後まで辿って、本当に完了条件へ接続されるか**」と書く。規定の存在確認で止めると見逃す。

## 4. closure evidence の書き方

### 実体条件で書く

closure 条件を「文書ができたか」で書くと、文書ができた瞬間に条件が壊れる。**値・runner・evidence path・承認記録が登録されたか**で書く。

```
悪い: 「X.md が未作成のため保留」
      → X.md ができた瞬間に嘘になり、誰も直しに戻らない

良い: 「X の canonical 値が未登録のため保留
       （closure: X へ値が登録され Owner 承認されたとき）」
      → 条件が実体を指しており、勝手に嘘にならない
```

### 承認だけで閉じない

closure evidence が「担当 WP の指定」を含むなら、**指定を承認しただけでは足りない**。承認 → 正本の実改訂 → 一致確認、まで到達した時点で closure が成立する。

この区別を open 本文に書く。「本 open は承認時点では閉じない」と明記すると、後で「承認したから閉じた」という誤解を防げる。

### closure record の形

open を閉じるとき、open 本文を closure record へ置き換える。record には evidence の**項番ごと**に:

- 何が成立したか
- どこで成立したか（決定 ID、handoff ID、実測値）
- いつ成立したか

これがないと、後から「本当に条件が揃っていたのか」を検証できない。

**あわせて「この closure が何を意味しないか」も書く。** 実例: 「これは契約の `[DECISION]`／`[AI-APPROVED]` 昇格ではなく、別の2 openも閉じず、D5でもない」。範囲の誤解を防ぐ。

---

## 5. 判断材料の実測

P0契約承認のgateが「判断材料n点」を定めているなら、**承認する側が自分で再計算する**。人間本人の直接承認だけを `[DECISION]`、委任AIの範囲内行使を `[AI-APPROVED]` と記録する。後者はD5やformal documentのStatus昇格を満たさない。

実プロジェクトの4点:

1. 論理 module 表と物理 mapping 表の全件対応（差集合 0）
2. path 導出の一意性（導出結果と登録値の mismatch 0、重複 0）
3. Work Packages の担当欄との照合（割当数、scope 越境 0）
4. Rojo 記法の整合（既存 project file との mismatch 0）

**1つでも不成立なら承認せず止まる。** 実測結果は承認記録に残す。「判断材料を確認した」ではなく、**数値**を書く。P0 core完了時の出口は `post-P0 D4待ち`。B0→candidate の3系統差分D4が Critical 0 / Major 0 で B1 に昇格した後だけ `D5提示可能`。実装開始可能とは宣言しない。

同じことがP0管理WPのVerified遷移条件にも当てはまる。製品実装WPはD5前に遷移させない。P0管理WPのDone definitionにvalidatorが含まれるなら実際に走らせる。**追跡ファイルを上書きしない一時出力先**を使うこと（Studioが開いているファイルへの上書き事故を避ける）。
