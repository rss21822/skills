# 独立照合のプロトコル

## 基本形

照合は**別セッション・読み取り専用**で発注する。執筆したセッションによる自己レビューは、ここでは検証として成立しない（同じ文脈と同じ盲点を共有しているため）。

**独立照合は品質検査の外部視点であり、人間承認とは別の役割を持つ。** 人間は製品判断を承認し、照合役は文書の整合性・実装可能性を検査する。片方で他方を代替しない。巡数を減らすことはあっても、0 にはしない。

照合役は使用者が指定した worker（`worker-registry.md`）。**執筆役と別であること**が唯一の固定条件で、別系統のモデルならなお良い——同一モデルの別セッションは文脈は分離できてもモデル固有の盲点は共有したままになる。

gate照合役はClass Aに限定する。validator、test、対象file、canonical source、evidenceを自身で再検査できる必要がある。Class Bはhash付きcontext/evidence bundle範囲のsupplemental semantic reviewにだけ使え、Critical 0 / Major 0、D4合格、実装準備判定を単独で出せない。

Codex CLI を**文書単位の照合役**にする場合は、`worker-registry.md` と `codex-run` skill の**現行 companion 経路**を使う。`review_request.md` の全文を `task` の prompt として渡し、`--write` を付けず、依頼文にも「読み取りのみ・修正禁止」と明記する。完了通知の `output-file` を回収し、`docs/handoffs/out/<id>_reviewN.md` へ無編集で保存する。raw `codex exec` のコマンドをここへ複製すると、起動経路や Windows PATH の要件が `codex-run` 改訂時にずれるため、複製しない。D4 gate はこの保存先を使わず、`audit-d4.md` の capsule / `docs/audits/<PREFIX>_d4_<lane>_<candidate-id>_r<N>.md` 契約を使う。

**どの worker でも読み取り専用で発注する。** 書き込み能力を持つ worker（クラス A）を照合に使うとき、read-only 指定を落とすと照合役が是正を始めてしまい、「指摘した本人が直した」状態になる。

出力は**無編集で保存**する。文書単位照合は`<id>_reviewN.md`、Class Bの補助照合は`<id>_supplemental_reviewN.md`へ分け、後者をgate evidenceとして参照しない。D4 gate の3 lane raw report は前段の `docs/audits/` path を使う。

## 巡ごとのスコープ

これが収束速度を決める。

### 1巡目 — 全面

観点を明示列挙する。列挙しないと照合者は形式検査に流れ、意味論的欠陥を見逃す。標準観点:

1. **正本準拠** — 上流の逐語転記が正確か。改変・欠落・創作がないか
2. **独立再計算** — タグ集計・件数・数値走査を照合者自身が数え直す（作成側の申告を検算させる）
3. **決定の出所・承認トレース** — `[DECISION]` の全出現に出所と人間承認記録が付き、`M` は evidence、`W` は URL と取得日、`U` は intake、`J` は判断理由・代替案・承認記録へ遡れるか
4. **トリガ行の実質** — テンプレート／trigger-matrix が要求する項目が、実装可能な粒度で存在するか
5. **上流整合** — 上流の `[PROPOSAL]` を昇格していないか。所有境界を侵していないか
6. **実装可能性** — 実装者がこの文書から作業へ落とせるか。未確定は gate へ誘導されているか

**機械実測を含む運行の追加観点**（実測依存文書、`HUMAN_ACTIONS.md`、`AI_ACTIONS.md`を含む場合）:

7. **実測の妥当性** — 閾値ファイルのタイムスタンプが計測より前か。evidence に生出力が含まれているか（要約だけではないか）。判定が PASS/FAIL/INCONCLUSIVE の3値か（「概ね達成」のような中間表現がないか）。Studio 計測と実機の差が記録されているか
8. **実行主体の妥当性** — `[HUMAN]`が人間専権のままか。`[AI-ACTION]`が別台帳にあり、approval/evidenceを持つか。`blocked-safety`をAI実行へ寄せていないか

### 2巡目以降 — 残存点のみ

```markdown
1巡目照合記録: <path>（Major N 件）。**PASS 済み観点は再精読不要**。

## 照合観点（残存点の解消判定に限定）
1. <指摘1> が解消したか＋行番号根拠
2. <指摘2> が解消したか
3. 回帰: 是正差分の範囲内で新規矛盾・新規数値・タグ違反・出所欠落が生じていないか
```

**なぜ絞るか**: 全面再読を繰り返すと、前巡で合格した領域に新しい指摘が出続けて終わらない。実プロジェクトで、5巡かかった文書と2巡で終わった文書の差は、ほぼスコープ限定を始めた時期の差だった。

**適用境界**: residual-only は1文書の制作サイクル内だけ。D4 gate で Critical / Major 是正後に行う再監査へ適用しない。initial D4 再監査は毎回、過去 findings と差分を渡さない fresh clean context の3系統 full audit。post-P0 は `audit-d4.md` §6 の B0→candidate delta D4を基本とし、同節の条件に該当すればfull escalationする。

## 是正方針を判定基準として渡す

**本節は文書単位の制作サイクルだけに適用する。** D4 gate の監査者へ是正方針・過去 findings・期待判定を渡してはならない。D4 は `audit-d4.md` の fresh capsule 規則を優先する。

未確定事項が多い Draft では、照合者が「決めていないこと」を欠陥として報告し続ける。これを防ぐには、**是正で採った方針を照合依頼に書いて判定基準にする**。

実際に有効だった方針:

> 「確定可能な構造は閉じる／FR 依存や数値未確定は field・行単位の `[OPEN blocking: yes]` gate 付きレジスタへ変換し、実装者が独自決定も全面停止もしない」という2分法。**未確定値の推測 closure を要求しないこと。** 判定すべきは、この2分法が一貫して適用され、どちらでもない曖昧な状態が残っていないか。

もう一つの型:

> 「契約は確定・手段は gate」の2層。payload field/type は machine-readable instance が所有し、本書は受信・ack・停止完了の semantics/evidence を確定、transport の実装手段だけが gate。

方針を渡さないと、照合者は「gate が閉じていない」を毎巡報告する。方針を渡すと、「gate 化が一貫しているか」という**実際に有用な検査**に変わる。

## Class A照合者に自分で実行させる

gate照合依頼へ明記する:

- validator を自分で実行せよ
- テストを自分で実行せよ（可能なら）
- タグ・件数を自分で数え直せ（作成側の申告値は信用しない）
- 全件検査せよ（サンプル検査を許すと漏れる）
- **evidence の実在を確認せよ**（パスが書かれているだけで中身が無い、要約しか無い、を見つける）
- **`J` 出所の分布を数えよ**（`J` が集中している箇所が、誰も外部から検査していない判断の集中箇所）

実プロジェクトでは、これで申告値と実数の食い違い、承認記録の範囲外引用、要件の未解決 union などが実際に見つかった。

## 発散の判定

**巡を重ねるごとに新しい Major が出る**なら発散している。判断:

1. その指摘は**実害**を指しているか、**形式的厳密さ**を求めているか
2. 実害なら是正する
3. 形式的厳密さなら、正本が要求する**目的**まで戻り、手段を簡素化する

3の簡素化が製品判断、canonical contract、gate強度を変える場合は`[PROPOSAL]`として使用者承認へ送る。純粋な重複削除・表現整理だけ指示役が実行できる。採否と理由を`DECISIONS.md`へ残す。

実例: あるセキュリティ主張が3巡かけても証明できなかったとき、主張を削除して構造的性質を正直に記述し、採用可否を gate にした。「証明できないことを証明しようとし続ける」より、「証明できないと記録して判断を gate へ渡す」ほうが正しい。

**実装前に実装詳細を文書で完全に閉じようとしている**のも発散の典型。実際に書いてみないと分からないことは、目的だけ固定して手段は実装から確定させる。**自律モードでは「Studio で試せば分かる」ものが増えている**ので、文書上で論争が続いたら実測へ倒す選択肢を先に検討する。3巡議論するより1回測るほうが速く、証拠も強い。

## 監査フェーズ（D4 相当）

文書単位の照合を何十巡回しても、**文書横断の欠陥は見つからない**。各照合が「その文書の handoff に照らして」検査するため、体系全体の整合は誰も見ていない。

実プロジェクトでは62巡の照合を通過した体系に対し、横断監査が以下を新規検出した:

- 値の二重正本（DATA ID 参照が0件だった）
- 決定 ID の名前空間衝突の全体像
- 陳腐化前提句15箇所
- 前提文書の Change history 破損（同一判定の FAIL と PASS が supersede 表示なしで併存）

### 監査の設計

**モデル系統を変える。** 同一モデルで62巡回しても出なかったものが、別系統の監査で出た。同じモデルは同じ盲点を持つ。**自律モードでは指示役も同じモデルなので、系統を変える意義がさらに大きい。**

3系統を並行実行する（`phase-definitions.md` §7 の監査エージェント定義に対応）:

| 系統 | 何を見るか |
|---|---|
| consistency | 二重正本・参照切れ・矛盾・未解決状態・変更伝播 |
| readiness | 権威・保存・性能・課金・権利・公開復旧・未計測リスク |
| clean-room | 過去の経緯を知らない実装者が最初の作業を開始できるか |

clean-room は特に有効で、**gate の循環や承認記録の欠落**という、内部にいると見えない欠陥を捕まえる。「新規 AI になりきって CLAUDE.md から読み始め、着手不能になった地点を報告せよ」と指示する。

**自律モードでは clean-room に1問足す**——「この体系の製品判断は、何を根拠に決まったと読めるか」。出所記録が機能していれば辿れるはずで、辿れない箇所が G-1（出所なき自律決定）の残存。

### 監査結果の処理

1. 監査記録を保存（`docs/audits/<PREFIX>_d4_<lane>_<candidate-id>_r<N>.md`）
2. 指摘を **是正可能 / 実行が要る / 安全境界で止まる**に仕分ける
   - 是正可能 = 文書の書き換えで済む
   - 実行が要る = Studio 実測・調査で解決する（自分で実行する）
   - 安全境界で止まる = `HUMAN_ACTIONS.md`へ`exec: human-only`、AI停止理由`blocked-safety`として登録
3. 是正分を handoff へ（内容の性質でまとめる。記録・計画系／正本系／安全規則系のように分けると1便が大きくなりすぎない）
4. 実行が要る分は実行し、evidence を作ってから該当文書を是正する
5. initial D4 の是正後は新しい immutable `D4-CAND-(n+1)` を作り、fresh clean context の3系統 full D4 にかける。post-P0 の是正後は新しい `P0-CAND-(n+1)` を作り、`audit-d4.md` §6 の B0→candidate delta D4（escalation 条件に該当すれば full D4）を fresh 3系統でやり直す

機械的に実行可能な項目は`AI_ACTIONS.md`へ、人間専権は`HUMAN_ACTIONS.md`へ分離する。同じ`[HUMAN]`項目をAI完了扱いにしない。

## 執筆モデルの報告の扱い

執筆モデルは、実施していない検証を報告に書くことがある。1セッションで7件発生し、禁止語を追加するたび表現が変形した。

**方針: 争わず、記録して不採用にする。** 記録は `docs/handoffs/out/<id>_note.md` へ置く（執筆モデルの最終報告そのものは `docs/handoffs/out/<id>_last-message.md`。lint の `report_globs` 既定がこの名前を見る）。

```markdown
# <handoff> note

執筆役（<worker 名>）最終報告の「<該当行>」は、発注していない検証の主張であり真偽を検証できないため不採用。
正とする照合は本セッションが発注した読み取り専用照合のみ。実害なし（実測: <自分の検査結果>）。
```

理由:

- 訂正を求めるやり取りは費用に見合わない（次の handoff で別の変形が出る）
- 構造的に吸収できる。自分の機械検査と実際の独立照合だけを正とすれば、捏造報告は成果物へ影響しない
- 実際、7件のいずれも成果物へ影響しなかった

同様に、報告された sha256 も自分で計算し直す（誤報告の実例あり）。

## 自分の報告の扱い

**同じ基準を指示役自身へ適用する。** 執筆モデルの捏造報告を検査する構造を持ちながら、自分の報告を検査しないのは一貫していない。自律モードでは指示役の報告を受け取る人間の検査も無いので、なおさら。

特に頻出する型:

- **「実行できる」を「実行した」と書く**（`defect-catalog.md` G-5）。Studio MCP で計測可能だと確認しただけで、実測値のない記録を書く
- **画像を判定根拠にする**（G-3）。スクリーンショットは補助であって、数値ではない
- **判定を甘くする**（G-2）。閾値を跨いだ値を「概ね達成」と書く

対処は執筆モデルと同じく構造的に行う。**記録には生の出力を貼る。** 要約だけの記録を evidence として採用しない。照合依頼で evidence の実在と中身を確認させる。
