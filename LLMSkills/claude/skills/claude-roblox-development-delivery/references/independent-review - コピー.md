# 独立照合

実装に参加していない**別のsession/worker**が読み取り専用でレビューする。同じsessionが自分の実装をレビューしても独立照合にならない。

実運用で19回実施し、実装だけでは絶対に見つからない欠陥を捕まえた。

## 起動契約

レビュアーも所有者が今回指定する。worker、model、exact tool pin、認証channel/account、送信するprompt・repository・path・secret除外を記録し、送信先ごとの明示承認を取る。実装workerの承認を流用しない。

Codexを指定された場合は、[共通委譲契約](../../claude-roblox-mvp-buildout/references/delegation-contract.md) のexact-pinned `start_codex_job.ps1` helperを `read-only` で使う。helperを迂回したCLI直接起動、固定modelの直書き、グローバル設定、未pin版の導入へfallbackしない。別workerなら、その階層に存在しない強制機構を主張しない。

prompt fileへ次を記録し、owner-approved helper/workerへ渡す。

```markdown
あなたは独立レビュアー。この実装には一切参加していない。読み取り専用。ファイル変更禁止。最終メッセージが成果物。

## 対象
<変更ファイル一覧と baseline commit または immutable snapshot ID>

## 正本
<準拠すべき設計文書と該当節>

## 実装報告（検証対象。鵜呑みにしない）
<実装workerの主張。数値・件数・hashを含める>

## 照合観点
1. <正本準拠。省略・緩和をfile:lineで指摘>
2. <実装者の主張の独立再計算。実装者のコードを使わず自分の方法で>
3. <不変であるべきものの不変性>
4. <創作値の混入>
5. <D6同期とLKG commit/snapshotの完全性>

## 出力
各観点PASS/FAIL（FAILはfile:line＋根拠）。Critical/Major/Minor（なければ「なし」）。総合判定（承認可/差し戻し）1行。日本語。
```

read-only reviewerの最終出力は、起動helper/orchestratorがowner管理の証跡場所へ保存する。本文を改変しない。ヘッダ（対象・日付・worker・承認ID・判定）の追加だけ可。

**自分の所見をレビュアーへ渡さない。** 渡すのは対象ファイル・baseline・正本の該当節・成果物が暗黙に主張していること・照合観点まで。自分が見つけた欠陥を先に伝えると、レビュアーはそれを追認する作業に寄り、独立性が消える。実運用でこの分離を守ったところ、レビュアー側だけが見つけた欠陥があった（テストの判定関数が assert も非0終了もせず、実装をどう壊してもCIが通る構造）。逆に自分だけが見つけたものもあり、両方を足して初めて全体が見えた。

## 効く照合観点

実際に欠陥を捕まえた観点:

**独立再計算** — 実装者の抽出コードを使わず、別の方法で同じ結果を出す。1703件の転記照合で、レビュアーが独自スクリプトを書いて全数突合し、一致を確認した。もし実装者のコードを再利用していたら、コードのバグは検出できなかった。

**見せかけPASSの検出** — テストが「本当にその条件を作ってから検証しているか」。実運用で、テストハーネスがシミュレーション入力だけでPASSしていた（実配線されていなかった）ケースが見つかった。

**不変性** — 変えてはいけないもの（golden hash、既存schema、承認済み値）が本当に変わっていないか。実測して比較させる。

**創作値** — 実測していない値が事実として書かれていないか。URL・hash・バージョン・errnoが典型。

**目的の担保** — 簡素化したときに「何を守るはずだったか」が守られているか。手段を変えても目的が残っているかを見る。

## 差し戻しへの対処

判定が「差し戻し」なら、指摘ごとに是正handoffを出す。是正の範囲を明示し、**前回PASSした観点の再精読は不要**と伝えると、レビュー時間が短縮される。

```markdown
対象: 前回照合のMajor N件への是正のみ。前回PASS観点（<列挙>）は再精読不要。
```

## 発散したときの判断

巡を重ねるごとに新しいMajorが出続けるなら、発散している。実運用で3巡（Major 6→3→5）発散した。

**発散の兆候**:
- 各巡で前回と別の箇所に新しい指摘が出る
- 指摘が実装詳細のレベルまで降りている（「この構造体にこのフィールドを足せ」）
- まだコードが存在しない段階で、そのコードの詳細を文書で決めようとしている

**原因のほとんど**: 実装前に実装詳細を完全に閉じようとしている。実際に書いてみないと分からないことは、書いてから決まる。

**対処**: 正本が守ろうとしている**目的**まで戻る。「この仕組みは何を保証するためにあるか」を1〜3個に言語化し、目的を守ったまま手段を簡素化する案をユーザーへ提示する。決定はユーザーが下す。

実例: offline検証の目的は「lint stdlibの決定論・toolchainのpin・CIのネットワーク非依存」の3点だった。手段（サンドボックス隔離の形式証明）は目的に対して過大で、実装前に閉じられない性質だった。目的ベースへ簡素化した結果、以降の照合は3→1→0と単調に収束した。

**発散していない差し戻し**: 指摘が実害を指しているなら、巡が増えても健全。「このテストは条件を作らずにPASSする」「このpinは別バイナリでも通る」は実害。素直に是正する。

## 記録

判定に関わらず全巡を保存する。後から「なぜこの設計になったか」を追跡できる。差し戻しの記録こそ価値がある（何を避けたかが分かる）。
