# 手続き生成した建物のテクスチャ設計

エンジンの制約を守りながら、生成済みの建物群に見た目を与えるための手法。

この領域の失敗は**落ちない・ログは出る・結果が静かに間違う**型に強く偏る。
実プロジェクトで出た不具合は9件中8件がそれで、うち4件は**レンダを見て初めて**
分かった。手順の暗記より、どこで静かに壊れるかを知っておくほうが効く。

参照ファイル:

| ファイル | いつ読むか |
|---|---|
| `references/atlas-design.md` | 区画の切り方・寸法の最適化・UV の焼き方を決めるとき |
| `references/failure-modes.md` | 実装中、および「終わった」と言う前 |
| `references/citygen-example.md` | citygen リポジトリ（`Claude3DProject/Tokyo`）を触るとき。**そこでは正本** |
| `references/citygen-texture-style-schema.md` | 同リポジトリの都市 YAML `texture_style` を書くとき |

## 1. 先に制約を確定する。設計はそこから落ちてくる

**公式文書を引く。記憶で進めない。** エンジンのテクスチャ・UV・マテリアルの
制限は設計の根幹を決めるので、ここを間違えると全部やり直しになる。

最低限これらを確認する。

- UV は 0〜1 に収める必要があるか。1を超えたとき繰り返すのか、切り詰められるのか
- 1メッシュに何枚のマテリアルを持てるか
- テクスチャの最大解像度、および推奨解像度（オブジェクトの実寸あたり）
- 法線・粗さ・金属度などの追加マップをどう運ぶか（別アセット？ 別インスタンス？）
- 書き出す形式（FBX/glTF）が何を運べるか。**プロシージャルなマテリアルノードは運べない**

最後の点は見落としやすい。Blender の Noise/Brick ノードは FBX に乗らない。
運べるのは UV と画像ファイルへの参照だけなので、どこかで必ず画素に落ちる。

### 文書に書いていないときの決め方

挙動が公式に明記されておらず実機でも試せないことがある。そのときは
**どちらに転んでも致命的でないほう**を選ぶ。

例: 「UV>1 でタイリングされるか」が不明だったとき。

- タイリング前提で作り、実際は切り詰められた → 全壁面が引き伸ばされた窓1個。**破滅的**
- アトラス前提で作り、実際はタイリングできた → 解像度が下がるだけ。**緩やか**

後者を選ぶ。楽観に賭けて壊れ方が急峻な設計は、検証できないうちは採らない。

## 2. タイリングかアトラスか

最初の分岐で、後戻りが最も高くつく。

| | タイリング | アトラス |
|---|---|---|
| UV | 1を超える | 0〜1 に収まる |
| 実効解像度 | 高い | 低い（分割するぶん） |
| 1枚に複数種の絵 | **不可**（全体が繰り返される） | 可 |
| 1メッシュ1マテリアル | 壁と屋根で別マテリアルが要る | 満たせる |

**「1枚に複数種の絵を置けるか」が効く。** 壁と屋根は同じメッシュにあり、
タイリングでは同じ画像が両方に繰り返されるので、屋上に窓が寝そべる。
これを別マテリアルで解こうとすると「1メッシュ1マテリアル」に触れる。
アトラスなら両方が一度に解ける。

## 3. アトラスの面積は実測で配る

直感で配らない。**面を数える。**

1. 対象メッシュの面を、カテゴリ別・向き別（壁／屋根／小面）に数える
2. 壁面については幅と高さの分布（p15 / 中央 / p85 / 最大）を採る
3. 使用頻度の高い区画に大きいセルを割り当てる

実例では屋根が全面の **52%** を占めるのに 256×256 しか与えておらず、
使用45回の区画が 512×256 を占有していた。配分を実測に合わせ直しただけで
屋根の面積が4倍になった。

**解像度には頭打ちがある。** 64 px/ベイ程度を超えると視認できないので、
それ以上は使用頻度の高い区画へ回す。目的関数は

```
Σ 使用面数 × min(1, 実解像度 / 目標解像度)
```

区画の寸法（何ベイ × 何階を描くか）も**実測した面に対して最適化**する。
手で決めた値は最悪 8.9 倍ずれていた（幅3mの壁に窓が8段入った）。
比のずれ（log）の平均二乗を最小化する貪欲法＋局所改善で 2.4 倍まで落ちた。

詳細は `references/atlas-design.md`。

## 4. 様式は「オブジェクトごとに一定な量」で分岐する

面は**寸法**で区画を選ぶ。同じ建物でも幅の違う壁は別の区画に行く。
だから**幅で様式を変えると、1棟の正面と側面が別の建築になる**。

階数（高さ）は建物ごとに一定なので、こちらで分岐する。階数の近い区画には
同じ様式を置く。実例では8階=石造 / 10階=ガラスという比 1.25 の割り当てがあり、
9階建ての建物が幅によって石造にもガラスにもなっていた。

これは**テストで機械的に検査できる**。「階数比が N 倍以内の区画どうしは同じ様式」
という不変条件を書いておくと、割り当てを見直すたびに再検査される。

## 5. 基調色はアトラスに焼く。マテリアル乗算は微差だけ

1枚の画像に壁・屋根・トリムが同居しているので、マテリアル側で色を掛けると
**全部が同じ色に引きずられる**。レンガを指定したら屋上まで赤茶になる。

区画ごとに生成時点で色を決めれば分離できる。マテリアル側の乗算は
**建物ごとの微差**（1.0 のまわりで振る）に留める。

### 再着色は「明るい側」を基準にする

区画全体の平均に合わせると、窓や目地の暗さに引きずられて壁が目標より
**約1.4倍明るく**出る。鈍いレンガ色を指定したのに鮮やかなオレンジになった。
輝度の中央値以上の画素を「壁」とみなして、そこを目標色に合わせる。

## 6. プロジェクト固有の見た目は、プロジェクト側の設定に置く

配色を**共有アセット定義**（全プロジェクト・全都市で読むファイル）に書くと、
別のプロジェクトまで巻き添えになる。

固有の見た目は固有の設定ファイルに置き、未指定なら従来どおりに振る舞わせる。
**コードに固有名（都市名・プロジェクト名）を持たせない。** 三番目の対象が
コード変更なしで独自の様式を宣言できる状態を保つ。

参照名の綴り違いは**必ずキー名付きで落とす**。通すとその一群だけ既定色になり、
レンダを凝視するまで気づけない。

## 7. 小さな立体は既存メッシュに融合する

平面に描いても成立しない要素がある（屋上の設備、看板の袖、庇）。
斜めから見ると立体のシルエットが要るものは形状で作るしかない。

ただし**別オブジェクトにはしない**。既存メッシュに融合させれば、

- オブジェクト数／ドローコールが増えない
- 1メッシュ1マテリアルのまま
- 配置解（どこに何を置くかの計算）を再実行しなくていい

増えるのは三角形だけになる。実例では +47% で、上限の 5.9% に収まった。

### 冪等にする

追加した頂点の**開始位置をメッシュに記録**し、次回はそこから先を消してから
足し直す。これが無いと実行のたびに積み上がる。変更したら**3回連続で実行して
三角形数が一定であること**を確かめる。

### 取り付け面の選び方

「最も高い水平面」では選べない。既にある小さな付加物の天端を掴む
（実測で面積 6m² の面が最上部にあった）。**高さの上位25%にある水平面のうち
最大のもの**のように、面積で選ぶ。

## 8. 終わったと言う前に

数値とレンダの両方を見る。**どちらか一方では足りない。**

機械的に検査できるもの（自動化する価値が高い）:

| 検査 | 期待 |
|---|---|
| 全 UV が 0〜1 の内側 | 範囲外 0 件 |
| 1メッシュあたりのマテリアル数 | エンジンの上限以下 |
| 領域あたりのテクスチャ枚数 | 予算以下 |
| 適用したマテリアルとアセット同一性の一致 | 不一致 0 件 |
| アトラス区画が重なりも隙間もなく敷き詰まる | 画素単位で検査 |
| 乱数がプロセスをまたいで同じ | 同じ seed で同じ結果 |

**そのうえで必ずレンダを見る。** 実例では9件の不具合のうち4件がレンダでしか
分からなかった（屋根の窓、無地の格子の写り込み、色の彩度、非常階段の密度）。
少なくとも「遠景の全体」と「真上から」の2枚を撮る。プレイヤーの視点が
決まっているなら、その高さからの1枚も足す。

### 予算超過を「完了」と扱わない

超過したら**設計を畳む**（カテゴリを統合する、面積配分を見直す）。
予算のほうを上げて通さない。上限が仕様として凍結されている場合はなおさら。

## 9. 静かに壊れる型（詳細は references/failure-modes.md）

- **同一性を可変な名前から引く** — マテリアル名は最適化パスに統合されて別物を指す。
  メッシュ名・アセットIDのような安定した識別子から引く
- **`split(prefix)` で接頭辞を落とす** — 別の接頭辞が語幹を共有していると素通りする
  （`"MATTEX_X".split("MAT_")` は分割されない）。`startswith` + スライスを使う
- **`str.hash` を「決定論的乱数」に使う** — プロセス毎に変わる。同じ seed から
  同じ結果が出なくなる
- **出力先をプロジェクト間で共有する** — 別対象を処理した瞬間に上書きされる
- **一括処理が橋渡し層のタイムアウトを超える** — 数千件を1回で送らず分割する
- **プレビューに出荷しない物が写る** — ライブラリ・破壊状態・コリジョン殻。
  撮影中だけ隠して必ず戻す
- **既存コードの docstring が書いている前提を、自分の変更が壊す** —
  「今は差が無いので統合してよい」の類。最適化は仮定の上に建っている

## 10. 対象プロジェクトへの適用手順

1. 制約を公式文書で確認し、**数値として設定ファイルに書き出す**（後から根拠を辿れる）
2. 既存メッシュの面を数え、分布を採る
3. アトラスの区画配分と寸法を、その分布に対して最適化する
4. 小さな試験範囲（数十〜数百オブジェクト）にだけ適用する
5. レンダを見る。数値検査を通す
6. 判断が要る箇所（色の方向性、密度）は人に見せて決めてもらう
7. 全域へ展開する
8. UV かジオメトリを変えたなら**書き出しをやり直す**。絵柄だけなら画像の差し替えで済む
