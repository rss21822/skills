# Roblox Motif UI

投稿されたモチーフを、そのゲームにしか無い画面の手触りに翻訳し、既存コードを壊さずに Luau で着せ替え、Studio で実測して仕上げる。

ゴールは**モチーフへの忠実さ**。失敗は 2 通りある:

1. **AI の既定値へ収束する** — 紺〜スレートの半透明パネル、1 px の薄い水色の縁、細い白文字、全部同じ角丸カード。管理画面には見えても、遊びたくなる画面には見えない。
2. **このスキルの作例をどのモチーフにも着せる（ハウススタイル）** — クリーム色の紙、太いインクの縁、キャンディ色、艶と下縁、傾いた黄色いピル型 CTA、絵文字、Frame のマスコット。これは「丸くて可愛い」モチーフ（SpinOut の Pop Rink ロビー、`assets/skin-spec.example.json`）への一つの答えにすぎない。高級ホテルに飴色のピル、水墨画にキャンディ色、ホラーに弾むボタンを置けば、紺のダッシュボードと同じくらいモチーフを裏切る。

判定は**言い換えテスト**: スクリーンショットだけ見た人が、何のモチーフか言い当てられるか。モチーフ名を別の物に差し替えても通用する設計なら、まだモチーフを読めていない。

## 成果物

1. **モチーフブリーフ**（下の形式）と **skin spec JSON** → `scripts/skin_preview.py` の lint 結果と style board（HTML / PNG）。コードを書く前に見た目を合意するため。
2. **スキン実装**: `assets/MotifSkinKit.luau` をコピーし、spec から生成した Luau モジュールで初期化。既存 UI へのアダプタと、プレイヤーが一番見る画面（主役画面）の作り直し。
3. **検証**: コンパイル、既存テスト、スキンの Lune テスト、Studio 監査（文字の収まり・48 px のタッチ領域・はみ出し・重なり）、各画面のスクリーンショットで言い換えテスト。
4. **適用と報告**: Place への反映、バックアップ、変更範囲と見送った事項の記録。

## 手順

### 1. モチーフを読む

入力は文章・画像・参考ゲーム・その組み合わせのどれでも来る。**ユーザーが書いた指定（色・書体・「可愛くしない」「紺と白で」「マスコット不要」など）はこのスキルのどの既定値よりも優先する。** 指定と既定がぶつかったら指定に従い、lint の警告は spec の `allow` に理由を書いて通す。

次の 7 軸で言葉にする（`references/motif-design.md` に読み方、トーン別の出発点、作例がある）:

- **トーン**: 可愛い / 元気 / かっこいい / 怖い / 上品 / 懐かしい / 静か …（混ざってよい。「怖いけど子供向け」など）。形・縁・艶・動き・色数の出発点がここで決まる。ステッカー語彙（艶・下縁・太い縁取り・傾き・弾み）はトーンが可愛い/元気のときだけの既定。
- **素材**: そのモチーフの世界で看板や札は何でできているか（紙のステッカー、真鍮、錆びた鉄板、布、和紙、ネオン管、石板、画面のドット…）。パネルの面・縁・艶の有無が決まる。艶は光る素材にだけ。
- **形**: 丸い / 角張る / 手描きで揺れる / 切り欠き / ドットの階段。角丸・縁の太さ・傾きの有無。
- **色**: 役割（インク・紙・主役・アクセント・意味色）に割り当てる。色数もモチーフが決める（墨と朱だけ、4 色のゲーム機、6 色のキャンディ…）。
- **字**: 見出し・ボタン・本文。Roblox に実在する書体だけ（`references/fonts.md`）。
- **物**: マスコットや象徴物。モチーフに生き物がいなければ無理に作らない。代わりに看板の形・紋章・小物。
- **動き**: 弾む / 漂う / キビキビ / じわりと滲む / 明滅（ゆっくり、点滅はしない）。

ユーザーが物を列挙したら（「セーラー服、信号旗、真鍮の舷窓、ロープ」）、**全部を主役画面のどこかに割り当てる**。1 つでも背景の小さな飾りに埋もれると「言ったのに無い」になる。ブリーフに「列挙された物 → 置き場所」を書いて確かめる。

次に**世界の中の UI** を 3 つ探す: モチーフの世界に元からある「表示物」を CTA・パネル・ナビ（ドック/タブ）に割り当てる。例: 西部劇 → 手配書のパネル・保安官バッジの CTA・木の看板のドック。宇宙船 → 計器パネル・警告縞の CTA・ホログラムのタブ。図書館 → 図書カードの一覧・蔵書印の CTA・背表紙のタブ。これが言い換えテストに一番効く。汎用の「角丸カードに色を塗る」はその次の手段。

画像が来たら画像そのものを見て、形・質感・字の雰囲気・構図を書き出し、`python scripts/extract_palette.py motif.png` で色を拾って役割に割り当て直す（写真の色は彩度が低いので UI では上げる）。参考ゲームなら、その UI の部品の作り（縁、書体の性格、色数、CTA の置き方）だけを借りる。

**ブリーフの形式**（出力に残す）:

```
モチーフ: <ユーザーの言葉をそのまま>
トーン: <1〜2 語>
7 軸: 素材 … / 形 … / 色 … / 字 … / 物 … / 動き …
世界の中の UI: CTA=… / パネル=… / ナビ=…
列挙された物 → 置き場所: <ユーザーが挙げた物それぞれ>
構図: <中央 CTA＋下部ドックのままか、モチーフの構図に変えるか>
使わないもの: <このモチーフでは外す既定（例: 艶・マスコット・キャンディ色）と理由>
言い換えテスト: <スクショから何のモチーフと言われるか、決め手になる要素>
```

モチーフが暗い（深海・ホラー・宇宙・夜の街）ときも、暗さはモチーフ固有の色相で出す。**紺そのものがモチーフ**（海軍、夜の港、制服、藍染め）なら紺を使ってよい。そのときは紺を「管理画面の紺」にしない素材（真鍮、ロープ、信号旗、刺繍、藍の布目）と組み合わせる（motif-design.md の「暗いモチーフ」）。

### 2. spec を書き、style board で先に見せる

`assets/skin-spec.example.json`（可愛いトーンの作例）を形式の雛形にして spec を書く。値はモチーフから決め直す（形式は `references/spec-format.md`。トーンに合わせて `shape` のフラグで艶・下縁・縁取り文字・押下の縮みを切る）。次を実行する:

```bash
python scripts/skin_preview.py spec.json --html board.html --png board.png --luau MotifSpec.luau
```

- lint の ERROR は直す。モチーフが求める例外（紺が主題、単色が主題）は `allow` に理由を書く。warning は理由を理解した上で判断する。
- board（PNG）を自分で見て: 言い換えテストに通るか、主役の CTA が一目でわかるか、全部が同じ強さで騒いでいないか。ユーザーが対話中なら board を見せて合意を取る。自律モードなら自己レビューして先に進む。
- 見た目の議論はここで済ませる。Luau を書いた後の配色変更は高くつく。

### 3. 既存 UI を棚卸しする

作り直す前に、何がどこで作られ、何に縛られているかを調べる（`references/integration.md`）:

- テーマ/スタイルのモジュール（色表、ボタン生成関数）、各画面の生成コード、画面の一覧。
- テストや他のコードが参照している Instance 名・属性・階層（壊すと機能が壊れる「名前の契約」）。
- 同じファイルを他の人やセッションが編集中か（`git status`、最近の変更）。
- Place の構成: Rojo で組み立てるのか、Studio で保存された Place に直接スクリプトが入っているのか。

その上で方式を選ぶ:
- **A. 実行時スキン（推奨）**: 既存テーマの色表をその場で書き換え、ボタン等の生成関数を包んで見た目だけ差し替える。共有コードを触らずに済み、失敗時は元の見た目に戻せる。
- **B. 直接編集**: 小さいコードベースを自分だけが触っている場合。
- どちらでも主役画面（最初の画面の CTA、ドック、モード選択、ロード/遷移、リザルト）は専用に作り直す。「世界の中の UI」はここに効かせる。

### 4. 実装する

1. `assets/MotifSkinKit.luau` をゲーム側へコピーし、step 2 の `MotifSpec.luau` を隣に置く。`Kit.new(require(MotifSpec))` で初期化。キットの部品（lip・gloss・badge・mascot など）は必要なものだけ使う。モチーフ固有の部品（手配書の破れ、計器の目盛り、二重線の枠、落款…）は自分で作る。技法は `references/luau-techniques.md`。
2. アダプタ（方式 A）か直接編集（方式 B）で既存画面へ適用。
3. 主役画面を作り直す。

守ること（それぞれ理由がある）:
- **名前と振る舞いは変えない**: Name・Parent 階層・属性・コールバック・有効/無効の判定は元のまま。見た目だけ変える。テストと他の機能がそこに依存している。
- **文字色は面の明るさで決める**（`kit:textOn`）。どの面でも読めることがモチーフの再現より先。
- **Roblox のトップバーを避ける**: `IgnoreGuiInset = true` の画面では、左上のメニュー/チャットのボタン列（上 58 px、左 ~200 px）と右上に文字やボタンを置かない。背景は全面に敷いてよい。安全域は `GuiService.TopbarInset` で取れる（luau-techniques.md）。
- **タッチ領域 48 px 以上**、**絵文字は TextSize の約 1.5 倍の箱**（22 pt なら 36 px）、Unicode 12 までのものだけ（新しいものは □ になる）。
- **日本語**: Roblox 内蔵書体には日本語グリフが無く、システムの CJK 書体に落ちる。その際、要求した太さで描かれるので本文・ボタンは Bold 以上を要求する。英字専用の飾り書体に日本語を流さない（`latinOnly`）。
- **見出しは画面幅で縮む**ように（`kit:fitHeading`）。
- **UIGradient は文字色も掛け算する**。下縁やグラデーションを文字と同じ Instance に掛けるときは、文字が掛かる帯を白にするか、文字色をインクにする。
- **動きは TweenService 経由で reduced motion を尊重**。常時ループは画面が見えていない間止める。点滅・高速フラッシュ（3 Hz 以上）は怖いモチーフでも使わない。
- **全段 pcall**: 書体やプロパティが無くても画面は必ず出る。スキンの失敗で UI が消えるのが最悪の結果。

### 5. 検証する

`references/verification.md` の順に:

1. 変更した全 Luau のコンパイル（`luau.compile` か Studio での読み込み）と既存テスト。
2. スキンの Lune テスト（`assets/lune_gui_mock.luau` と `assets/test_skin_example.luau` を雛形に）: 名前の契約、色の割り当て、無効状態、押下、reduced motion。
3. Studio で Play し `scripts/studio_ui_audit.luau` を execute_luau（Client）に貼って監査。サイズ 3 種 × 対応言語 × 全画面。失敗 0 まで直す。
4. 各画面のスクリーンショット（`screen_capture`、ファイルに残すなら `scripts/capture_studio.ps1`）で言い換えテストと目視チェック。数値の監査は「壊れていない」しか保証しない。

### 6. 適用して報告する

- Rojo 構成なら通常のビルド。Studio 保存の Place なら、変更したスクリプトの Source だけを差し込み、それ以外が変わっていないことを確かめる。差し込み前の Place はバックアップする。
- 他の人・セッションの未完了の変更を巻き込んでいないか、差し込むファイルの差分が自分の変更だけかを確認する。
- 報告には: ブリーフ（モチーフをどう翻訳したか、使わなかったもの）、変えていない範囲とその理由、検証結果（数値と目視）、未検証のもの（実機など）、次の候補。

## 品質基準

どのモチーフでも:
- 言い換えテストに通る。CTA・パネル・ナビの少なくとも 2 つに、そのモチーフでしかありえない形か素材がある。
- ユーザーの明示指定（色・書体・雰囲気・禁止事項）が全部守られている。
- 読める: 本文 4.5:1、大きな文字 3:1 以上。日本語は Bold 以上。
- 1 画面の主役は 1 つで、CTA が最も目立つ（大きさ・明度差・位置・動きのどれで立てるかはトーン次第。傾きや黄色である必要はない）。
- 文字の階層が 3 段以上ある（声になる見出し / 見出し・ボタン / 本文）。
- 紺スレートの AI 既定値に逃げていない（紺が主題なら紺を素材と組み合わせている）。
- トップバーの下に文字やボタンが潜っていない。reduced motion でループが止まる。

モチーフ次第（ハウススタイルにしない）:
- 縁の描き方は素材から: ステッカーなら太いインク、高級なら細い不透明の金の二重線、ドットなら階段状の角、墨なら太さの揺れる筆の帯。「薄くて半透明で意味の無い 1 px」だけが一律に悪い。
- 艶・下縁・傾き・弾む押下は、光る素材・手貼り感・元気なトーンのときだけ。
- 色数はモチーフが決める。墨と朱だけのモチーフにキャンディ色を足さない。
- 空白: 賑やかなモチーフは柄や小物で埋め、静かなモチーフは余白そのものを見せる。
- マスコットは、モチーフに生き物がいてトーンに合うときだけ。
- 構図もモチーフから考える。名前の契約は Name と階層を縛るが、位置と大きさは（テストが縛っていなければ）自由。中央の CTA＋下部の 4 枠ドックは既定値にすぎない（RPG ならコマンドウィンドウを左下、書道なら縦組みで右から、ホテルならフロントのカウンター）。
- CTA の後光（放射状の光）は、モチーフに光源があるときだけ。英大文字の小さな設定テキスト（"SITE A-7" など）も毎回は付けない。

## よくある失敗

- どのモチーフでも黄色いピルの CTA・キャンディ色のドック・マスコットになる → ハウススタイル。トーンの出発点と「世界の中の UI」から組み直す。作例の値を流用しない。
- どのモチーフでも同じ構図（中央 CTA＋後光＋下部 4 枠ドック）になる → 色と素材は変わっても骨格がハウススタイル。ブリーフの「構図」でモチーフの構図を検討する。
- ユーザーが挙げた物の 1 つが画面に見当たらない → ブリーフの「列挙された物 → 置き場所」を埋めずに作った。
- 日本語をドット文字や筆文字にしたい → Roblox の内蔵書体には無い。できること（太い日本語で妥協、英字・数字だけ専用書体、画像のビットマップ文字）と限界をユーザーに伝える（fonts.md）。
- ユーザーが「紺で」「可愛くしないで」と書いたのに、lint やこのスキルの既定に合わせて変えた → 指定が優先。`allow` に理由を書く。
- lint を通したのに Studio で書体が変わらない → spec の書体名が Roblox に無い（Web フォント名を書いた）。`references/fonts.md` の一覧から選ぶ。
- 日本語だけ細く見える → 本文やボタンに Regular を要求している。Bold 以上に。
- 絵文字や見出しが TextFits で落ちる → 箱が小さい。絵文字は 1.5 倍、見出しは fitHeading。
- 絵文字が □（豆腐）になる → Roblox の絵文字フォントは Unicode 12 まで。🪙🪄🫧🪼 などは使えない。
- タイトルが Roblox のメニューボタンの下に潜る → `IgnoreGuiInset = true` の画面で上端に文字を置いた。上 58 px の左右を空ける。
- ボタンの文字色がくすむ → 同じ Instance の UIGradient が文字も掛け算している。
- 画面を開くと同じ内容が二重に並ぶ → 描画中に自分のサイズを変え、AbsoluteSize の監視から描画が再入している（integration.md）。
- 既存テストが落ちる → Instance 名や階層を変えた。見た目の部品は子として足し、元の部品は残す。
- スクリーンショットに BillboardGui が写らない → AlwaysOnTop の Billboard は Studio の画面キャプチャに出ない。確認時だけ AlwaysOnTop を切る。
