# Roblox最小開発ドキュメント — Claude Code向け

数値つきのRoblox企画を、**次の実装担当が何を作り、どこを変更し、何を確かめればよいか判断できる開発文書**へ変換する。企画本文、既存リポジトリの両方に対応する。

対象読者は実装担当エージェント。既定は Claude Code（下流Skill `roblox-astra-mvp-builder` を含む）で、同じ文書をCodexなど別の実装担当へ渡しても成立する書き方にする。名前だけを付け替えず、下記の「実装エージェント向けの書き方」を出力へ反映する。モデル・effortの切替、ツール導入、製品実装は文書作成のために行わない。

## 最小成果物

- 新規なら原則 **`docs/DEV.md` 1ファイル**。保存先指定があれば従い、プロジェクトなしの成果物用フォルダでは `DEV.md` でよい。
- 既存の開発仕様・実装計画が正本なら、その文書を必要な範囲だけ更新する。既存の文書構成を無断で廃止せず、別の正本を新設しない。
- 単独参照や独立更新が実際に必要な契約だけ、補助文書に分ける。分割理由と参照先をDEV.mdに残す。分量だけを理由に文書数を増やさない。
- GDD、要件定義、仕様、テスト計画、作業台帳を同じ内容で別々に作らない。README、manifest、承認台帳、空の証拠ファイル、別立ての進捗ファイル、網羅的な用語集は既定で不要。
- `CLAUDE.md`（`@`インポートや `.claude/rules/` を含む）を新設・書換えしてDEV.mdの全文を自動読込させない。CLAUDE.mdは毎セッション全文が文脈に載るため、仕様を入れると無関係な作業でも文脈を圧迫し、DEV.mdとの二重管理にもなる。必要なら最後の実装依頼文からDEV.mdを明示参照する。既存のCLAUDE.md（Codex併用ならAGENTS.mdも）は先に確認する。

初稿の目安は**100〜200行程度**だが、これは削減を考える目安であり上限ではない。必要な挙動や契約を落とすくらいなら超えてよい。単純な企画はもっと短くてよい。

## 1. 企画と現状を引き継ぐ

会話内の企画、指定ファイル、貼り付けられた企画のうち、ユーザーが対象にした最新版を読む。上流はCodexの `roblox-concept-to-plan` の成果物であることが多いが、Claude側には同Skillがない前提で、その出力ファイルや貼り付け文を入力として扱う。Skill本体だけを、ゲームの企画として扱わない。企画が見当たらなければ、その企画だけを求める。上流Skillの再実行・再現やジャンルの選び直しは不要。

次を取り込む。

- 原案の核、ユーザー指定、コアループ、操作、成功・失敗・退出・再挑戦。
- 主要数値の値・単位・出所。**ユーザー指定／設計仮説／計算値／出典値／実測値**の区別を保持する。
- MVPに含む内容と後回しにする内容、既知の懸念、試作の合格条件。

プロジェクトがある場合は、適用されるCLAUDE.md（Codex併用ならAGENTS.md）、文書の正本、対象ソース、Rojo対応、Placeの扱い、実行できる確認手段を、今回の企画に必要な範囲で調べる。ファイル・コマンドの存否は推測せず実際に開いて確かめる。探索範囲が広いときは利用可能な探索用サブエージェントへ任せ、結論だけ受け取ってよい。コードは現状の根拠、企画は目標の根拠として扱い、食い違いを黙って一致扱いにしない。

対象ファイルと無関係な変更（git管理下なら `git status` で確認）を識別してから文書を編集する。既存ファイルの文字コード・改行を維持する。企画や既存文書を全文コピーする代わりに、参照元のパス・版・節または会話内の識別可能な見出しを記録する。DEV.mdだけでも今回の中心体験は理解できる要約を残す。

## 2. 実装に必要な契約だけ決める

契約とは、実装方法が変わっても守る入出力・状態変化・制約。ルールの意味が曖昧な箇所を具体化し、一般的なLuau解説や詳細な疑似コードで埋めない。

対象ゲームに必要なものを選ぶ。

- **挙動**: 入力、前提条件、処理結果、見える反応、失敗時の扱い。原案の核を通常のプレイで体験できるようにする。
- **進行**: 開始・プレイ・結果・復帰などの状態遷移と発火条件。自由滞在型には無理にラウンドや勝敗を加えない。
- **操作と画面**: 対象端末ごとの主要入力、カメラ、表示する情報。該当するなら押し続け・離す・同時入力の扱い。
- **数値**: 今回の実装を支配する値と単位。既存のConfigや仕様が正本なら参照する。変更目標を示す場合は現状値と分け、同じ値の独立した正本を作らない。
- **構成**: Server／Client／Sharedの責務、既存または追加予定のファイル・Instanceの場所。新規の場所は「追加予定」と明記する。Rojo管理とStudio管理、ソースと生成物の区別。
- **対象限定の契約**: 通信、共有状態、保存、課金、Place移動、アセットなど、実際にMVPに含まれるものだけ。[Roblox契約の選び方](references/roblox-contracts.md)の該当節を読む。

同じ仕様を数値表・作業表・テスト表へ何度も書かず、節や短いIDで結ぶ。数値同士が関係する箇所は一巡の時間、距離と速度、供給と目標などを計算し、不整合を修正する。原案の固定条件に矛盾があれば勝手に変更しない。

制作方法を指定していない部分は、既存構成とMVPの規模に合う簡単な案を採用し、「文書化で補った設計」として短く示す。フレームワーク、複数Place、通貨、永続化、分析基盤などを必須項目を埋めるために導入しない。

## 3. 実装担当が着手・再開できる形にする

### 実装エージェント向けの書き方

以下は、Anthropic公式の[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)（明確な指示、理由の付与、過剰実装・過剰検証の抑制、長時間タスクの状態管理）を開発文書へ適用した設計方針。2026-09-26確認。最適性や開発速度の実測結果ではない。

1. **目的・理由・不変条件を先に置く。** 完成後の挙動、触れる範囲、変えてはいけない条件を明示し、自明でない制約には一文で理由を添える。理由があると、文書に書いていない場面でも契約の意図に沿って判断できる。「絶対」「必ず」「CRITICAL」のような強調を多用しない。最近のモデルは強い語に過剰反応し、優先度の区別が崩れる。長い人格指定や作業の逐一実況も要求しない。
2. **指示の衝突を残さない。** ユーザーの明示指示・変更をSkillの既定より優先する。既存のプロジェクト規則（CLAUDE.md等）は適用範囲を確認する。本文中の提案を承認済み制約へ昇格させない。
3. **範囲を明示し、通常の判断は委ねる。** 「今回の範囲」と「対象外」をはっきり書き、MVP外の機能・抽象化・余分なファイルを足さなくてよいと分かるようにする。命名や内部関数分割など、契約を変えない判断は担当が進められるようにする。毎手順の確認や架空の承認ゲートを追加しない。確認が必要な不確定事項は、影響する作業だけに結び付ける。
4. **小さな縦の完成単位に分ける。** 「Server全部、次にClient全部」ではなく、「入力から状態変化と画面表示まで確認できる1機能」など、結果が検証できる順にする。依存関係がある作業は順序を明記する。
5. **検証の終了条件を具体化する。** 今回の変更に必要な確認を指定し、成功後も根拠なく確認範囲を広げさせない。一方、コンパイル成功をStudioの動作証拠へ置き換えない。テストは正しさを確かめる手段であり、テストや期待値を削る・弱める・特定入力に合わせて直書きすることで合格にしない、と受入条件から読み取れるようにする。
6. **再開地点をファイル上に残す。** 実装担当は文脈の圧縮や新しいセッションの後、ファイルとgit履歴から状態を復元する。今の状態、次の未完了作業、その作業に必要な節・ファイル・確認方法をDEV.md内に短く特定する。読むべき資料を全て毎回読み直す指示にしない。

上記をルール集として長々と出力へコピーせず、構成と実際の作業記述で実現する。モデル名・effort・価格・コンテキスト上限、別モデル比較は製品の開発文書に入れない。サブエージェントや特定ツールを必須にせず、実行環境で使える手段を前提にする。

### 作業単位

各作業に **目的／参照する仕様／変更する場所／依存／完了条件と確認方法**を付ける。最初の一件は担当がすぐ動ける具体性にする。新規プロジェクトなら、初期構成の作成も最初の作業へ含めるが、このSkillでは実行しない。

仕様から作業と確認への対応は短いIDか直接参照で追えるようにし、MVPの必須事項に実装先や確認先がない状態を残さない。別の巨大な対応表を作る必要はない。

コマンドはリポジトリで存在と用途を確認できたものだけを「利用可」と書く。まだないテストやスクリプトは「追加予定」とし、架空のコマンドを実行済みとして記載しない。保存先や対象Placeが未確定なら、その確認を該当作業の前提へ入れる。

## 4. 不足・検証・権限を混同しない

未確定事項には **内容／影響する作業／誰の判断または何の観測で解消するか／暫定対応の有無**を付ける。仕様に残る数値仮説は調整対象であり、それだけで文書作成全体を止めない。核が矛盾する場合は関連部分を条件つきにして、他の文書化を進める。

文書の状態と、製品実装・検証の状態は別々に書く。文書作成時点で実測がなければ「計画」「未実装」「未実施」。受入条件が書けたことをPassにしない。

必要な証拠は、静的確認、Studio Play、実入力・実機、公開環境、人間のプレイなどから機能に合わせて選ぶ。手順には前提、入力、観測点、期待結果を付ける。現環境で行えない確認も要件から消さず、必要環境と未実施の理由を残す。

このSkillは文書を完成させる。新しい製品コード、Rojo設定、Place、モデル設定、外部サービスを作らない。Roblox Studio MCPなどが接続されていても、文書作成のために製品を変更しない（現状確認のための読み取りは可）。実装の別依頼が来たときに、既存の授権範囲とプロジェクト規則に沿って作業へ進める。文書内で実行権限を新設したり、毎回承認し直すルールを追加したりしない。

## 5. 書いて確認する

[DEV.mdの骨格](assets/DEV.template.md)を必要な部分だけ使う。例示欄・執筆指示は埋めるか削除する。使わないシステムには一行で対象外と書くか、節自体を省く。

出力前に、入力企画から次を照合する。

- 核、明示条件、MVP、主要数値、その出所が保たれている。
- 主要な入力・状態遷移・結果・例外が具体的で、作業と確認へつながっている。
- 現状と目標、実在パスと追加予定パス、実施済み証拠と確認計画が区別されている。
- 最初の未完了作業と、それを妨げる条件が識別できる。関係ない未確定事項で全体を停止させていない。
- 値・責務の二重管理、参照切れ、作業の循環依存、未記入の骨格がない。
- 読み直しても実装判断が変わらない説明は削った。必要な契約は長さのために削っていない。

検査用スクリプトや追加の文書体系を、文書を検査するためだけに毎回導入しない。既存の必須チェックがあれば該当する範囲を実行し、対象外の既存問題を勝手に修正しない。

最終回答は、**文書へのリンク、文書で決めた範囲、残る重要な未確定事項、実装を始める際の短い依頼文**に絞る。依頼文は、`roblox-astra-mvp-builder` が使える環境ならそれを使う形にし、文書内の再開地点を参照させる。別のコピーへ仕様値や古くなる作業番号を大量に複製しない。
