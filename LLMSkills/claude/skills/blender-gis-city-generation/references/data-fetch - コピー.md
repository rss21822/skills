# 地理データの取得

公開 API から都市規模のベクタデータを取る。相手は無償の共有資源なので、
作法を守らないと止められる。

## レイヤ別に取る

1回の巨大クエリで全部取ろうとしない。必要なレイヤを分けて取る。

| レイヤ | 何に使うか |
|---|---|
| 建物 | 高さ分布・建蔽率・用途の推定 |
| 道路 | 街区の切り出し・街路の向き |
| 海岸線・水域 | 陸海マスク・シルエット |
| 用途区分（landuse） | ゾーニングの観測事実 |
| 鉄道・橋 | インフラ配置 |
| ランドマーク | 個別配置する対象 |

レイヤごとに分ければ、1つが失敗しても他は使える。再取得も部分的で済む。

## 範囲はタイルに割る

都市規模の範囲は1リクエストに収まらない。緯度経度で格子に割って取る。

**隙間ができていないか検査する。** 範囲内にランダムな標本点を撒き、
どのタイルにも入らない点が無いことを確かめる。境界の扱いを1つ間違えると
細い帯が抜けるが、出力を見ても気づけない。

## 空の応答を成功と見なさない

ミラーによっては **HTTP 200 で要素ゼロ**を返す。これを成功として扱うと、
そのタイルだけ静かに欠ける。

「200 かつ要素0」は、その範囲に本当に何も無い場合を除き**失敗として扱う**。
判断がつかないなら失敗側に倒す。

## エンドポイントの健全性を順序に反映する

複数のミラーを回すとき、失敗が続いたものを先頭に置き続けない。
連続失敗数で安定ソートし、**降格はするが除外はしない**（一時的な不調で
恒久的に失うのはもったいない）。

## 再試行と待ち時間

- 指数的に待つ。即座に叩き直さない
- レート制限（429）は待ち時間を長めに取る
- タイムアウトは長めに設定する。都市規模のクエリは分単位で返ることがある

## キャッシュする

同じ範囲を何度も取らない。キャッシュの鍵には**クエリを決める要素を全部**入れる。

範囲・レイヤ・タイル位置・クエリ本文・API 版・タイル分割幅。1つでも漏れると、
条件を変えたのに古い結果が返る。**鍵が全成分を弁別しているかテストで確かめる。**

## 書き込みは原子的に

途中で落ちたときに壊れた JSON が残ると、次回の実行が「キャッシュがある」と
誤認する。一時ファイルへ書いてから `rename` する。**部分書き込みが残らないこと**を
テストする。

## 連絡先の扱い

Overpass は User-Agent に連絡先を入れることを推奨している。入れると
レート制限が緩むことがある。

ただし**第三者のサーバへ個人のメールアドレスを送ることになる**。
勝手に設定せず、ユーザーに確認する。環境変数で渡し、リポジトリには置かない。

## ライセンスと帰属

| データ源 | ライセンス | 義務 |
|---|---|---|
| OpenStreetMap | ODbL | **帰属表示が必須** |
| PLATEAU（日本） | CC BY 4.0 系 | 出典表示 |
| Google Earth / Maps / 3D Tiles / Cesium ion | — | **利用不可**（ToS 違反） |

帰属文をパイプラインが**自動生成**してゲーム内クレジットに載せる。手書きだと
データ源を足したときに更新が漏れる。

ライセンス不明のアセットは混ぜない。「たぶん大丈夫」で入れたものは後から
特定できなくなる。

## 座標系

**Web メルカトルで距離を測らない。** 緯度によって距離が膨らむ（東京の緯度で
1.23倍）。街区の寸法も建物の間隔も狂う。

原点を対象都市に置いた**局所的な等距離投影**（方位等距離図法など）を使う。
原点がちょうど (0, 0) m になるので、後段のデバッグも楽になる。

## 取得結果の妥当性

取得した直後に、少なくともこれを見る。

- 要素数がレイヤごとに桁で妥当か（建物が数十件しかない都市は無い）
- 建物の高さタグが付いている割合（後段の統計の信頼度に直結する）
- 海岸線が閉じているか、切れているか

高さタグの充足率は都市によって桁違いに変わる。実測では東京 0.9%、
ニューヨーク 74.6% だった。**この差を吸収する設計にしておく**（次の
`terrain-analysis.md` を参照）。
