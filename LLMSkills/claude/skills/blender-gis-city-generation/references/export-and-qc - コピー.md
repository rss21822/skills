# 破壊状態・書き出し・検査

## 破壊状態はひな型ごとに事前に作る

実測メッシュを直輸入していたら作れない。ひな型方式を採った最大の理由。

3状態が基本。

| 状態 | 内容 |
|---|---|
| intact | そのまま |
| damaged | 上部の崩落、外壁の剥離、屋根の破孔、傾き、へこみ |
| ruin | 瓦礫の山、平たい残骸、飛散、クレーター |

加えて**瓦礫プリセット**を数種（低ポリ・共有）。クライアント側の演出に使う。

崩落を作るときは、**傾けた平面で切る**。水平に切ると人工的に見える。
切断面には床スラブと折れた柱を足すと、内部が見えている感じが出る。
頂点に微小な揺らぎを入れる（元の寸法の 10% 程度）。

### ゲームバランス数値は入れない

**HP・ダメージ・スコア・遷移閾値はここで決めない。** マニフェストには
状態の対応表だけを書き、閾値は空のまま渡す。

ここで決めるとゲーム側のデータ定義と二重管理になり、片方だけ直る。

## 書き出し

破壊状態のメッシュは**状態ごとにセクター分割しない**。状態はひな型単位の
性質であってセクター単位ではないので、セクター×状態で書き出すと同じメッシュを
何百回も複製することになる（実測で 351セクター×3状態＝1,053ファイル、約4時間）。

正しくは:

- セクターごとに `intact` を1本
- 破壊状態と瓦礫は**まとめて1本**
- どのインスタンスがどの状態メッシュを使うかは**マニフェスト**が対応表として持つ

### 書き出し設定

エンジンの規約に合わせる。少なくとも確認するもの:

- 上方向の軸（Y-up か Z-up か）
- 三角化の要否
- 単位（メートルか、エンジン独自の単位か）
- 命名規則
- テクスチャを埋め込むか、外部参照にするか

単位変換は**書き出し時に変換行列へ焼く**。座標そのものは実寸のまま保つと、
デバッグのときに地図と突き合わせられる。

## マニフェスト

書き出しと対になる JSON。少なくとも:

- インスタンスの一覧（位置・回転・スケール・使うメッシュ・コリジョン）
- セクターごとの集計（オブジェクト数・三角形数・ファイルサイズ）
- 破壊状態の対応表
- 生成に使った設定値（圧縮率・原点・seed）

**設定値を書いておく**と、後から「なぜこの配置になったか」を検算できる。

## 予算検査

領域ごとに数えて、上限と突き合わせる。

| 項目 | なぜ効くか |
|---|---|
| オブジェクト数 | ドローコールと管理コスト |
| 三角形数（領域・単体） | 描画コスト |
| テクスチャ枚数 | VRAM とバインド回数 |
| 1メッシュあたりのマテリアル数 | エンジンの制限に触れることがある |

**超過したまま「完了」と言わない。** 終了コードを 1 にする。警告を握り潰す
仕組みを作らない。

超過したら設計を畳む（ひな型を統合する、LOD へ降格する、セクターを細かくする）。
上限のほうを上げて通さない。上限が仕様として凍結されているならなおさら。

## 異常検知

配置の誤りは目視では見つからない。機械で数える。

| 異常 | 判定 |
|---|---|
| 浮遊 | 地面から一定以上浮いている |
| 地面貫通 | 一定以上沈んでいる |
| 重複配置 | 同一ひな型が至近距離に2体 |
| ゼロ体積 | 体積が閾値未満 |

**総当たりで距離を測らない。** 数万体では終わらない。格子ハッシュで
近傍だけを見る。

## プレビュー

**数値検査だけでは足りない。** 実測19件の不具合のうち、複数はレンダを見て
初めて分かった。そのとき数値検査は全部緑だった。

最低限:

- 上空俯瞰1枚
- プレイヤー視点の高さから数枚（角度を変えて）

### 撮るときの注意

- **クリップ距離を明示する。** 既定値（100m 程度）のままだと都市が丸ごと消える。
  「真っ黒な画像」を眺めても原因は分からない。境界を数値で射影して確かめる
- **画角を実測から決める。** 外接球で合わせると、縦画角の狭いレンズでは
  遠すぎる位置に置かれる（566×464m の街を 3,285m 先から撮ったことがある）
- **出荷しないものを隠す。** ひな型ライブラリ、破壊状態、瓦礫、コリジョン殻が
  シーンに残っていると写り込む。撮影中だけ隠し、`finally` で必ず戻す

ひな型ライブラリの写り込みは、全体が無彩色のうちは街に紛れて気づけない。
見た目を変えた瞬間に露呈する。**「今まで気づかなかった」は「今まで無かった」ではない。**

## クレジット

データ源とライセンスを**パイプラインが自動生成**してゲーム内クレジットに載せる。

手書きにするとデータ源を足したときに更新が漏れる。OSM は帰属表示が
ライセンス上の義務であって、任意ではない。

## 人間に渡す境界

エンジンへの搬入（インポート、アセットのアップロード、モデレーション審査）は
**人間の工程**として明示的に分ける。自動化できる部分でも、権利とアカウントが
絡むので勝手に進めない。

API キーは環境変数のみ。リポジトリに置かない。
