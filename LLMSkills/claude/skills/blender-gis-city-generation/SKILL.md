# 地理データからゲーム用の都市を作る

実在都市の**ベクタGIS**を入力に、エンジンの予算に載る 3D 都市を手続き生成する。

## まず用語を正す — 衛星データは使わない

「衛星データから都市を作る」と言われることが多いが、実際に使うのは
**ベクタGIS**（建物の輪郭ポリゴン、道路の線、海岸線、用途区分、階数タグ）であって、
衛星画像でもフォトグラメトリでもない。

これは好みの問題ではない。

- **Google Earth / Google Maps / 3D Tiles / Cesium ion 由来のメッシュ・点群・
  テクスチャは利用規約違反**。取得も利用もしない
- 実測メッシュはそもそもゲーム予算に載らない（次節）

入力は OpenStreetMap（ODbL・**帰属表示が必須**）や自治体のオープンデータ
（日本の PLATEAU は CC BY 4.0 系）。ライセンス不明のアセットは混ぜない。

ユーザーが「衛星データ」と言ったら、何を指しているか確かめる。多くの場合
「地図データ」の意味で使っている。

## 設計の核 — 実測を直輸入せず、ひな型から生成する

**実データは統計の供給源として使い、ジオメトリは建物ひな型（アーキタイプ）
20〜30種の手続き生成と配置で作る。**

理由が3つあり、どれも後から覆せない。

1. **数万棟の実測メッシュはエンジン予算に載らない**
2. **破壊状態を事前に作れるのはひな型方式だけ。** 実測を直輸入すると
   「壊れる街」が原理的に作れない。破壊が企画の中心なら、ここで方式が決まる
3. **都市の「らしさ」は街区リズム・高さ分布・海岸線のシルエット・ランドマークで
   9割決まる。** 1棟ごとの正確な形は効かない

ひな型方式を採ると、実データから取り出すのは以下になる。

- 街区の輪郭と向き（道路網から）
- 街区ごとの建蔽率・平均高さ・高さの分位
- 用途ゾーン（住宅／商業／工業／港湾）
- 海岸線と水域
- ランドマークの位置と概寸

## 工程

各工程が**何を決めるか**と、**何を確かめないと静かに壊れるか**。

| 工程 | 決めること | 静かに壊れる箇所 |
|---|---|---|
| **設定検証** | 対象範囲・原点・投影・圧縮率・予算 | 綴り違いのキーが既定値に落ちる |
| **取得** | どのレイヤをどう分割して取るか | タイルの隙間、空応答を成功と見なす |
| **解析** | 陸/海、街区、ゾーン、高さ分布、街路の向き | 陸海の反転、建物数を密度と取り違える |
| **ひな型生成** | 形状・LOD・コリジョン・UV | 部品が本体から飛ぶ、LODが無駄に増える |
| **配置** | どの街区に何をいくつ、どの向きで | スケール圧縮の適用漏れ、高さ統計の汚染 |
| **最適化** | マテリアル統合・LOD降格 | 予算内なのに降格して都市が消える |
| **破壊状態** | intact / damaged / ruin ＋瓦礫 | ゲームバランス数値を混入させる |
| **書き出し** | セクター分割・FBX・マニフェスト | 常駐オブジェクト数でエンジンが落ちる |
| **検査** | 予算・異常検知・プレビュー・クレジット | 超過したまま「完了」と言う |

詳細はそれぞれ `references/` を参照。

- `references/data-fetch.md` — 取得の作法、タイル分割、キャッシュ、エンドポイント
- `references/terrain-analysis.md` — 陸海判定、街区、ゾーニング、統計
- `references/build-and-place.md` — ひな型、スケール、配置、セクター、メモリ
- `references/export-and-qc.md` — 破壊状態、書き出し、予算検査、プレビュー
- `references/citygen-example.md` — 実装例（`Claude3DProject/Tokyo`。**そこでは正本**）

## この領域の失敗は「静かに間違う」型に偏る

実プロジェクトで19件出た不具合のうち、**例外も警告も出ないもの**が大半だった。
落ちてくれれば楽なのだが、落ちない。

代表例を挙げる。どれも「動いている」ように見える。

- **陸と海が反転**していて、建物103棟のうち100棟が海上と判定された
- **建物数を密度の主軸**にしたため、巨大な footprint 2つの CBD が「疎」に分類された
- **スケール圧縮を位置だけに適用**し、街区あたり1棟の「村の集まり」になった
- **高さ統計がタグ既定値に汚染**され、低層が配置の93%を占めた
- **LOD距離を静的な距離規則と誤読**し、351セクター中271を板ポリ化して都市を消した
- **文字列置換が一度も一致していない**のに「patched」と表示し続けた

対処は3つ。

1. **不変条件をテストで固定する。** 「落ちないが間違う」ものは目視では守れない。
   陸海の向き、ゾーン判定、スケールの一貫性、決定論的乱数などを機械で検査する
2. **レンダを見る。** 上記のうち複数はレンダを見て初めて分かった。数値検査は全部緑だった
3. **前提が書かれているコメントを疑う。** 「今は差が無いので統合してよい」の類は、
   後の変更で前提ごと壊れる

## スケール圧縮は位置と寸法の両方に掛ける

1:1 の実寸では、プレイヤー（特に巨大キャラクター）との相対感が成立しない。
距離を圧縮して「名所が近い」街にする。

**圧縮率は位置にも建物寸法にも同じだけ掛ける。** 位置だけに掛けると街区が
詰まって建物が入らなくなり、街区あたり1棟の散村になる。実際そうなった。

高さは別に補正してよい（相対感を優先して +10〜20%）。掛ける順序と対象を
1か所に集約し、マニフェストへ記録して後から検算できるようにする。

## 大量インスタンスはメモリで落ちる

数万オブジェクトを常駐させると 3D ソフトが落ちる。**未保存のシーンを失う。**

対策は「同時に載せる数を減らす」。配置解（どこに何を置くか）を JSON に持ち、
書き出しは

```
1セクター生成 → 書き出し → 破棄
```

を繰り返す。ピーク時のオブジェクト数がセクター最大に収まり、落ちても失うのは
1セクターぶんで済む。

**重い工程の後は必ず保存する。**

## ひな型は共有し、インスタンスは軽くする

同じひな型を参照するリンク複製にすると、

- メッシュ編集が全インスタンスに伝わる（UV の張り直しなどを後から一括でできる）
- メモリとファイルサイズが1棟ぶんで済む

**インスタンスごとのスケール差を作らない**と、後段でアトラス化する際に
引き伸ばしが起きない。バリエーションはひな型の種類とバリアントで出す。

## 破壊状態はここで作る。ゲーム数値はここで決めない

intact / damaged / ruin の3状態と瓦礫プリセットは、ひな型ごとに事前に作る。

**HP・ダメージ・スコアといったゲームバランス数値はこのパイプラインの管轄外。**
マニフェストには状態の対応表だけを書き、閾値は空のまま渡す。ここで決めると
ゲーム側のデータ定義と二重管理になる。

## 終わったと言う前に

- 予算検査（オブジェクト数・三角形数・テクスチャ枚数）が**全領域で**通ること
- 異常検知（浮遊・地面貫通・重複配置・ゼロ体積）が0件
- 自動テストが通ること
- **プレビューを見ること。** 最低でも上空俯瞰1枚と、プレイヤー視点の高さから数枚
- クレジット（データ出典・ライセンス）が生成されていること

**予算超過を「完了」と扱わない。** 超過したら設計を畳む（ひな型を減らす、
LOD を使う、セクターを分ける）のであって、予算を上げて通さない。
