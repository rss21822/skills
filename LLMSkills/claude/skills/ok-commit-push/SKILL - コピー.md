# OK → Commit & Push

ユーザーが「OK」とだけ送ってきたとき、直前の作業内容を git にコミット＆プッシュする。
これは「今の変更で確定・承認」という意思表示だと解釈してよい。

## 手順

### 1. 変更確認（読み取りのみ）

次の3つを並行して確認する。

```bash
git status
git diff HEAD
git log --oneline -5
```

- `git status` で変更ファイルを把握する
- `git diff HEAD` で変更内容の中身を把握する
- `git log` で既存コミットのメッセージスタイルを把握する（日本語か英語か、prefix があるかなど）

変更がなければ（untracked も staged も modified も何もなければ）、
「変更がないためコミットをスキップしました」と報告して終了する。

### 2. コミットメッセージを考える

git log のスタイルを参考にメッセージを決める。
- 既存が日本語なら日本語、英語なら英語
- `feat:` `fix:` のような prefix がある場合はそれに合わせる
- 変更内容を1行で端的に表す（長くても72文字以内）

末尾には必ず次を付ける:
```
Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
```

### 3. ステージング

センシティブファイルを除いて、関連ファイルを選択的に add する。

除外するもの（git add しない）:
- `.env` `.env.*` など環境変数ファイル
- `*.key` `*.pem` `*.secret` など認証情報
- `node_modules/` `__pycache__/` などキャッシュ

それ以外の変更済み・新規ファイルをすべて add する。
ファイルが多い場合でも `git add .` ではなく、除外ルールを意識した add をすること。

### 4. コミット

メッセージは HEREDOC で渡す（特殊文字のエスケープを避けるため）:

```bash
git commit -m "$(cat <<'EOF'
<コミットメッセージ1行>

Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
EOF
)"
```

### 5. プッシュ

```bash
git push
```

失敗した場合（リモートに新しいコミットがある等）は、エラー内容をそのまま報告し、
`git pull --rebase` して再pushするかどうかをユーザーに確認する。
自動でforce-pushは絶対に行わない。

### 6. 結果報告

完了したら以下を簡潔に報告する:
- コミットハッシュ（短縮形）
- コミットメッセージ
- push 先のリモート/ブランチ名

## 例

```
コミット完了: a1b2c3d
  "feat: プレイヤー移動速度の調整とアニメーション修正"
  → origin/main へ push しました
```

## 注意

- `--no-verify` は使わない（hooks を尊重する）
- force-push (`--force`) は使わない
- 空コミットは作らない
- ユーザーから明示的な確認なしに destructive な操作（reset, rebase 等）は行わない
