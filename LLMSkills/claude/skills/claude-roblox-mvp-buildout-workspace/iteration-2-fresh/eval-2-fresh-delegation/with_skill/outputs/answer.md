# Codex CLI へ「サーバー側 当たり判定バグ修正」を投げるための指示文一式

ご相談の 2 つの事故（バックグラウンドで何時間も止まる／モジュールが読み込めなくなる書き方をされる）は、どちらも**起動コマンドとプロンプトの定型で塞げる種類**です。以下、(1) 起動、(2) 投げるプロンプト本文、(3) 投げたあとにこちらで確認すること、の順に置きます。

`《 》` は埋めてください。

---

## 0. 投げる前に一度だけ決める分岐

当たり判定の不具合は「コードはどこも仕様どおりで、繋がり方か実行環境だけが違う」型が非常に多い領域です。そのため、まず次を決めます。

| 状態 | 投げるもの |
|---|---|
| 原因が `file:line` まで特定できている | **§3 の修正プロンプト**をそのまま |
| 「当たらない／当たりすぎる」しか分かっていない | **先に §2 の調査専用プロンプト（読み取り専用）**。修正はそのあと |

原因未確定のまま修正を投げると、実装側は推測を前提に「修正」します。実例として、不可解な場外判定の真因が「入力が入りっぱなしで本当に外へ出ていただけ」だったことがあり、そこで推測のまま直していたら**正しい判定のほうを壊していました**。分岐を惜しまないほうが結果的に速いです。

## 1. 起動コマンド（ハング対策の本体はここ）

```bash
codex exec --model 《pinned-model》 -c model_reasoning_effort=high \
  --sandbox workspace-write --skip-git-repo-check "$(cat 《prompt.md への絶対パス》)" < /dev/null
```

守る点は 4 つです。

1. **`< /dev/null` は必須。** これが無いと標準入力待ちで永久に停止します。前回の「何時間も止まっていた」はほぼ確実にこれです（実測で 11 時間ハングし、その間の進捗はゼロでした）。バックグラウンドだと、止まっていることと考えていることの区別がつかないので特に効きます。
2. **モデルは毎回コマンドラインで明示する。** 設定ファイルの既定値に暗黙依存すると、後から「どのモデルが書いたか」を再構成できません。
3. **プロンプトはファイルに書いて渡す。** クォート地獄を避けられて、投げた内容がそのまま記録に残ります。
4. **長い実装はバックグラウンドで投げ、完了通知で受ける。ポーリングしない。**

**Windows での標準入力の閉じ方**（`<` は PowerShell では使えません）:

- Git Bash から上記コマンドをそのまま実行するのが一番素直です。
- PowerShell から出すなら `cmd /c "codex exec ... < NUL"`、あるいは `Start-Process ... -RedirectStandardInput "NUL"`。
- いずれにせよ **stdout / stderr はログファイルへ落としてください**。§4.1 のハング判定でファイルのバイト長を使います。

調査だけ投げる場合（§2）は `--sandbox read-only` に変えます。

## 2. 調査専用プロンプト（原因未確定のとき／読み取り専用）

~~~text
# 役割
Rojo プロジェクトのサーバー側当たり判定の不具合について、根本原因を特定する調査のみを行う。
**コードは一切書き換えない。** 記述による報告だけを返す。

# baseline
リポジトリ: 《repo path》
commit: 《baseline commit hash》
（作業前に git rev-parse HEAD を実行し、上記と一致することを報告に含めること）

# 症状（実測値のみ。推測は含めていない）
- 《例: プレイヤー2人が接触した状態で、サーバーの hit ログが1行も出ない。players=2、接触は目視で確認》
- 《例: hit=accepted は出るが damage=0 が続く。同セッションで 12 回中 12 回》
- 再現手順: 《手順》
- 再現率: 《n / m 回》

# 調査対象（この範囲だけ読む）
- 《src/ServerScriptService/... の具体パス》
- 《src/ReplicatedStorage/Shared/... の具体パス》

# 出力してほしいもの
1. 根本原因を `file:line` で指し示すこと
2. 最小修正案の「記述」（差分は作らない。何をどう変えるかの説明のみ）
3. その原因で上記の症状すべてが説明できるかどうか

# 最重要
**原因が一意に確定できない場合は「確定できない」と明記して報告すること。**
それらしい推測を確定として返さないこと。確定できない場合は、
「どの値を実行時に観測すれば一意に絞れるか」を、観測すべき変数名と場所つきで挙げること。
~~~

「確定できない」と返ってきたら、それは失敗ではなく正しい応答です。次は診断ログを入れて実測する段階に進みます。

## 3. 修正プロンプト（本命）

~~~text
# タスク
Rojo プロジェクトのサーバー側当たり判定バグを修正する。

# baseline
リポジトリ: 《repo path》
commit: 《baseline commit hash》
着手前に `git rev-parse HEAD` と `git status --short` を実行し、実出力を報告に含めること。
clean でなければ、何も変更せずに停止して報告すること。

# 症状（実測値のみ）
- 《実測ログの実値をそのまま貼る》
- 再現手順: 《手順》 / 再現率: 《n / m 回》

# 根本原因（確定済み）
- 《file:line》: 《何がどう誤っているか》

# inScope（ここだけ直す）
- 《src/ServerScriptService/《Module》.lua の 《関数名》》

# outOfScope / 凍結（触れてはならない）
- 上記以外のすべてのファイル
- 《default.project.json / rojo 設定 / aftman.toml / wally.toml など》
- 《ビルド生成物（*.rbxlx / *.rbxl）》
- 《テスト定義・データ定義ドキュメント》

# 禁止条項（すべて必須。1つでも破ったら成果物は不採用とする）
1. ゲームプレイ数値の新規創作を禁止する。ダメージ・判定半径・クールダウン・許容誤差
   などの数値は、既存のデータ定義の ID 参照または承認済みの値のみを使う。
   既存値の変更も禁止。値を足す必要が生じたら、実装せずに停止して報告すること。
2. **行頭が開き括弧になる型キャストへの代入を禁止する。**
   NG: (someValue :: SomeType).Property = x
   OK: local casted = someValue :: SomeType
       casted.Property = x
   これは Luau の曖昧構文で、モジュールが丸ごと読み込めなくなる。ビルドは通ってしまう。
3. **ファイルの新規作成・削除・改名・移動を禁止する。拡張子を変更してはならない。**
   Rojo は拡張子でインスタンス種別を決める（.lua = ModuleScript /
   .server.lua = Script / .client.lua = LocalScript）。
   「サーバー側の処理だから」と .lua を .server.lua に付け替えると、
   ModuleScript が Script に変わり、require している側が全滅する。
4. **`require` の記述を書き換えないこと。循環する参照を足さないこと。
   モジュール末尾の return を消したり、条件分岐の内側へ移動したりしないこと。**
   これらはいずれもビルドが成功したまま、読み込み時にだけ壊れる。
5. 状態遷移表・guard の構造そのものは変更しない。
   （判定に使った値を出す診断ログの追加は可。構造変更は不可。）
6. ビルド設定・ツールチェーンの pin・ビルド生成物を編集しない。
7. **実施していない検証を「実施した」と書かない。**
   「実機で確認」「Studio で動作確認」等の検証語彙を、自己レビューや静的確認の
   名称として流用しないこと。
8. **sha256 は実際に計測した値のみ報告する。**

# 受け入れ条件
1. 上記症状が、根本原因の修正によって解消される見込みを、変更箇所ごとに1行で説明できること。
2. **当たり判定の観測ログを追加すること。** 形式は `key=value` の1行ログ。最低限:
   - 判定の入力: `hit_eval attacker=《id》 target=《id》 dist=《実値》 radius=《実値》 dt=《実値》`
   - 受理: `hit accepted attacker=... target=... damage=《実値》`
   - **棄却: `hit rejected attacker=... target=... reason=《理由コード》 value=《判定に使った実値》`**
   棄却は理由コードと**判定に実際に使った値そのもの**を必ず出すこと。
   「範囲外と判定した」だけのログは切り分けに使えない。「判定に使った距離と半径」を出す。
3. 決定論ビルドを2回実行し、生成物の sha256 が一致することを実測して報告すること。
   （コマンドと2回分の sha256 実値を貼ること）

# あなたがやらないこと
- **実機検証（Roblox Studio での Play）は行わない。**
  サンドボックスから Studio には触れない。実機検証は依頼側が行う。
  よって「動作確認済み」とは書かないこと。

# 報告フォーマット
1. `git rev-parse HEAD`（着手前）の実出力
2. `git status --short` の実出力
3. 変更ファイル一覧と、各ファイルの変更理由を1行ずつ
4. 根本原因の `file:line` と、修正内容
5. ビルド2回分の sha256 実値
6. 禁止条項1〜8それぞれについて、遵守したことの自己申告（該当なしはその旨）
7. 判断がつかず実装しなかった箇所があれば、その一覧

# 迷ったとき
範囲外に手を出す必要が生じたら、**広げずに停止して報告すること。**
判断がつかない場合も同様に停止すること。推測で進めないこと。
~~~

## 4. 投げたあと、こちらで確認すること

前提として一つ。**実装は委譲してよいが、検証は委譲しないでください。** 実装側の報告は要約であって証拠ではありません（実施していない検証を「実施した」と報告された例が複数あります）。訂正を求めるやり取りは費用に見合わないので、報告は参考にとどめて、検証は自分のツール実行で行うのが結局いちばん安く済みます。

### 4.1 走っている間 — ハングの判定（完了通知では捕まらない）

止まったプロセスは通知を出しません。「まだ動いている」と見分けがつかないので、**数分あけて 2 回**、次の 2 つを採ります。

- ログファイルのバイト長: `(Get-Item 《logfile》).Length`
- プロセスの累積 CPU 時間: `(Get-Process -Id 《pid》).TotalProcessorTime`

| ログ長 | CPU 時間 | 判定 |
|---|---|---|
| 伸びている | — | 正常。待つ |
| 平ら | 増えている | 考えている。待つ |
| **平ら** | **平ら** | **ハング。停止し、標準入力を閉じて投げ直す** |

確証が要るなら 1 回だけ前面で実行して、入力待ちを示す行が出るかを見ます。なお `< /dev/null` を付けていれば、この判定に引っかかる頻度自体がほぼ無くなります。

### 4.2 受け取った直後 — 自分の手で回す 5 点

1. **`git status --short` を自分でも実行し、報告と突き合わせる。** 一覧に無いファイルが変わっていたら範囲違反です。
2. **差分の中身を自分の目で読む。** 特に見るのは禁止条項の 2〜4 に触れる形:
   - 行頭 `(` のキャスト代入（`^\s*\(` で検索するとまとめて出ます。1 回の委譲で 13 箇所出たことがあります）
   - ファイルの新規作成・改名・**拡張子の変化**（`.lua` → `.server.lua` など）
   - `require` 行の変更、モジュール末尾の `return` の消失・移動
   - 承認していない数値リテラルの出現
3. **決定論ビルドの 3 回目を自分で回し、sha256 が報告値と一致することを確認する。**
4. **ビルドが通ったことを、コードが読み込めることと読み違えない。** Rojo は Luau をパースしません。ファイルをインスタンスへ変換するだけなので、**モジュールを壊す構文が入っていてもビルドは成功し、sha も決定論的に一致します。** この関門が保証するのは梱包の再現性だけです。
5. **実機で通しを回す前に、モジュールの読み込みだけを安価に舐める。** Studio でサーバー文脈からこれを流します。

   ```lua
   -- サーバー文脈で読めるべき場所だけを舐め、失敗したものだけ列挙する
   local roots = {
       game:GetService("ServerScriptService"),
       game:GetService("ServerStorage"),
       game:GetService("ReplicatedStorage"),
   }
   local failed = {}
   for _, root in roots do
       for _, d in root:GetDescendants() do
           if d:IsA("ModuleScript") then
               local ok, err = pcall(require, d)
               if not ok then table.insert(failed, d:GetFullName() .. " -> " .. tostring(err)) end
           end
       end
   end
   return if #failed == 0 then "all modules loaded" else table.concat(failed, "\n")
   ```

   注意が 2 つあります。**クライアント専用のコンテナを含めない**でください（サーバー文脈でクライアント専用モジュールを読むと、正常なコードが失敗して誤検知の山になります）。そして require は各モジュールの初期化を実際に走らせるので、**通しの検証を始める前**に済ませてください（検証対象のセッション状態が汚れます）。

   エラー文言と原因はおおむね対応します。

   | 文言の形 | 原因 |
   |---|---|
   | 読み込み中にエラーが発生した | 循環参照、または読み込み時の例外 |
   | ちょうど 1 つの値を返さなかった | 末尾の return が消えた／分岐の中へ移動した |
   | 待機し続けている旨の警告 | 階層の前提が崩れた（配置換え・改名） |
   | スクリプトを呼び出そうとした | 拡張子が変わってインスタンス種別が変わった |

   ご相談の「モジュールが読み込めなくなる書き方」は、**ここで必ず捕まります**。プロンプト側の禁止条項が予防、この sweep が検出、の二段構えです。

### 4.3 実機検証（これだけは委譲できない）

当たり判定は静的検査では原理的に見えない欠陥が出る領域なので、修正後は Studio で実際に接触させて、**サーバーの構造化ログの実値**を読みます。画面キャプチャは「何かおかしい」までしか言えませんが、`hit rejected attacker=-1 target=-2 reason=out_of_range dist=3.2 radius=5.0` のような 1 行は、どの判定がどの値で成立/不成立したかを一意に決めます。

確認する形:

- 受理と棄却の**両方**が出ていること（片方しか出ないログは切り分けに使えません）
- 棄却の `reason` と `value` が、期待どおりの値で出ていること
- **「無かったこと」も数えて記録する。** エラー 0 件・棄却 0 件は、**数えたなら証拠**、見ていないなら何でもありません。件数として書き残してください
- 単発ではなく、試合の 1 サイクル（開始 → 接触 → 決着 → 終了 → 次試合）を通すこと

### 4.4 契約違反だったとき — 新規 handoff ではなく「差し戻し」

やり直しは、新しい handoff を書くより**同じ契約の差し戻し**として出すほうが安く、範囲がずれません。差し戻しに必ず入れるもの:

- 検出した違反を具体的に（どのファイルのどの行が、どの条項に触れたか）
- **違反部分だけを戻す指示。** 正しく直っている部分まで巻き戻させない
- **範囲を狭め直す。** 違反が出たということは、範囲指定が緩かった可能性があります
- **元の禁止条項はすべて有効なままだと明記する。** 差し戻し便で条項が失効したと解釈されると、2 回目で別の違反が出ます
- 判断がつかないなら広げずに止まれ

**2 回目で範囲が静かに広がるのが典型的な失敗**なので、そこを名指しで塞いでください。

### 4.5 止まる条件を先に決めておく

診断 → 修正 → 再実測を **2 巡**回して実測値が動かないなら、コードをいじるのをやめます。無人で回しているとき、この歯止めが無いと 1 つの症状で一日溶けます。先へ進む道は 3 つで、決める人が違います。

- **(a) 当該挙動を範囲から外す** — 所有者（あなた）の判断
- **(b) 既知の欠陥として受け入れ、実測値つきで「言えないこと」に載せる** — 実行側で決めてよい
- **(c) その箇所だけ止めて、依存しない作業を先に進める** — 実行側で決めてよい

いずれの場合も、症状は**実測値のまま**残します。推測で言い換えないでください。

## 5. 当たり判定で特に踏みやすい、実測済みの罠

「コードは何度読んでも正しいのに、環境でだけ壊れる」型です。修正後も直らないときは、実装欠陥と決めつける前にここを疑ってください。

- **ローカルテストのプレイヤー識別子が負数**（-1, -2, -3…）。本番は正数なので、`userId > 0` を前提にした入力検証が **Studio テストでだけ全滅**します。当たり判定は攻撃者・被弾者の識別子検証を必ず通るので、直撃します。対処は「有限な非ゼロ整数」で表現し、符号に意味を持たせないこと。テスト専用の分岐で回避すると、テスト経路と本番経路が別物になって検証の意味が薄れます。
- **リモート通信が数値キー辞書のキーを文字列へ変換する。** `{[-1] = 0}` が受信側で `{["-1"] = 0}` になります。ヒット結果を `{[userId] = damage}` の形で送っていると、受信側でだけ検証が落ちて、**エラーも出ずに黙って捨てられます。** これは本番でも起きます。新規に設計するなら `{ {id = ..., value = ...}, ... }` の配列にすれば影響を受けません。
- **閾値スナップが加速を殺す型。** 「一定値未満は 0 に丸める」を毎ステップ無条件に適用すると、1 ステップの増分が閾値未満のとき永久に発進できません。移動が絡む当たり判定（相対速度・ノックバック）で同じ形が再発します。値ではなく**関係**（毎ステップの丸め vs ステップあたりの増分）で確認してください。
- **症状を数えて原因を数えない。** 1 つの根本原因が、無関係に見える複数の症状を同時に出します。1 つ直して片方が消えたら、**もう片方も再実測してから**追加修正を判断してください。実例として、「FSM のバグ」に見えた症状の真因が別レイヤの数値制約で、そちらを直したら両方同時に消えました。

そしてもう一つ。**観測経路そのものを先に確認してください。** 「エラーが 1 件も出ない」は、出ていないのか、**出ている場所を見ていない**のか区別がつきません。Roblox のマルチクライアントセッションでは、クライアント側の出力は各クライアントのウィンドウに出て、サーバーのコンソールには現れません。まず無条件に 1 行出力する仕掛けを入れ、それが自分に見えることを確かめる。**ここが通らないうちは、以降の観測結果はすべて無効です。**
