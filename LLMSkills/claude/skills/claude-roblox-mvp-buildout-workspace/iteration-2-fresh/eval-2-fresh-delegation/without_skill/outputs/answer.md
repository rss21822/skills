# Codex CLI 向け 実装依頼テンプレート（Roblox / Luau / Rojo・サーバー側当たり判定バグ修正）

前回の失敗（① バックグラウンドで何時間も無進捗、② モジュールが読み込めなくなる書き換え）は、どちらも **指示文の側で構造的に潰せます**。

- ① は「Codex が終わらないコマンドを起動した」か「承認待ちで止まった」のどちらかがほぼ全てです。→ 常駐コマンドの禁止 + 非対話実行 + 打ち切り条件を指示文に明記。
- ② は Rojo プロジェクトで `require` のパス、ファイル名規約、`default.project.json`、ModuleScript の `return` のいずれかを触られたのが原因です。→ 「触ってはいけない構造」を列挙して禁止。

以下、**(1) そのまま渡す指示文**、**(2) 起動コマンドと運用**、**(3) 投げた後の確認手順** の順です。

---

## 0. 渡す前に自分で埋める欄

指示文の【】は必ず埋めてください。ここが空だと Codex は探索に時間を溶かします（＝ハングに見える無進捗の主因のひとつ）。

| 欄 | 何を書くか | 例 |
|---|---|---|
| 【症状】 | 観測した事実だけ。原因の推測は分けて書く | 「至近距離で攻撃しても Humanoid.Health が減らないことが 3 回に 1 回ある」 |
| 【再現手順】 | Studio でその通りやれば再現する手順 | 「Play Solo → 敵 Dummy に正面 3 stud で近づく → 左クリック」 |
| 【期待動作】 | 1 行 | 「1 回の攻撃で Health が 10 減る。連打しても 0.5 秒に 1 回まで」 |
| 【対象ファイル】 | 分かっている範囲で列挙。分からなければ「ServerScriptService 配下の Combat 系」等の範囲指定 | `src/server/Combat/HitService.server.lua` |
| 【触ってはいけない領域】 | 進行中の作業があれば | 「src/client/UI/ は別作業中につき変更禁止」 |
| 【再現の確度】 | 100% 再現 / 間欠 | 「間欠。10 回中 3 回」 |

「間欠」の場合はそう書いてください。100% 再現だと誤って伝えると、Codex は再現しない現象を追って延々ループします。

## 1. そのまま Codex CLI に渡す指示文

以下をコピーして、【】を埋めて使ってください。

````text
# 役割
あなたは Roblox / Luau / Rojo プロジェクトの実装担当です。以下のバグ 1 件のみを、最小の差分で修正してください。

# 対象バグ
- 症状: 【症状】
- 再現手順: 【再現手順】
- 期待動作: 【期待動作】
- 再現の確度: 【100%再現 / 間欠（10回中N回）】
- 当たり判定はサーバー側で行われている（クライアント側の見た目の問題ではない）。

# 調査の起点（ここから見ること。当てが外れたら範囲を広げてよい）
- 【対象ファイル】
- 関連しそうなサーバースクリプト / ModuleScript

# 実行に関する絶対ルール（違反したら作業を中断して報告）
1. 終了しないコマンドを起動しないこと。特に以下は禁止:
   `rojo serve`、`--watch` 系、`npm start` / `npm run dev`、`tail -f`、
   対話型 git（`git rebase -i`、`git add -i`）、ページャを開くコマンド
   （git を使うときは必ず `git --no-pager ...`）、REPL、Roblox Studio の起動。
2. 実行するコマンドは 60 秒以内に終わるものだけ。60 秒を超えたら中断し、
   何を実行して何秒で打ち切ったかを報告に書くこと。
3. 人間の承認や追加情報を待って停止しないこと。判断に迷ったら
   「最も既存コードの流儀に沿う選択肢」を仮定として採用して進み、
   採用した仮定を最後にまとめて列挙すること。質問だけして止まるのは失敗扱い。
4. 探索は最大 30 ファイルまで。読んでも原因が特定できない場合は、
   その時点で「絞り込めた範囲」と「次に見るべき箇所」を報告して終了すること。
   憶測で広範囲を書き換えないこと。
5. 変更してよいファイルは最大 3 ファイル。それを超える必要があると判断したら、
   実装せずに理由と計画だけを報告して終了すること。
6. `git commit` / `git push` / `git checkout` / `git stash` / `git reset` を実行しないこと。
   変更は作業ツリーに残すだけにすること。
7. 依存パッケージの追加・更新（wally.toml / package.json 等）をしないこと。
8. フォーマッタ・リンタの一括適用をしないこと（stylua や selene を全体に走らせない）。
   無関係な行の空白・改行・並び替えを差分に混ぜないこと。

# モジュール構造に関する絶対ルール（これを壊すと Studio で require が失敗する）
9. `default.project.json`（および他の *.project.json）を変更しないこと。
10. ファイルの新規作成・削除・リネーム・移動をしないこと。
    どうしても新規ファイルが必要なら、作らずに提案だけ書いて終了すること。
11. ファイル名の拡張子規約を変えないこと。
    `*.server.lua(u)` = Script、`*.client.lua(u)` = LocalScript、`*.lua(u)` = ModuleScript、
    `init.lua(u)` = そのフォルダ自身。ModuleScript を Script にする／その逆をしない。
12. ModuleScript は必ず単一の値を `return` して終わること。
    末尾の `return` 文を削除・移動・条件分岐の内側へ入れないこと。
13. 既存の `require` の書き方を一切変更しないこと（相対 `script.Parent...` を
    サービス起点に書き換える、`WaitForChild` を付ける／外す、等を含む）。
    新たに require が必要な場合は、同じディレクトリの既存ファイルで
    最も多く使われている書き方をそのまま真似ること。
14. 新たな循環 require を作らないこと（A が B を、B が A を require する形）。
15. 既存ファイルに `--!strict` を新規に付けないこと。
16. トップレベルでの無条件 `WaitForChild`（タイムアウト無し）を新規に追加しないこと。
    Studio で "Infinite yield possible" となり、そのスクリプトが永久に起動しなくなる。

# 修正方針
- 原因を特定してから直すこと。症状を隠すだけの対症療法（判定を緩める、
  ヒット数を水増しする、クライアントの申告値を信じる等）は不可。
- 当たり判定バグでよくある原因。まずここを確認すること:
  - Touched の多重発火／デバウンス欠落、またはデバウンスが対象ごとでなく
    グローバル 1 個になっている
  - OverlapParams / RaycastParams の FilterType の取り違え
    （Exclude と Include の逆）、FilterDescendantsInstances の設定漏れ・
    設定後に再代入していない
  - Raycast の direction に単位ベクトルを渡していて距離が 1 stud しか出ていない
    （direction は「向き × 距離」のベクトル）
  - 判定対象パーツの CanQuery / CanTouch / CanCollide が false で
    空間クエリに引っかからない
  - CollisionGroup の設定で当たらない
  - HumanoidRootPart のみを見て他パーツを取りこぼす、または逆に
    1 キャラの複数パーツにヒットして多重ダメージになる
  - Humanoid.Health <= 0 の対象や、同一攻撃で既にヒット済みの対象への再ヒット
  - キャラクター／パーツが Workspace に親子付けされる前にイベント接続している
  - ループ内で毎回イベント接続を張り直して接続が累積している
  - 攻撃者自身・味方への自傷判定
- 既存のコードスタイル（命名、インデント、エラー処理の流儀）に合わせること。

# 完了前に必ず実行して結果を報告すること
A. `rojo build default.project.json --output <一時ディレクトリ>/verify.rbxlx`
   （プロジェクトファイル名が異なる場合はリポジトリ内の実ファイル名に合わせる）
   - 修正**前**と修正**後**の両方で実行する。
   - 修正前から失敗する場合は環境側の問題として即報告し、実装を止めること。
   - 修正後に失敗した場合は、成功するまで直すか、直せないなら報告して終了。
B. 変更した各ファイルの構文チェック。
   `luau-lsp analyze` / `selene` / `stylua --check` のうち **既に導入済みのものだけ**
   を、**変更したファイルのみ** に対して実行する。導入されていなければ実行せず、
   「未導入のためスキップ」と報告に書くこと（新規インストールはしない）。
C. `git --no-pager diff --stat` と `git --no-pager status --short`

# 報告フォーマット（この見出しで、この順に）
1. 根本原因: ファイル名:行番号 と、なぜそれで当たり判定が壊れるかの説明（3 行以内）
2. 修正内容: 変更ファイルごとに 1 行説明
3. 実行したコマンドと結果: コマンドと、成否および末尾数行の出力
4. 置いた仮定: 確認せず前提にしたこと（無ければ「なし」）
5. 人間が Studio で確認すべき手順: 具体的な操作と、見るべき Output の文字列
6. `git --no-pager diff --stat` の出力
7. 積み残し / 直せなかったこと（無ければ「なし」）
````

### この指示文で効いている箇所

| 前回の問題 | 効く条項 |
|---|---|
| 何時間も無進捗 | ルール 1（常駐コマンド禁止／`rojo serve` が最大の地雷）、2（60 秒打ち切り）、3（承認待ちで止まらない）、4・5（探索・変更の上限＝打ち切り条件） |
| モジュールが読めなくなる | ルール 9〜16（project.json 固定、ファイル移動禁止、拡張子規約、`return` 保護、`require` 書き換え禁止、循環参照禁止、Infinite yield 防止） |
| 直ったか分からない | 完了前チェック A（rojo build が通ることの機械的証明）、報告フォーマット 5（自分の確認手順が返ってくる） |

## 2. 起動コマンドと運用（ハングを「起きても 15 分で気付く」形にする）

### 基本方針

- **バックグラウンドで投げない。** 前景で走らせて、画面に出力が流れているのを見る。
- **非対話モード（`codex exec` 相当）で走らせる。** 対話モードだと承認プロンプトで無言停止し、それが「何時間も止まっていた」の正体になりがち。
- **ログをファイルに落とす。** 後追いで「どのコマンドで止まったか」を特定できる。

PowerShell での例（フラグ名は手元の `codex --help` で確認してから使ってください。バージョンで変わります）:

```powershell
# 指示文を先にファイルにしておく（長文をシェルに直書きしない）
$prompt = Get-Content -Raw .\codex-task.md

# 前景・非対話・ログ保存
codex exec --model gpt-5.6 $prompt 2>&1 | Tee-Object -FilePath .\codex-run.log
```

確認しておくとよいオプション（存在すれば使う）:

- サンドボックス / 承認モード（`--sandbox workspace-write`、`--ask-for-approval never`、`--full-auto` 等）
  → 承認待ちで止まらないようにする。ただし書き込み範囲はリポジトリ内に限定すること。
- 作業ディレクトリ指定（`-C` / `--cd`）
- モデルと reasoning effort の指定

### 走らせている間の見張り方

1. 開始時刻をメモ。
2. **15 分、出力に新しい行が増えなければ異常**とみなす。当たり判定バグ 1 件なら通常はそれより早く動きが出ます。
3. 異常なら Ctrl+C で落とし、`codex-run.log` の末尾を見て「最後に実行したコマンド」を確認。`rojo serve` や watch 系が出ていたら、指示文のルール 1 に該当コマンドを追記して再投入。
4. どうしてもバックグラウンドで走らせたい場合だけ、必ず (a) ログファイル出力、(b) タイマーをかけて 20 分後に自分で見にいく、をセットにする。

### 事故ったときの巻き戻し

投げる前に必ず作業ツリーをきれいにしておく（`git status` が clean）。そうすれば失敗時に

```powershell
git --no-pager diff              # まず何をされたか見る
git checkout -- .                # 全部捨てる
```

で 1 コマンドで戻せます。ここが汚れていると、Codex の変更と自分の変更が混ざって切り分け不能になります。

## 3. 投げた後にこちらで確認すること

上から順に。**A → B が通ってから Studio を開く**のが時間の節約になります。

### A. 差分が約束どおりか（5 分・Studio 不要）

```powershell
git --no-pager status --short          # ?? (新規) や D (削除) が無いこと
git --no-pager diff --stat             # 変更が 3 ファイル以内、想定の場所か
git --no-pager diff -- *.project.json  # 空であること（空でなければ差し戻し）
```

さらに、モジュール破壊の兆候を差分から先に拾います。

```powershell
git --no-pager diff -U0 | Select-String -Pattern "require|^\-.*return|WaitForChild|--!strict"
```

ここで以下が出てきたら、Studio で開く前に差し戻し判断:

- `require(...)` の行が **書き換えられている**（新規追加ならまだ可、既存行の変更は赤信号）
- `- return SomeModule` のように **`return` 行が削除されている**（ModuleScript が壊れる典型）
- 新規の `:WaitForChild("X")` がトップレベルに追加されている（第 2 引数のタイムアウト無し）
- `--!strict` が新規に付いている

### B. ビルドが通るか（2 分）

```powershell
rojo build default.project.json --output .\build\verify.rbxlx
```

- 成功 = 少なくとも「Rojo のツリー定義とファイル配置の整合」は壊れていない。
- ここで落ちるなら Studio を開く必要はありません。エラー文をそのまま Codex に返す。

### C. Studio で読み込み事故の確認（当たり判定を試す前にここ）

1. Output ウィンドウを開き、**フィルタを空にして**（既定でフィルタが残っていると赤字を見逃します）Play。
2. 次の文字列を検索。1 つでも出たらモジュール破壊です。
   - `Requested module experienced an error while loading` — require 先が実行時エラー
   - `Module code did not return exactly one value` — ModuleScript の `return` が壊れている
   - `is not a valid member of` — 参照パスがツリーと合っていない
   - `Infinite yield possible on 'X:WaitForChild("Y")'` — **警告（黄色）なので見逃しやすい**。これが出ているスクリプトは以降 1 行も動いていません。当たり判定が「何も起きない」形で壊れるときの最頻パターン。
   - `attempt to index nil with` — 上記のいずれかの二次被害
3. Output 右上のコンテキスト切り替えで **Server 側のログも見る**。クライアント側だけ見て「エラー無し」と判断しないこと。
4. 「エラーは無いが何も起きない」場合、当該サーバースクリプトの先頭に `print("[HitService] loaded")` を一時的に入れて Play。出なければ require で死んでいます。

### D. バグ本体の検証（本番）

1. **投げる前に書いた再現手順を、そのまま実行**して期待動作になるか。
   - 「直ったはず」ではなく、修正前に Fail していた手順が Pass することを見る。
2. 境界ケース（当たり判定の修正はここで壊れます）:
   - 連打 — デバウンスが効いているか。1 回の攻撃で 2 回減っていないか
   - 同時に複数対象 — 全員に入るか、逆に 1 人にしか入らないか
   - 対象が移動中 / 落下中
   - 対象の HP が 0 になった直後にもう 1 発 — マイナスや多重死亡処理にならないか
   - リスポーン後 — キャラ再生成でイベント接続が外れていないか
   - 自分自身・味方に当たらないか
3. **サーバー権威であることの確認**: 判定コードが ServerScriptService（サーバー側）にあること、クライアントから送られた座標やダメージ量をそのまま信用していないこと。差分で `RemoteEvent` の受け口が増えていたら中身を必ず読む。
4. 可能なら **2 プレイヤー**（Test → Clients and Servers、2 players）で確認。当たり判定バグは 1 人 Play では出ないものが多い。

### E. 回帰（10 分）

当たり判定以外の主要フローを 1 周（試合開始 → 進行 → 終了 → 結果表示）。とくに「同じ ModuleScript を require している別機能」が生きているか。差分に出た ModuleScript を誰が require しているかは、エディタの全文検索で `require(...ModuleName` を引けば分かります。

### F. 合格しなかったときの差し戻し文例

そのまま Codex に返せる形:

```text
Studio で確認したところ、まだ通っていません。

- 実行した手順: 【手順】
- 期待: 【期待】
- 実際: 【実際に起きたこと】
- Output に出たメッセージ（全文）: 【貼り付け】
- rojo build: 成功 / 失敗（失敗なら出力を貼る）

前回と同じ制約（常駐コマンド禁止・60秒打ち切り・project.json 変更禁止・
ファイル新規作成/移動/リネーム禁止・既存 require の書き換え禁止・変更 3 ファイル以内）を
維持したまま、原因を再特定してください。
前回の修正が的外れだった場合は、まず前回の変更を元に戻す差分を提示してから直してください。
```

## 4. 補足：次回以降ラクにするために

- この指示文の「実行に関する絶対ルール」「モジュール構造に関する絶対ルール」の 2 ブロックは、当たり判定に限らず **この Rojo プロジェクトへの実装依頼すべてで使い回せます**。`AGENTS.md`（Codex が自動で読む規約ファイル）に置いておくと、毎回貼らずに済みます。
- 逆に「対象バグ」「調査の起点」「完了前チェック」は依頼ごとに書き換える部分です。
- 依頼は 1 回 1 バグに割ること。複数まとめると、探索範囲が広がって無進捗時間が伸び、差分も切り分け不能になります。
