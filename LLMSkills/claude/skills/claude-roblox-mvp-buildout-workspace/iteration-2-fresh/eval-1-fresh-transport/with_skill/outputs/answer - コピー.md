# サーバーは送っているのに HUD が更新されない — 切り分け手順

先に結論だけ言うと、**この症状の形（送信成功・受信ゼロ反映・エラーも警告もゼロ・プレイヤーIDキーの辞書）は、実測で 2 つの原因に強く偏る**。

1. **観測経路そのものが間違っている** — クライアント側の出力（print も警告もエラーも）は**クライアントのウィンドウのコンソールに出る**。サーバーのコンソールには一切現れない。「エラーが出ていない」が「エラーを見ていない」である可能性が最初に潰すべき対象。
2. **リモート直列化が、数値キー辞書のキーを文字列へ変換する** — `{[-1]=..., [-2]=...}` で送ったものが受信側では `{["-1"]=..., ["-2"]=...}` になる。送信側と共有した検証関数を受信側でも使っていると、**受信側でだけ検証に落ちて、payload ごと黙って捨てられる**。例外は出ない。

ただし **当て推量で直さないでください**。この2つは有力なだけで、まだ命題として検証されていません。以下の順序を守ると、だいたい実測 2 回で原因が一意に決まります。順序を飛ばして「たぶんこれ」で直すと、正しい箇所を壊して症状が増えます（実測でよくある）。

---

## Step 0. 観測経路を先に確認する（ここが通るまで、以降の観測結果はすべて無効）

「エラーも警告も一切出ない」は、**出ていない**のか**出ている場所を見ていない**のか区別がつきません。Roblox のサーバー＋クライアント構成では、出力の宛先はプロセスごとに別です。

やること: **無条件に 1 行出力する仕掛けを、HUD 更新スクリプトの一番上に入れる。**

```lua
-- HUD の LocalScript の先頭（どんな条件分岐よりも前）
print("[HUD] script alive", os.clock())
```

- この行が**クライアントのコンソール**に出るか確認する。出ないなら、**受信の問題ではなくスクリプトが走っていない**。LocalScript の置き場所（`StarterPlayerScripts` / `StarterGui` 配下の ScreenGui 内 / `StarterCharacterScripts` 以外では走らない）を最初に疑う。
- `WaitForChild` の「Infinite yield possible」警告も、**クライアント側にしか出ません**。サーバーのコンソールしか見ていなければ、リモートが永久に見つかっていなくても「警告なし」に見えます。

ついでに、**サーバー側の「送信成功」ログが何を証明しているか**を確認してください。それは「送信関数の呼び出しが例外を出さずに戻った」だけで、**到達も、直列化後の形も、受信側での受理も証明していません**。到達保証のないリモート（UnreliableRemoteEvent）なら、パケットは通知なく落ちます。

---

## Step 1. 「確認済み」を命題へ分解する

いま「サーバー側 phase が Racing なのは確認済み」と書かれていますが、これは次の 5 つのうち **1 つしか検証していません**。

| # | 命題 | 現状 |
|---|---|---|
| 1 | サーバー内部の状態変数が `Racing` | **検証済み** |
| 2 | 実際に送信した payload の該当フィールドが `Racing` | 未検証 |
| 3 | クライアントが受け取った payload の該当フィールドが `Racing`（値も**型も**） | 未検証 |
| 4 | 受信ハンドラがそもそも 1 回でも呼ばれた | 未検証 |
| 5 | 書き込んだ TextLabel が、**画面に出ている個体**である | 未検証 |

2〜5 のどこで落ちているかで、直す場所がまったく別になります。ここを分解しないまま実装側（Codex 等）に投げると、**その推測を前提に「修正」されて別の欠陥が入ります**。

## Step 2. 実測 1 発で二分する（走っているセッションのまま、再ビルド不要）

Studio MCP の Luau 実行（`datamodel_type: Client`）か、届かない場合は対象クライアントのコマンドバーに 1 行で投入して、**検証層を通す前の生データを型ごと**見ます。

```lua
local Players = game:GetService("Players")
local remote = game:GetService("ReplicatedStorage"):FindFirstChild("<スナップショットのRemote名>", true)
if not remote then return "remote not found on client (経路の問題: 複製されない場所にある)" end

local got, n = nil, 0
local conn = remote.OnClientEvent:Connect(function(payload)
    n += 1
    if got == nil then got = payload end
end)
task.wait(1.5)   -- 20Hz なら 30 発来るはず
conn:Disconnect()

if got == nil then
    return ("recv=0 path=%s local=%s"):format(remote:GetFullName(), Players.LocalPlayer.Name)
end

local out = {
    ("recv=%d in 1.5s"):format(n),
    ("phase=%s phaseType=%s"):format(tostring(got.phase), typeof(got.phase)),
    ("localUserId=%d"):format(Players.LocalPlayer.UserId),
    ("remotePath=%s"):format(remote:GetFullName()),
}
for k, v in pairs(got.<ラップタイム辞書のフィールド名> or {}) do
    table.insert(out, ("key=%s keyType=%s valType=%s"):format(tostring(k), typeof(k), typeof(v)))
end
return table.concat(out, "\n")
```

**必ず `typeof(key)` を出すこと。** 値だけ見ると正常に見えて、キーの型が変わっているのが原因、というのがこの症状の典型です。

読み方:

| 実測結果 | 判定 | 次に見る場所 |
|---|---|---|
| `recv=0` | **経路の問題**（payload の形は無関係） | 下の「経路系の候補」へ |
| `recv>0` かつ `keyType=string` | **transport の変換にぶつかっている** | 下の「キー文字列化」へ |
| `recv>0` かつ `phase` が `Racing` 以外 / 型が違う | 送信側の payload 組み立て or phase の表現不一致 | サーバーの送信直前の値を出す |
| `recv>0` かつ phase も キー型も正常 | **受信より後ろ**（ガード or 書き込み先） | 下の「受信後の無言失敗」へ |

補助として、**最小 payload テスト**も安価で強力です。`phase` という文字列 1 個だけを別リモートで 20Hz で送ってみる。届けば「payload の形の問題」、届かなければ「経路の問題」。これで確実に二分できます。

`localUserId` が **負数**で出たら、それも記録しておいてください（後述）。

## 有力候補 A: 通信層が数値キー辞書のキーを文字列へ変換する

**実測済みの事実**です。Roblox のリモート直列化は、**数値をキーに持つ辞書のキーを文字列へ変換します**。配列の添字と、テーブルの「値」は変換されません。

```
送信側: lapTimes = { [-1] = 31.4, [-2] = 33.8 }     -- キーは number
受信側: lapTimes = { ["-1"] = 31.4, ["-2"] = 33.8 } -- キーは string
```

これは**本番でも起きます**。テスト環境固有ではありません。

これが「一度も更新されない」に化ける経路は 2 通り:

- **クライアントが `lapTimes[player.UserId]`（number）で引く → 常に nil → 更新スキップ**
- **送信側と共有した検証関数が受信側で落ちる → payload 全体を黙って捨てる → phase も届かないので HUD が Racing 表示に切り替わらない**（phase が Racing なのは確認済み、という報告と矛盾しないのが厄介なところ）

### 直し方

受信側に **wire decode 層**を置き、**検証の前に**キーを数値へ復元します。

```lua
local function decodeNumericKeyMap(src)
    local out = {}
    for k, v in pairs(src) do
        local nk = if typeof(k) == "number" then k else tonumber(k)
        if nk == nil then return nil, "undecodable key: " .. tostring(k) end
        if out[nk] ~= nil then return nil, "key collision after decode: " .. tostring(nk) end
        out[nk] = v
    end
    return out
end
```

守るべき点:

- **復元できないキー・復元後に衝突するキーは、復元せずそのまま検証へ渡して落とす。** 検証を緩めるのではありません。これは *schema の緩和* ではなく *transport 変換の復元* です。この区別を仕様書に書き残さないと、後から「なぜ受信側だけ特別扱いなのか」が誰にも分からなくなります。
- **受信 payload を破壊しない。** 新しいテーブルへ詰め替える。

### 設計上の回避（新規設計ならこちらが安全）

そもそも数値キー辞書を payload に載せないでください。

```lua
-- 変換の影響を受けない形
standings = {
    { userId = -1, place = 1, lastLap = 31.4 },
    { userId = -2, place = 2, lastLap = 33.8 },
}
```

配列（1 始まり連番）とテーブルの値は変換されないので、この形なら transport の性質に依存しません。**キーを `tostring(userId)` に統一して両側で文字列として扱う**のも成立しますが、配列化のほうが後から要素を増やしやすいです。

あわせて: **配列部と辞書部が混在したテーブル**（`{[1]=a, name="x"}` のような形）は直列化で欠落します。payload のどのテーブルにも混在がないか確認してください。

## 有力候補 B: 識別子の符号（Studio ローカルテスト限定で全滅する）

Studio のローカルテストセッションが割り当てるプレイヤー識別子は**負数（-1, -2, -3, …）**です。本番は正数。したがって

```lua
assert(typeof(id) == "number" and id > 0)   -- テスト環境でだけ全滅する
```

のような検証が入っていると、**ローカルテストでのみ**全パケットが検証で落ちます。「サーバー側ログでは送信成功」「クライアントは無反応」の形にぴったり合います。

対処: 識別子の妥当性は「**有限な非ゼロ整数**」で表現し、符号に意味を持たせない。**テスト専用の分岐で回避しないこと**（テスト経路と本番経路が別物になり、検証の意味が薄れます）。

なお候補 A と B は**同時に成立していることがあります**。`tonumber("-1")` は通っても `> 0` で落ちる、という二段構えです。**症状を数えて原因を数えない**（逆も同様に、1 つ直して症状が 1 つ消えても、もう片方は再実測してから判断する）。

## `recv=0` だった場合: 経路系の候補

エラーを出さずに黙って何も起きない経路の一覧です。上から確認コストが安い順。

| 症状の形 | 起きていること | 見分け方 |
|---|---|---|
| ハンドラが一度も呼ばれない | LocalScript が**走らない場所**にある（`ReplicatedStorage` / `Workspace` 直下など） | Step 0 の無条件 print が出るか |
| 同上 | リモートの実体が**クライアントに複製されない場所**（`ServerStorage` / `ServerScriptService` 配下）にある | クライアントで実体を取得できるか。`WaitForChild` の待機警告（クライアント側に出る）が手がかり |
| 受信はするが別物を見ている | **同名のリモートが 2 つ**あり、送信側と受信側が別個体を掴んでいる | 生成時に固有の印を属性で打ち、両側で `GetFullName()` と属性を出して突き合わせる |
| 大きい payload だけ届かない | 到達保証のないリモートは 1 パケットの上限が小さい。**20Hz でプレイヤー全員分のラップタイム＋順位**は普通に超えうる | payload を最小にして再試験。分割するか保証付きへ切り替える |
| 例外が出ているはずなのに見えない | 更新経路が例外を握り潰す形で包まれている（`pcall` で戻り値を捨てている） | 握り潰し箇所で内容を出力する |

## `recv>0` なのに画面が変わらない場合: 受信後の無言失敗

| 症状の形 | 起きていること | 見分け方 |
|---|---|---|
| 更新は走るが画面が変わらない | 画面に出ている複製ではなく、**複製元のテンプレート側**（`StarterGui` 配下）へ書いている | 書き込み先で `label:GetFullName()` を出す。`StarterGui.…` なら別個体。正解は `Players.<name>.PlayerGui.…` |
| しばらく動いていたのに突然止まる | リスポーンで UI が破棄・再生成され（`ResetOnSpawn`）、保持していた参照が**死んだ個体**を指している。**破棄済みへの書き込みは例外を出さない** | 参照を毎回引き直すか `ResetOnSpawn` を切る |
| phase ガードで毎回抜けている | 比較対象の表現不一致（`"Racing"` と `"RACING"`、文字列と Enum/数値、ネスト位置の違い） | ガードの直前で「比較した2つの値と型」をそのまま出す。「Racing ではなかった」ではなく**比較に使った値そのもの**を出すこと |

HUD が実値を持っているかは、画面キャプチャより **GUI ツリーを歩いてテキストを読む**ほうが速く正確です。

```lua
local gui = game:GetService("Players").LocalPlayer.PlayerGui:FindFirstChild("<ScreenGui名>")
local out = {}
for _, c in gui:FindFirstChild("<Frame名>"):GetChildren() do
    if c:IsA("TextLabel") then table.insert(out, c.Name .. " = [" .. c.Text .. "]") end
end
return table.concat(out, "\n")
```

## 実測のコスト順序（ここを間違えると時間が溶ける）

1. **走っているセッションのまま読む**（Step 2 のスニペット、GUI ツリー読み）。**再ビルドが不要なので、これで取れるならこれで済ませる。**
2. **実行時に届かない値だけ、ソースへ診断ログを入れる。** 抑制なしで 1 行、**実際に判定に使った値そのもの**を出す。ただしこちらは安くありません: Studio 全終了 → 再ビルド → place 再オープン → サーバー起動 → クライアントを 1 台ずつ再追加 → 操作の再実行、が 1 行ごとに必要で、**しかも再ビルドで診断中のセッション状態は消えます**。入れるなら、次に要りそうな値をまとめて 1 回で入れてください。

診断ログの原則: `phase from=X to=Y guard=Z result=committed` / `recv seq=N keyType=string reject=key_type` のような **`key=value` 形式の 1 行**にする。とくに**棄却は理由コード付きで出す**。「受け付けなかった」だけのログは切り分けに使えません。これは後付けすると足すためだけに実機を回す羽目になるので、**受信・検証・状態遷移のログは実装の成果物として最初から要求する**のが正解です。

---

## 止める条件を先に決めておく

診断 → 修正 → 再実測を **2 巡**回して実測値が動かないなら、コードをいじるのをやめてください。歯止めがないと 1 つの症状で一日溶けます。先へ進む道は 3 つで、決める人が違います。

- (a) 当該挙動を MVP の範囲から外す — **所有者（あなた）の判断**。勝手に切らない
- (b) 既知の欠陥として受け入れ、引き渡しの「言えないこと」へ**実測値つきで**載せる
- (c) 当該 WP だけ止めて、依存しない WP を先に進める

いずれの場合も、症状は**実測値のまま**残す。「FSM が壊れている」ではなく「recv=30/1.5s, keyType=string, HUD text 未変化」と書く。推測で言い換えると、次に読む人（や実装を委譲した先）がその推測を前提に動きます。

---

## 直した後にやること

- **修正が、既に合格していた検証を無効にしていないか名指しで確認する。** 根本原因が 1 つで症状が複数のことがあるので、影響範囲は「直した箇所」より広い。関係しそうな出口条件は**議論ではなく再実測**する。
- **「無かったこと」も数えて記録する。** 「クライアント側エラー 0 件」「棄却 0 件」は、**数えたなら証拠**、見ていないなら何でもない。件数として書く。
- 実機検証の記録には**そのときのビルド sha** を併記する。検証後にビルド対象へ触れる commit を打ったら、その検証は無効になり再実行が要ります（「直してから測る」ではなく「測ったものを出す」）。
- 引き渡しには **この検証では言えないこと**を書く。典型的には、実端末のタッチ操作、実ネットワークの遅延と損失（ローカルサーバーは同一機なので未検証）、複数人が**同時に**操作したときの挙動（Studio のテストセッションでは前面のウィンドウにしか入力が届かないため、順に操作している限り同時性は未検証）。

---

## まとめ（実行順）

1. クライアントのコンソールを見ているか確認する（無条件 print 1 行）。**ここが通るまで他の観測は全部無効。**
2. 「確認済み」を 5 命題へ分解し、いま何が未検証かを書き出す。
3. 走行中のセッションのまま、`OnClientEvent` の生 payload を **`typeof(key)` 込みで**読む。
4. `recv=0` → 経路系 / `keyType=string` → transport 変換 / それ以外 → ガードと書き込み先、へ分岐。
5. 原因が一意に決まってから直す。決まらないなら「決まらない」と書いて、値を取りに行く。
