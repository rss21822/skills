# Roblox タワーディフェンス（3人協力）のマルチプレイ実機検証 — 進め方と完了条件

以下は手順書です。この回答を書いた時点では Studio の起動も入力注入も実行していません。数値・座標は実測が要る箇所を明示してあります。

---

## 0. 先に押さえる制約（知らずに始めると原因不明の無反応で半日溶ける）

この 4 つが、検証の設計そのものを規定します。

1. **MCP の合成キー入力は `UserInputService` / `ContextActionService` に届きません。** ゲームの操作系はこれらに載っているので、**MCP からキーを送ってもプレイヤー操作は一切再現できません**。実操作の再現には OS レベルの入力注入（SendInput 相当）が必要です。
2. **OS 入力は前面のウィンドウにしか届きません。** ここから「**3人を同時に操作することはできない**」が出ます。1台ずつ前面を取って順に操作します。
3. **クライアント側の Luau 実行（MCP）は構成依存**です。単独 Play なら届きますが、サーバー＋複数クライアントでは届かないことがあります。しかも届いても**どのクライアントに入るかは選べません**。「3人全員の HUD を確認した」と言うには別の手段（コマンドバー投入）が要ります。
4. **クライアントの出力はサーバーのコンソールに出ません。** サーバーコンソールだけ見て「エラーが出ていない」と判断すると、後でまるごと読み違えます。

役割分担はこう固定します。

| 目的 | 手段 |
|---|---|
| プレイヤー操作の再現 | **OS 入力注入**（`scripts/studio_input.ps1`） |
| セッション構築（サーバー＋3クライアント） | メニュー操作の自動化（`scripts/studio_session.ps1`） |
| 状態の読み取り・世界の問い合わせ | Studio MCP の Luau 実行（Server は常用可 / Client は構成依存） |
| ログの回収 | Studio MCP のコンソール取得＋ディスク上のログファイル |
| メニュー・ダイアログの位置確認 | 全画面捕捉（`scripts/studio_capture.ps1 -FullScreen`） |

合言葉は「**入力は OS、観測は MCP**」です。

## 1. 実機を触る前にやること（開始ゲート）

### 1-1. 疎通確認 4 点

**実装を積み上げてから実機が動かないと、どの部分が原因か切り分けられなくなります。** 先にここを通してください。

1. **MCP がインスタンスを列挙できるか** — インスタンス一覧ツール（`list_roblox_studios` 相当）を呼び、対象が出るまで 5 秒間隔で最大 7 回待つ。
2. **Luau 実行が返るか** — `return "ok"` を `datamodel_type: Server` に投げる。Client 側も試すが、**届かなくても異常ではない**（代替は §5）。どちらが使えるかをここで確定させる。
3. **OS 入力が届くか** — 無害なキーを送り、戻り値の `fg=True` を確認する。

```powershell
$S = "C:\Users\Administrator\.claude\skills\claude-roblox-mvp-buildout\scripts"
& "$S\studio_input.ps1" -ProcId <編集ウィンドウPID> -Actions "press:ESC:80"
```

`fg=False` や `WARN` 行が出たら、その実行は「操作した」と扱わないこと。リモートセッション経由などで入力デスクトップが切り離されていると SendInput は効きません。復旧は次の通り（**セッション ID を決め打ちしない**。他人のセッションをコンソールへ繋いでしまう危険があります）。

```powershell
query session
tscon <自分のセッションID> /dest:console
```

4. **自分の出力が自分に見えるか** — サーバーとクライアントの両方から無条件に 1 行出力させ、それぞれどこに出るかを確認する。**ここが通らないうちは、以降の観測結果はすべて無効です。**

MCP のツール名は接続構成で変わります（`mcp__Roblox_Studio__*` など）。実名をツール一覧で確認してから使ってください。使うのは概ね `list_roblox_studios` / `execute_luau` / `get_console_output` / `start_stop_play` の 4 つです。

### 1-2. ビルドの決定論を確認する

同一入力から 2 回ビルドして sha256 が一致することを確認します。一致しないなら生成に時刻や順序が混ざっており、**以後「同じビルドで検証した」という主張が一切成立しません**。

ただし注意点が 2 つあります。

- **ビルドが通ることは、コードが読み込めることを証明しません。** Rojo 系のビルダは Luau をパースせず、ファイルをインスタンスへ変換するだけです。モジュールを丸ごと壊す構文が入っていてもビルドは成功し、sha も決定論的に一致します。この関門が保証するのは**梱包の再現性だけ**です。
- したがって、**セッションを組んだ直後・通し検証を始める前に**、全モジュールを保護付きで読み込んで舐める安価な確認を挟みます（§3-5）。

### 1-3. ログが「実装の成果物」として存在するか確認する

**これが今回いちばん効きます。** 観測の主軸は画面ではなく**サーバーの構造化ログ**です。画面キャプチャは「何かおかしい」までしか言えませんが、`key=value` 形式の 1 行は、どの遷移がどの条件で成立したかを一意に決めます。

タワーディフェンス 3人協力なら、最低でもこの 4 種が要ります。

```
wave phase from=Idle to=Building wave=1 players=3
place tower player=P2 kind=arrow cell=(3,5) cost=50 balance=120->70 result=accepted
place tower player=P3 kind=arrow cell=(3,5) cost=50 balance=40 result=rejected reason=cell_occupied
wave cleared wave=1 spawned=12 killed=12 leaked=0 lives=20 elapsed=42.3
```

要点は 3 つ。

- **棄却の理由コードまで出させる。** 「受け付けなかった」だけのログは切り分けに使えません。
- **player 別に出させる。** 合計値だけ見ていると、1人だけ動いて残り2人が実質飾りでも気づけません。3人協力の検証では致命的です。
- **後から足さない。** 足すために実機セッションを組み直す羽目になります（再ビルド 1 回につき Studio 全終了 → 再ビルド → place 再オープン → サーバー起動 → クライアント 3 台の再追加 → 操作の再実行、が要ります）。

## 2. テストセッションを立てる（サーバー1 + クライアント3）

### 2-1. place を開く

```powershell
& "$S\studio_session.ps1" -Action Open -PlacePath <ビルド生成物の .rbxlx>
```

固定 sleep ではなくプロセス成立で待つ実装になっています。開いたら**必ず全画面捕捉でモーダルダイアログの有無を確認**してください。

```powershell
& "$S\studio_capture.ps1" -FullScreen -OutFile C:\temp\screen.png
```

前回 Studio をプロセス強制終了していると「自動復元」ダイアログが前面を塞ぎ、この状態ではキーもメニューも届きません。**ウィンドウ捕捉には写らないので全画面捕捉が要ります。** 「無視」（現行ファイルをそのまま開き復元ファイルを消さない非破壊の選択）を、全画面捕捉から読んだ座標で押します。ダイアログは主ウィンドウとは別のトップレベルウィンドウなので、ウィンドウ相対の `click:` では押せません。

```powershell
& "$S\studio_input.ps1" -ProcId <編集PID> -Actions "absclick:641:516"
```

### 2-2. サーバーを起動する

```powershell
& "$S\studio_session.ps1" -Action Start -EditPid <編集PID>
```

既定は F7 ですが、**版によってショートカット割り当てが違います**。効かないときに疑う順序は (a) ダイアログが前面、(b) 3Dビューポートにフォーカスが無い（ビューポート中央をクリックしてから送る）、(c) 入力デスクトップ。どれでもなければメニュー経路へ切り替えます。全画面捕捉でメニューを開いた状態を撮り、項目のウィンドウ相対座標を読んで渡します。

```powershell
& "$S\studio_session.ps1" -Action Start -EditPid <編集PID> `
  -StartMenuX .. -StartMenuY .. -StartItemX .. -StartItemY ..
```

**読んだ座標は証跡に残してください。** 次回からそのまま使えます。

### 2-3. クライアントを 3 台追加する

```powershell
& "$S\studio_session.ps1" -Action AddClients -ServerPid <サーバーPID> -Clients 3
```

- **1 台追加するごとに成立を待ちます。** 連続クリックすると取りこぼします。スクリプトは各ラウンドで他ウィンドウを最小化してから操作します（前面の奪い合いを避けるため）。
- 成立判定はウィンドウタイトルではなく**プロセス数**。タイトルは言語設定で変わります。今回の目標は `1(編集) + 1(サーバー) + 3(クライアント) = 5`。
- メニュー座標は環境で変わります。既定値は日本語 UI・1280x720 相当での実測例（テストタブ ≈ (246,43)、クライアント追加 ≈ (290,290)、いずれもウィンドウ相対）なので、**初回は全画面捕捉で実位置を読んでから**使ってください。
- 1 台の起動に数十秒かかることがあります。固定 sleep で待たないこと。

### 2-4. 参加を確認する

**プロセスが立っていることと、ゲームに参加していることは別です。** サーバーコンソールで `players=3` を実測してください。参加時に人数と識別子を 1 行出すログがあると一目で分かります。

### 2-5. プロセスとプレイヤーの対応表を作る

入力注入が指すのは**プロセス**、検証で操作したいのは**プレイヤー**です。両者を結ぶ表が無いと「プレイヤー2 にタワーを置かせた」と書けません。**セッションを組んだ直後に 1 度だけ作ります。**

1. `studio_session.ps1 -Action List` でクライアントの PID を列挙
2. 各プロセスを順に前面化し、そのウィンドウのコマンドバーから自分が誰かを出力させる

```powershell
Set-Clipboard -Value 'print("WHOAMI " .. game:GetService("Players").LocalPlayer.Name)'
& "$S\studio_input.ps1" -ProcId <対象PID> `
  -Actions "click:<cmdX>:<cmdY>,wait:300,down:CTRL,press:V:60,up:CTRL,wait:200,down:CTRL,press:ENTER:60,up:CTRL"
```

3. 出力と PID を突き合わせ、`pid=... player=...` の表を証跡に残す

コマンドバーの位置も全画面捕捉で実測します。**コードは 1 行に収めてください**（複数行はコマンドバーで期待どおり動かないことがあります）。この表が無いまま「プレイヤー2 を操作した」と書かないこと。

## 3. ウェーブ開始からクリアまでを実際に操作する

### 3-1. タワーディフェンスは、実はこの方式と相性がいい

前面制約で同時操作ができない以上、常時 3人が同時入力するゲームだと検証範囲が大きく削られます。しかしタワーディフェンスの操作は**離散的**です。

```
準備フェーズ:  P1 が設置 → P2 が設置 → P3 が設置   ← 順に前面を取れば全部通せる
ウェーブ開始:  誰か1人がボタン/キー              ← 単独操作
戦闘中:        基本は観測のみ（自動迎撃）        ← 操作不要ならログ観測に専念できる
クリア:        次ウェーブへ                      ← 単独操作
```

つまり**主要な遊びの循環はほぼ全部、順次操作で通せます**。同時性が要るのは共有資源の競合（2人が同時に同じ残高から購入）くらいで、そこは後述の「言えないこと」に落とします。

### 3-2. 操作の実際

```powershell
& "$S\studio_input.ps1" -ProcId <クライアント1のPID> `
  -Actions "click:650:380,wait:400,press:1:120,wait:300,click:520:340,wait:800"
```

守る規則は 3 つ。

- **操作の前にビューポートをクリックしてフォーカスを取る。** 省くと最初のキーが捨てられます。
- **キーの押下と解放は 1 回の呼び出しの中で閉じる。** `down:` したまま別ウィンドウを前面にすると `up:` がそちらへ飛び、押しっぱなしのプレイヤーが残ります。実測で誤った判定を生んだ例があります。
- **戻り値を必ず読む。** `fg=False` や `WARN` が出たら「操作した」と扱わない。操作が効いていないように見えるときは、ゲーム側を疑う前に**入力側の戻り値**を見ます。

### 3-3. 再現性のあるマクロにする

「ビューポートクリック → 400ms → タワー選択キー → 300ms → セルをクリック」のように**時間で組む**と、同じ結果が繰り返し得られます。1 周ぶんのマクロが決まれば、以後はループで何度でも回せます。設置座標（セルのスクリーン位置）はカメラ固定なら固定値で済みます。カメラが動く設計なら、設置は座標クリックではなく MCP でカメラ状態を読んでから決めるか、キー操作主体の経路があるならそちらを使ってください。

### 3-4. 3人ぶんを回す順序

```
1. クライアント1を前面 → 設置操作 → サーバーログで player=P1 の accepted を確認
2. クライアント2を前面 → 設置操作 → player=P2 の accepted を確認
3. クライアント3を前面 → 設置操作 → player=P3 の accepted を確認
4. いずれか1台からウェーブ開始 → phase 遷移ログを確認
5. 戦闘中はサーバー側の実値を MCP で読む（敵数・ライフ・残高）
6. wave cleared ログを確認 → 次ウェーブへ（5周ぶんではなく、最低でも「循環が戻る」ところまで）
```

各ステップの直後にサーバーコンソールを取り、**そのステップで出るはずのログが出たか**を確認します。まとめて最後に見ると、どこで壊れたか分からなくなります。

### 3-5. 通しを始める前に、モジュールが読み込めることを確認する

セッションが立った直後、通し操作を始める**前**に、サーバー文脈で読めるべきモジュールを舐めます。require は各モジュールの初期化を実際に走らせるので、通し検証の途中でやると状態が汚れます。

```lua
local roots = {
    game:GetService("ServerScriptService"),
    game:GetService("ServerStorage"),
    game:GetService("ReplicatedStorage"),
}
local failed = {}
for _, root in roots do
    for _, d in root:GetDescendants() do
        if d:IsA("ModuleScript") then
            local ok, err = pcall(require, d)
            if not ok then table.insert(failed, d:GetFullName() .. " -> " .. tostring(err)) end
        end
    end
end
return if #failed == 0 then "all modules loaded" else table.concat(failed, "\n")
```

**クライアント専用のコンテナは含めないでください。** サーバー文脈でクライアント固有の値を参照するモジュールを読むと、正常なコードが失敗して誤検知の山になります。

## 4. 観測のしかた

### サーバー側（主軸）

`execute_luau` を `datamodel_type: Server` で。権威側の実値を直接読めます。

```lua
local Players = game:GetService("Players")
local out = {}
for _, p in Players:GetPlayers() do
    table.insert(out, string.format("%s uid=%d", p.Name, p.UserId))
end
return table.concat(out, "\n")
```

タワーディフェンスなら、ここでウェーブ状態・残ライフ・共有残高・生存敵数・設置済みタワー数を 1 回で読む問い合わせを作っておくと、各ステップの前後で叩くだけで済みます。時間差を測りたいときは同じスクリプト内で `task.wait()` を挟んで前後を返すほうが、往復ごとに読むより正確です。

### クライアント側（HUD の確認）

UI が実値を表示しているかは、画面キャプチャより **GUI ツリーを歩いてテキストを読む**ほうが速く正確です。

```lua
local gui = game:GetService("Players").LocalPlayer.PlayerGui:FindFirstChild("<ScreenGui名>")
local out = {}
for _, c in gui:FindFirstChild("<Frame名>"):GetChildren() do
    if c:IsA("TextLabel") then table.insert(out, c.Name .. " = [" .. c.Text .. "]") end
end
return table.concat(out, "\n")
```

ただし `datamodel_type: Client` は**アクティブなクライアントの1つ**に入り、どれかは選べません。必ず `Players.LocalPlayer` を先に出力してから解釈してください。届かない構成なら §2-5 のコマンドバー投入に切り替えます（手間はかかりますが**狙ったクライアントを確実に指定できる**利点があります）。どちらも使えないなら、クライアントごとの読み取りは**未検証**として引き渡しに書きます。

### コンソールとログファイル

- `get_console_output` は起動以降の蓄積を毎回全文返します。**差分は末尾を見る。**
- **出力の宛先はプロセスごとに別です。** ログファイルもプロセスごとに別ファイルができるので、最新 1 本だけ読むとクライアント側の記録をまるごと取り落とします。
- ファイルは**文字コードを明示して読む**（既定のままだと日本語を含む行が化ける）。
- **件数 0 を結果として記録する。** 「エラー 0 件」「棄却 0 件」は、数えたなら証拠。見ていない不在は何でもありません。

## 5. 実機で予想と違う挙動に当たったときの手順

**当て推量で直さないこと。** 順序を守ります。

0. **観測経路そのものを先に確認する。** 「エラーが 1 件も出ない」は、出ていないのか**出ている場所を見ていない**のか区別がつきません。無条件に 1 行出力する仕掛けを入れ、それが自分に見えることを確認する。ここが通らないうちは以降すべて無効。
1. **症状を実測値だけで書き、「確認済み」を命題へ分解する。** 「ウェーブ管理が壊れている」ではなく「players=3 なのに `to=Building` のログが 1 行も出ない」。

   そして「サーバー側の残高は 70 だと確認済み」は、次のうち 1 つしか検証していません。

   - サーバー内部の残高が 70（検証済み）
   - **送信した payload の当該フィールドが 70**（未検証）
   - **クライアントが受け取った値が 70**（未検証）
   - **受信側の更新処理がそもそも動いた**（未検証）
   - **書き込んだ先が画面に出ている個体である**（未検証）

   この分解だけで調査範囲が数分の1になります。推測を症状に混ぜると、実装側がその推測を前提に直してしまいます。
2. **コードだけで根本原因が一意に決まるか、読み取り専用で分析させる。** 決まらないなら「決まらない」と報告させる。推測で修正させない。
3. **決まらない症状の値を出す。安いほうから 2 段階で。**
   - **まず走っているセッションのまま読む。** 権威側の DataModel へ問い合わせて、判定に使う値・関数の入力・通信の受信内容を直接取る。**再ビルドが要らないのでこれで済むならこれで済ませる。**
   - **実行時に届かない値だけ、ソースへ診断ログを入れる。** 「境界外と判定した」ではなく「**判定に使った座標と半径そのもの**」を出す。ソースへ入れる側は高くつく（再ビルドで診断中のセッション状態が消える）ので、**次に要りそうな値をまとめて 1 回で入れる。**
4. **再実測してログの値を読む。**
5. **そこで初めて修正する。**

「サーバーは送っているのにクライアントが反映しない」形なら、クライアント側に一時的な受信リスナーを張り、**届いた値そのものと型**を見てください。送信側と受信側のどちらが悪いか一撃で分かります。

### 止まる条件を先に決める

診断 → 修正 → 再実測を **2 巡**回して実測値が動かないなら、コードをいじるのをやめます。先へ進む道は 3 つあり、決める人が違います。

- **(a) 当該挙動を今回の範囲から外す** — 所有者（あなた）の判断。勝手に切らない
- **(b) 既知の欠陥として受け入れ、引き渡しの「言えないこと」へ実測値つきで載せる** — 実行側で決めてよい
- **(c) 当該部分だけ止めて、依存しない部分を先に進める** — 実行側で決めてよい

いずれも症状は**実測値のまま**残します。1 つの症状に使ってよい時間の上限を、開始時に決めておいてください。

---

## 6. このゲーム種別で刺さりやすい既知の罠

コードを何度読んでも出てこない、実行環境側の性質です。症状が出てから探すのではなく、先に知っておくと速い。

**(1) テストセッションのプレイヤー識別子が負数。** Studio のローカルテストが割り当てる UserId は -1, -2, -3 … です。`UserId > 0` を前提にした検証は**テスト環境でだけ全滅**します。3人協力で「参加者を検証してからウェーブ開始」という設計だと、ここで人数が揃っているのに開始しません。妥当性は「有限な非ゼロ整数」で表現し、符号に意味を持たせないこと。しかもこの 1 つの制約が無関係に見える複数の症状（送信エラーと遷移停止）を同時に出します。**症状を数えて原因を数えないこと。**

**(2) 通信層が数値キー辞書のキーを文字列へ変換する。** これはタワーディフェンスで**ほぼ確実に踏みます**。プレイヤーごとの残高・貢献度・スコアを `{ [userId] = value }` の形で送ると、受信側では `{ ["-1"] = value }` になります。エラーは出ず、HUD が初期文字列のまま黙って止まります。**本番でも起きます。** 対処は受信側に wire decode 層を置いてキーを数値へ復元するか、そもそも `{ {id=..., value=...}, ... }` の配列形式で送る（新規設計ならこちらが安全）。

**(3) クライアント側で「エラーを出さずに何も起きない」経路。** 受信ハンドラが一度も動かない（リモートの実体が複製されない場所にある）／同名リモートが 2 つあって別個体を掴んでいる／画面に出ている複製ではなくテンプレート側へ書いている／UI 再生成で参照が死んだ個体を指している（**破棄済みへの書き込みは例外を出しません**）／payload が大きすぎる、など。最短の切り分けは**判定に使うフィールド 1 つだけの最小 payload を送ってみる**こと。届けば payload の形の問題、届かなければ経路の問題と二分できます。

**(4) 試合開始直後だけ初期化が失敗して再試行する。** クライアントのキャラクタ生成が完了する前に開始処理が走ると整合性検査に落ちます。回復経路があれば数回で自己収束します（実測で 3〜4 回）。**自己収束するなら機能欠陥ではなく起動遅延**ですが、黙って流さず再試行回数をログに残して観察事項に上げてください。回復経路が無い設計だと永久に止まるので、**回復経路の存在自体は必ず確認する**こと。

**(5) 閾値スナップが加速を殺す。** 「一定値未満は 0 に丸める」を毎ステップ無条件に適用すると、1 ステップあたりの増分がその閾値未満のとき永久に発進できません。タワーディフェンスなら減速タワーの slow 適用や、敵のスポーン直後の加速に同じ形が出ます。値ではなく**関係**（増分と閾値の大小）で確認してください。

**(6) Studio は place を開いている間にファイルへ書き戻す。** 検証前後で sha が変わったら、ビルドし直して元の sha が再現することを示せば同一性は証明できます。**再ビルドは Studio を閉じてから。**

## 7. 後始末

```powershell
& "$S\studio_session.ps1" -Action Cleanup -KeepPid <編集PID>
```

テストセッションのウィンドウを残すと、次回の疎通確認で取り違えます。**編集ウィンドウを強制終了すると次回に自動復元ダイアログが出る**ので、応答を待つほうが安いです。

## 8.「マルチプレイの動作確認できた」と言うために揃っているべきもの

ここが質問の後半への回答です。**下の 7 つが実測で揃って初めて言えます。** どれか 1 つでも欠けたら「一部を確認した」までです。

### 必須（7項目）

1. **ビルドの同一性**
   同一入力から 2 回ビルドして sha256 が一致する。そして**検証セッションが、記録したその sha の生成物そのもので起動されている**。
   → **ここが最も抜けやすい。** 各条件は独立に満たせてしまうので、ビルド A で通しを検証 → その後修正して sha B を出す → B の sha を記録、とすると **B を一度も遊ばずに全条件を満たせてしまいます。** 検証後にビルド対象へ触れる commit を 1 つでも打ったら、その検証は無効で再実行が要ります。「直してから測る」ではなく「**測ったものを出す**」。

2. **3人が本当に参加していた実測**
   プロセス数ではなく、サーバーログの `players=3` と、`pid=... player=...` の対応表。この表が無いと「プレイヤー2 を操作した」と書けません。

3. **試合の全サイクルが通っている**
   ウェーブ開始 → 迎撃 → クリア → **次ウェーブへ戻る循環** → 最終ウェーブ → 決着（勝利／敗北）→ 終了 → 次試合へ戻る、まで。
   → **単発の 1 ウェーブでは足りません。** 循環の欠陥（2周目で状態がリセットされない、決着後に次試合が始まらない）は循環を回して初めて出ます。敗北側の決着条件（ライフ 0）も、勝利だけ見て済ませないこと。

4. **3人それぞれの操作が権威側で受理された証拠**
   `player=P1/P2/P3` それぞれの `result=accepted` が別々に出ていること。
   → 合計値だけ見ていると、**1人だけ実際に効いていて残り2人の入力が捨てられていても気づけません。** 3人協力の検証ではこれが本体です。加えて**棄却経路も 1 回は通す**（残高不足でセルに置けない等）。理由コードつきで棄却が出ることを確認して初めて「受理判定が働いている」と言えます。

5. **主要な数値規則が実測ログで仕様どおりに効いている**
   タワー設置コストと残高の増減、撃破報酬、ダメージ式、漏れ 1 体あたりのライフ減少、ウェーブごとの敵数と種別。**仕様書の値と実測ログの値を並べて一致を示す**こと。

6. **「無かったこと」を数えた記録**
   エラー 0 件、想定外の棄却 0 件、警告 n 件。**数えたなら証拠、見ていないなら何でもありません。** 件数として書きます。サーバーとクライアント 3 台、**全プロセスのログを数えたうえで**の 0 件であること。

7. **証跡文書に実値が残っている**
   実測ログの実値とビルド sha。**ログの各セッション見出しに、そのときのビルド sha を書く。**

### 併記が必須の「この検証では言えないこと」

これを省くと、完成の宣言が沈黙によって過大主張になります。今回の方式なら少なくとも以下は未検証です。

- **3人の同時操作**（前面制約により順に操作しているため）。特に**共有資源の競合**（2人が同時に同じ残高からタワーを買う、同じセルへ同時に置く）は観測できません
- **実ネットワークの遅延と損失**（ローカルサーバーは同一機のため）
- **実端末・タッチ操作**（テストセッションでは端末エミュレーションが効かない構成があります）
- **長時間・多人数・多ウェーブの安定性**、および公開後の環境
- クライアント側の読み取りがコマンドバー経路でも通らなかった場合は、**「3人全員の HUD を確認した」とは書かない**

### さらに、主張の種類で道具を使い分ける

**「人が遊んで動いた」と第三者に言うなら、画面記録が要ります。** ログは OS 入力注入と人の手を区別しません。逆に「規則どおりに動いた」を示すのはログの仕事で、録画では精度が足りません。必要な主張に応じて用意してください。

### 最後に

**外部公開（publish）は所有者の専権です。** 実機検証が全部通っても、公開はあなたの明示的な指示があるまで行いません。公開は取り消しが難しく、課金・権限・審査が絡みます。

## 付録：実行順のまとめ

```
[事前]  疎通4点（MCP列挙 / Luau Server・Client / OS入力 fg=True / 出力の宛先確認）
        ビルド sha 2回一致
        構造化ログ（player別・理由コード付き）が実装済みか確認
          ↓
[構築]  place を開く → 全画面捕捉でダイアログ確認
        サーバー起動（F7 or メニュー実測座標）
        クライアント3台を1台ずつ追加（プロセス数=5 で成立判定）
        サーバーログで players=3 を確認
        pid ↔ player 対応表を作る
        pcall(require) で全モジュール読み込み確認
          ↓
[検証]  P1→P2→P3 の順に設置操作、各回サーバーログで accepted を確認
        棄却経路も1回通す（理由コード確認）
        ウェーブ開始 → phase 遷移ログ
        戦闘中はサーバー側の実値を MCP で読む
        wave cleared → 次ウェーブ → 決着 → 次試合へ戻る循環まで
        全プロセスのログを数える（エラー0件を「数えた結果」として記録）
          ↓
[記録]  ビルド sha + 実測ログ実値 + 読み取ったメニュー座標を証跡へ
        「言えないこと」を明記
          ↓
[後始末] Cleanup（編集ウィンドウは残す）
```

**この順序の肝は、実装より先に実機経路を通しておくこと**と、**検証後にビルド対象へ触れないこと**の 2 点です。
