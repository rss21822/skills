# Roblox タワーディフェンス（3人協力）マルチプレイ通し検証の進め方

結論から言うと、**「Studio を開いて3クライアント起動する」より前の仕込みで成否の8割が決まります**。ログとオーバーレイを入れずに3窓立てると、何が起きたか誰も説明できない映像だけが残ります。以下、順番に。

---

## 0. 前提：「実機マルチプレイ」には忠実度の段階がある

同じ「動作確認」でも、どこまでやったかで言えることが全く違います。最初にどの段まで登るか決めてください。

| 段 | 方式 | 検証できるもの | できないもの |
|---|---|---|---|
| 1 | Play Solo（Play） | 単純なロジック、UI | サーバ/クライアント境界。Solo は境界が曖昧なので**マルチのバグは出ない** |
| 2 | Run（サーバのみ） | サーバスクリプトの起動時エラー | プレイヤー絡み全部 |
| 3 | Play Here / Run + Play | 1人分の実 replication | 複数人の競合・共有状態 |
| 4 | **Local Server + 3 Client（今回の本命）** | 実 RemoteEvent、実 replication、3人分の join / 権限 / 共有リソース | 実ネットワーク遅延・パケットロス、実端末性能、TeleportService、MessagingService |
| 5 | Team Test（Publish 済み place に複数アカウント接続） | 実ネットワーク越しの挙動、実クライアント | 実端末の多様性（モバイル等） |
| 6 | 公開 place のプライベートサーバに実機3台 | ほぼ本番 | — |

**今回やろうとしているのは段4** です。段4は「マルチプレイのロジックが成立していること」の証明には十分で、「本番で快適に遊べること」の証明には不十分。ここを最後の宣言文で混同しないのが一番大事なポイントです（§6.3）。

---

## 1. 走らせる前の仕込み（ここが8割）

### 1-1. サーバ権威になっているか机上確認

3窓立てて最初に見つかるバグの大半はこれです。走らせる前に：

- ウェーブ進行・敵スポーン・敵HP・撃破判定・共有ゴールド・ライフは **すべてサーバが持っているか**（クライアントは表示だけか）
- クライアントからの操作は「やった結果」ではなく「やりたい要求」として RemoteEvent で飛んでいるか（`PlaceTower(cellId, towerId)` を送り、サーバが可否を判定して確定する形）
- 3人が**同じセルに同時に**タワーを置こうとしたとき、サーバ側で先勝ち処理があるか
- 敵の移動がクライアント側で独立計算されていないか（していると3画面で位置がズレる。ズレは「バグ」ではなく設計問題なので、走らせてから直すと高くつく）

### 1-2. 検証用テレメトリ（サーバ）を入れる

**証拠はスクリーンショットではなくログです。** 後から grep できる1行1イベント形式にしてください。

```lua
-- ServerScriptService/MPTestTelemetry.server.lua （検証時のみ有効化）
local T0 = os.clock()
local function log(tag, data)
    local parts = {}
    for k, v in pairs(data or {}) do
        table.insert(parts, string.format("%s=%s", k, tostring(v)))
    end
    table.sort(parts)
    print(string.format("[MPTEST][%07.2f][%s] %s", os.clock() - T0, tag, table.concat(parts, " ")))
end
```

最低限これらのタグを出す：

| タグ | 出すタイミング | 必須フィールド |
|---|---|---|
| `JOIN` | PlayerAdded | `player`, `count` |
| `ROLE` | 役割/スロット割当 | `player`, `slot` |
| `READY` | 準備完了操作 | `player`, `ready`, `readyCount` |
| `WAVE_START` | ウェーブ開始 | `wave`, `enemyTotal`, `players` |
| `TOWER` | 設置成功/拒否 | `player`, `cell`, `type`, `result`, `gold` |
| `ENEMY_DIE` | 撃破 | `wave`, `alive`, `reward` |
| `LEAK` | 敵が拠点到達 | `wave`, `lives` |
| `WAVE_CLEAR` | ウェーブ全滅 | `wave`, `lives`, `gold`, `elapsed` |
| `RUN_CLEAR` / `RUN_FAIL` | 決着 | `wave`, `lives`, `elapsed` |
| `SNAPSHOT` | 1秒ごと | `wave`, `alive`, `gold`, `lives` |
| `LEAVE` | PlayerRemoving | `player`, `count` |

### 1-3. 検証用テレメトリ（クライアント）を入れる ← これを飛ばさない

サーバログだけだと「サーバは正しかった」しか言えません。**3クライアントに同じ状態が届いていること**の証明には、各クライアントが自分の HUD 値を1秒ごとに吐く必要があります。

```
[MPTEST-C][Player2][0034.10][SNAPSHOT] wave=2 alive=7 gold=180 lives=20
```

後でサーバの `SNAPSHOT` と3クライアントの `SNAPSHOT` を同じ時刻で突き合わせれば、「replication が一致していた」が定量的に言えます。これが**マルチプレイ検証の中核証拠**です。

### 1-4. 画面内デバッグオーバーレイを入れる

各クライアントの画面隅に常時表示：

```
Player2 | slot=2 | wave=2 | gold=180 | lives=20 | alive=7 | ping=- | fps=--
```

理由：3窓のスクリーンショットは**どれが誰の画面か後から絶対に分からなくなる**。オーバーレイがあれば1枚1枚が自己説明的な証拠になります。窓のタイトルバーは当てにしないこと。

### 1-5. ショートモードを用意する

本番のウェーブ数で通すと1周が長く、失敗のたびに全部やり直しになります。検証用に「3ウェーブでクリア／敵数と体力を1/3」の設定を作り、**まずショートモードで通し→通ったら実ウェーブ数で1回**の順にする。

### 1-6. 乱数シードを固定する

敵スポーン揺らぎやドロップ判定に `Random.new()` を使っているなら、検証中は固定シードにする。再現性が無いと「直った」の判定ができません。

### 1-7. 強制操作フックを用意する

キー注入は必ずどこかで失敗します。逃げ道として、サーバ側にデバッグ用の関数（`_G.MPTEST.forceReady("Player3")`、`forceStartWave()`、`grantGold(500)`）を用意しておくと、詰まった箇所を飛ばして先の工程を検証できます。**ただし本番の入力経路の検証を全部これで代替してはいけません**（§6.1 の C-1）。

### 1-8. 事前の環境設定

- `File → Game Settings → Security → Enable Studio Access to API Services`：DataStore を使うなら ON（進捗保存があるTDなら必要）
- Studio Settings → Network の受信 replication lag（`IncomingReplicationLag` 相当）を後半で 0.1〜0.2 秒入れると、遅延前提のバグ（クライアント先読みのズレ）が出せる。初回は 0 のままで
- クライアント3窓 + サーバ1窓は重い。**各クライアントの画質を最低に**、ウィンドウは小さめに並べる
- Rojo 等で同期している場合、**Play セッション中のコード変更は反映されません**。必ず Stop → 同期 → Start

## 2. 3クライアント同時起動の手順

1. Studio で対象 place を開く（編集セッション）
2. **Test タブ → Clients and Servers** グループで **Players = 3**、Servers = 1 を選ぶ
3. **Start** を押す
4. サーバ用ウィンドウ1つ + クライアント用ウィンドウ3つが**別プロセス**として起動する
5. 終了時は **Test タブ → Cleanup**。× で閉じるとプロセスが残ることがあるので必ず Cleanup を使う

補足：

- クライアントは `Player1` / `Player2` / `Player3` として join します。**join 順は毎回同じとは限らない**ので、役割割当が join 順依存ならその前提を疑ってください
- Local Server のクライアントは実プロセスなので、`RunService:IsClient()` / `IsServer()` も RemoteEvent も本物の経路を通ります。ここが Play Solo との決定的な差
- Studio MCP の Play 開始系ツール（`start_stop_play` 等）は通常「1インスタンスの Play」を叩くもので、**この3クライアント起動はリボン UI 操作**です。MCP だけで完結させようとせず、起動は Computer Use（座標クリック）か手動、以後の観測を MCP、と役割分担するのが素直です

## 3. MCP + Computer Use での操作注入

### 3-1. インスタンスの識別

まず `list_roblox_studios` 相当で、MCP から見えている Studio インスタンスを列挙します。サーバ窓とクライアント窓が別々に見えるのか、1つしか見えないのかは**環境次第なので実測してください**。ここは事前に決め打ちせず、最初の3クライアント起動時に確認する工程として扱うのが安全です。

見えたインスタンスがどれか判別する方法：各窓のコンソール出力を取り、
- `IsServer=true` を出しているのがサーバ
- `[MPTEST-C][PlayerN]` を出しているのが各クライアント

で紐付ける。**ウィンドウタイトルで判別しない**（同一タイトルになりがち）。

### 3-2. キー入力注入の絶対制約

**Roblox クライアントはフォーカスされたウィンドウにしか入力を受け付けません。** よって：

- 「3人が同時にキーを押す」は OS レベル注入では**原理的に作れません**
- 実際の手順は必ず「対象窓をフォアグラウンドに → キー注入 → 結果確認 → 次の窓」の**逐次**になります
- 非フォーカスのクライアントは描画/フレームレートが大きく落ちることがあります。クライアント側のタイマーが遅れて見えても多くの場合バグではない（サーバは動き続ける）。この現象を「バグ発見」と誤認しないこと
- 「同時押しの競合」を検証したいときだけ、クライアント側デバッグフックで**同一フレームに要求を送る**手を使う（§1-7）。逐次注入では競合は再現できません

### 3-3. 入力経路の一致確認

キーボード注入で検証できるのは**キーボード経路だけ**です。本番の主操作が GUI ボタンやタッチなら、`UserInputService.InputBegan` ではなくボタンの `Activated` を通す必要があるため、**マウスクリック注入**（`user_mouse_input` 相当）でボタン座標を叩く形にしてください。ここを取り違えると「動いた」が本番と無関係になります。

### 3-4. 各ステップの型

すべての操作は次の3点セットで進めます。

1. 対象窓をフォーカス
2. 入力注入（キー or クリック）
3. **サーバのコンソール出力を読んで、対応する `[MPTEST]` 行が出たことを確認**

3 を省略して次に進まないこと。省略すると、後半で失敗したときに「どのステップから壊れていたか」が分からなくなります。

## 4. ウェーブ開始→クリアの通し台本

ショートモード（3ウェーブ）想定。各行に「期待するログ」を書いておき、出なければそこで止めます。

| # | 操作 | 期待ログ（サーバ） | 期待（各クライアント） |
|---|---|---|---|
| 0 | 3クライアント起動 | `JOIN`×3、`count=3` | 3窓ともオーバーレイに自分の名前とスロット |
| 1 | 各クライアントでスロット/役割確認 | `ROLE` ×3、slot 重複なし | 3窓とも他2人の存在が見えている |
| 2 | P1 が建設フェーズでタワー設置 | `TOWER player=Player1 result=ok gold=...` | **P2/P3 の画面にもタワーが出る**（← 最重要） |
| 3 | P2 が**同じセル**に設置を試行 | `TOWER player=Player2 result=occupied` | P2 に拒否フィードバック、盤面は変わらない |
| 4 | P2/P3 が別セルに設置 | `TOWER`×2 ok、gold が3人共有なら減算が1系列 | 3窓のゴールド表示が一致 |
| 5 | 3人が Ready | `READY readyCount=1,2,3` | 3窓とも「3/3」表示 |
| 6 | ウェーブ1開始 | `WAVE_START wave=1 enemyTotal=N` | 3窓同時にウェーブ表示が1へ |
| 7 | 敵進行中 | `SNAPSHOT` 毎秒 | 3窓の `alive` が±1以内で一致 |
| 8 | 撃破 | `ENEMY_DIE` が N 回、`alive` が単調減少 | 3窓のゴールド増加が一致 |
| 9 | ウェーブ1クリア | `WAVE_CLEAR wave=1` | 3窓ともクリア演出 |
| 10 | 2〜3を反復 | 同上 | 同上 |
| 11 | 最終ウェーブクリア | `RUN_CLEAR wave=3 lives=..` | 3窓ともリザルト表示 |
| 12 | **P3 を途中離脱**（別ランで） | `LEAVE count=2`、進行継続 or 規定の処理 | 残り2窓がフリーズ・エラーしない |
| 13 | Cleanup | — | プロセス残留なし |

行12（離脱テスト）は3人協力ゲームでは必須です。「3人揃わないと進行しない」設計だと、1人落ちた瞬間に残り2人が永久待機になる事故が非常に多い。

## 5. よくある詰まりどころ

| 症状 | ありがちな原因 |
|---|---|
| 3人目だけ役割が付かない / HUD が空 | `PlayerAdded` 接続前に join が完了している。接続直後に `Players:GetPlayers()` を走査して取りこぼしを回収する処理が無い |
| 自分の画面だけタワーが見える | クライアントでモデルを生成している（サーバ生成に直す） |
| 3窓でゴールドが食い違う | クライアントが自前で加算している。サーバの確定値を配る形に |
| 敵の位置が窓ごとにズレる | クライアント側で独立に移動計算。サーバ移動 + 補間に |
| 非フォーカス窓のタイマーが遅い | 仕様（描画スロットル）。サーバ時刻を正とする |
| Play 中にコードを直したのに変化しない | Play セッションは編集 DataModel と別。Stop → 同期 → Start |
| DataStore が全部失敗 | Studio Access to API Services が OFF |
| ロビー→試合の遷移が動かない | TeleportService は Studio では動かない。段5（Team Test / 公開 place）でしか検証できない |
| 起動が重い/落ちる | 4プロセス分のメモリ。画質最低・ウィンドウ縮小・他アプリ終了 |
| Cleanup 後も CPU を食う | 孤立プロセス。タスクマネージャで確認 |

## 6. 「マルチプレイの動作確認できた」と言うために揃えるべきもの

### 6.1 合格条件チェックリスト（各項目に証拠を紐付ける）

**A. 接続・参加**
- A-1 3人がサーバに参加し、サーバが `count=3` を記録
- A-2 3人に重複なくスロット/役割が割当たる
- A-3 3窓それぞれで他2人の存在（キャラ or HUD）が見える

**B. 権威と replication**
- B-1 各クライアントの操作が RemoteEvent 経由でサーバに届き、サーバが可否を判定している（拒否ケース1件以上を実測）
- B-2 **1人の操作の結果が残り2人の画面に反映される**（最低3種類の操作で確認：タワー設置、撃破報酬、ウェーブ遷移）
- B-3 サーバ `SNAPSHOT` と3クライアント `SNAPSHOT` が、全ウェーブを通じて `wave` 完全一致・`gold`/`lives` 完全一致・`alive` は許容差以内

**C. ゲームサイクル**
- C-1 ウェーブ開始が**本番と同じ入力経路**（キー or GUI ボタン）で起動できた ※デバッグフック起動だけでは不可
- C-2 敵スポーン → 移動 → 撃破 → 報酬 → ウェーブクリアが1周成立
- C-3 ウェーブ2以降へ自動/手動で継続し、最終ウェーブまで到達
- C-4 クリア条件成立時に `RUN_CLEAR` とリザルトが3窓に出る
- C-5 失敗条件（ライフ0）も1回は実測 ※クリアだけ見て「動いた」は片側だけ

**D. 異常系**
- D-1 途中離脱（3人→2人）で進行が停止・エラーしない
- D-2 同一セル同時設置など競合ケースで盤面が壊れない

**E. クリーンさ**
- E-1 サーバコンソールに**エラー/警告ゼロ**（通し全体を通じて）
- E-2 3クライアントすべてのコンソールにエラーゼロ
- E-3 通しの間、サーバの物理/スクリプト負荷が破綻していない

**F. 再現性**
- F-1 **同じ手順で2回連続成功**（1回だけの成功は「たまたま」と区別できない）
- F-2 手順書が第三者に再実行できる粒度で残っている

### 6.2 揃えるべき証拠パッケージ

1. **サーバコンソール全文ログ**（通し1周分、`[MPTEST]` 行を含む生ログ）
2. **クライアント3本のコンソール全文ログ**
3. **突き合わせ表**：時刻ごとに server / P1 / P2 / P3 の `wave, gold, lives, alive` を並べた表（B-3 の根拠）
4. **スクリーンショット**：最低5点 ×（可能なら3窓分）
   - join 直後（3人揃った状態）
   - ウェーブ開始瞬間
   - ウェーブ中（敵が複数体いる状態）
   - ウェーブクリア
   - 最終クリア/リザルト
   （オーバーレイが写っていること。写っていないと誰の画面か証明できない）
5. **チェックリストの記入済み版**（§6.1 の各項目に Pass/Fail と証拠へのポインタ）
6. **環境記録**：Studio バージョン、place のコミット/ハッシュ、実行日時、クライアント数、ショートモード有無、乱数シード、API Services 設定
7. **未検証事項リスト**（§6.3）

### 6.3 言えること / 言えないこと（宣言文の書き方）

上記が揃ったとき言えるのは：

> **「Roblox Studio の Local Server + 3クライアント構成で、3人参加からウェーブ開始・進行・クリアまでの1周を通し、サーバと全クライアントの状態一致・エラーゼロを2回連続で確認した」**

言えないのは：

- 実ネットワーク遅延・パケットロス下での挙動（同一PC内なので遅延ほぼ0）
- 実端末の性能（モバイル/低スペックPCでのFPS・入力遅延）
- 実プレイヤーの操作タイミング（人間の同時押し・想定外の順序）
- 4人以上、あるいは複数サーバ同時稼働
- TeleportService / MessagingService / 本番 DataStore に依存する経路
- 長時間安定性（数十分〜数時間のメモリリーク等）

**この「言えない」を明記したうえで「Local Server 3クライアントでの通し検証は完了」と書くのが正しい宣言**です。これを省いて「マルチプレイ動作確認済み」とだけ書くと、後で実機テストで壊れたときに検証の信頼が一気に落ちます。

さらに強い主張が必要なら、段5（Publish 済み place で Team Test、実アカウント3つ）を1回通してください。段4のチェックリストがそのまま流用でき、追加で確認するのは遅延起因のズレ・実端末FPS・遷移周りだけになります。

## 7. 所要時間の目安

| 工程 | 目安 |
|---|---|
| §1 仕込み（テレメトリ、オーバーレイ、ショートモード、フック） | 1〜2時間 |
| 初回の3クライアント起動 + インスタンス識別の実測 | 30分 |
| 初回通し（ほぼ確実に途中で詰まる → 修正 → 再起動の反復） | 1〜3時間 |
| 安定後の1周 | 15〜20分 |
| 証拠パッケージのまとめ | 30分 |

仕込みをケチると初回通しの時間が倍以上に膨らみます。順番を変えないのが最短経路です。

## 進め方の推奨順序（まとめ）

1. §1-1 の机上確認 → サーバ権威になっていない箇所を先に直す
2. §1-2〜1-7 の仕込みを入れる（テレメトリ / クライアントSNAPSHOT / オーバーレイ / ショートモード / 固定シード / 強制フック）
3. 段2（Run のみ）でサーバ起動時エラーをゼロにする
4. 段3（1クライアント）で1人分の経路を通す
5. **段4：3クライアントでショートモードを通す** → §4 の台本を1行ずつ、必ずログ確認しながら
6. 離脱テスト・失敗条件テストを別ランで実施
7. 実ウェーブ数で1周、その後もう1周（F-1 の2回連続）
8. §6.2 の証拠をまとめ、§6.3 の書き方で宣言する
