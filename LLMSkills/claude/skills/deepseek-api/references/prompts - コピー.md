# プリセットと依頼文の書き方

`--system-preset` で選べる4種。中身は `references/presets/*.md` にある。
プロジェクト固有の規約がある場合は、そのファイルを直接編集するか
`--system-file` で別途渡す。

| プリセット | 用途 |
|---|---|
| `luau-impl` | 実装コード生成。API捏造の抑制、実行文脈の明記、サーバ権威を要求 |
| `luau-review` | レビュー・デバッグ。位置の特定を必須にし、無理な指摘を抑制 |
| `design` | 設計の別案出し。追認を禁じ、代替案とその弱点を要求 |
| `plain` | 汎用 |

## プロンプトキャッシュを効かせる

入力の**先頭からの完全一致**プレフィックスだけがキャッシュ対象。同じコードベースに
何度も質問するなら、`--files` の指定順とプリセットを変えないこと。1バイトでも違うと
ヒットしない。効いているかは実行後に出る `cache hit` の数値で分かる。
ヒット時の入力単価はミス時の1/30なので、往復するほど差が出る。

## 依頼文の型

### 実装を頼む

悪い例: 「インベントリシステムを作って」
→ 何が正解か分からないので、それらしいが使えないコードが返る。

良い例:
```
ServerScriptService に置くインベントリサービスを実装してください。

要件:
- プレイヤーごとに最大30スロット。スタック可能アイテムは99個まで
- アイテム定義は ReplicatedStorage/ItemDefs (ModuleScript) から読む
- 追加・削除・移動を RemoteEvent で受ける。全ての検証はサーバ側で行う
- 変更は DataStore に保存。退出時とBindToCloseで確実に書く
- クライアントへの通知は変更差分のみ（全量送信しない）

正解の条件:
- 改造クライアントからアイテムを増殖できないこと
- 同時に2つの操作が来ても在庫がずれないこと
- 30スロット埋まった状態で追加要求が来たら拒否され、クライアントに理由が返ること
```

「正解の条件」を書くのが効く。要件だけだと解釈の幅が広すぎる。

### レビューを頼む

コードだけ投げると一般論しか返らない。**症状**を必ず添える。

```
--files "src/ServerScriptService/**/*.lua" を渡した上で:

症状: 2人以上が同時に宝箱を開けると、片方に報酬が二重に入ることがある。
再現: テストサーバーで2クライアントから同じ ProximityPrompt を
      0.5秒以内に発火させると3回に1回程度。
エラーログ: なし（例外は出ていない）
期待動作: 先に成立した1人だけが報酬を得て、後続は「既に開封済み」になる
```

### 設計を相談する

自分の案を先に出す。出さないと当たり障りのない一般論が返る。

```
現行案: マッチングをサーバ1つのグローバルキューで管理し、
        MemoryStoreService の SortedMap にプレイヤーIDを積む。
懸念:   人数が増えたときの MemoryStore のレート制限と、
        サーバをまたいだ整合性。
この案の弱点と、別の前提に立った代替案を出してください。
```

## 出力が長くなるとき

`--max-tokens` の既定は16000。実装一式を頼むと足りないことがある。
`finish_reason: length` はscriptがnonzeroで停止し、成果物outputを書かない。粒度を分けるか
`--max-tokens`を上げて再実行する。上限は384K。

ただし出力トークンは入力の3倍高い。「全部書いて」より
「まず設計と関数シグネチャだけ。実装は後で個別に」と分けたほうが、
安く、かつ検証しやすい。
