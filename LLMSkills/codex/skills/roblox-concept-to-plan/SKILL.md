# Robloxイメージ企画設計

ユーザーが思い描く体験を、**何を操作し、何を判断し、どんな結果が生じ、それを何回・何秒・何人で味わうか**まで設計する。成果物は、次に試作する内容とその判定方法が分かる数値つきゲーム企画。

企画と試作計画の作成をこのSkill内で完結する。承認待ちの段階を自動で追加しない。実装、Studio操作、アセット生成、公開は、この企画依頼だけでは開始しない。別Skillや特定のMCPを必須依存にしない。

## 1. イメージの核を固定する

自由文、箇条書き、擬音、情景、参考作品、添付画像を受け取る。入力書式を要求しない。画像がなくても文章だけで進める。画像がある場合は実際に確認し、見える特徴と推測した遊びを区別する。

原案から次を抽出し、短く提示する。

- **原案の核**: 誰になり、何をし、どんな感情を味わいたいか。重要な表現を短く原文で残す。
- **象徴的な場面**: プレイヤー自身の行動によって起きてほしい瞬間。
- **ユーザー指定**: 必須行動、世界観、人数、端末、予算、禁止事項など。
- **設計上の仮定**: ユーザーが未指定で、今回の企画を成立させるために補う事項。

指定と仮定を混ぜない。過去の別ゲームの人数、非P2W方針、ジャンル、制作体制などを、この新規企画へ無断で移植しない。入力の「100人」「無限」「絶対」も、明確な必須条件か雰囲気の表現かを文脈から判別し、曖昧なら解釈を明示する。

不足情報は合理的な仮定で埋め、企画の初稿を完成させる。核や明示的制約の両立に関わる曖昧さだけ、必要最小限を質問する。返答待ちでも確定できる部分は進め、問題の部分は条件つきとして示す。ユーザーが「質問なし」と指定した場合は、矛盾を隠さず条件つきの案としてまとめる。

## 2. 情景を遊べるルールに変える

主要なイメージごとに、次の因果をつなぐ。

`原案の表現 → プレイヤーの行動 → 判断・工夫 → 世界や他者の変化 → 見える／聞こえる反応 → 次にやりたくなること`

「爽快」「かわいい」「怖い」「巨大」「のんびり」を、演出だけで説明しない。たとえば「怖い」なら音を手掛かりに進むか隠れるかを選ぶ、「巨大」なら体で道を塞ぐなど、遊びへの効果を示す。鑑賞・交流・創作が核なら、感覚の変化、表現の選択、相手の反応も成果として扱う。必ず戦闘・制限時間・競争に変える必要はない。

中心となる遊びの構造を選び、通常は主案1つを具体化する。ユーザーが案数や設計を指定していたら従う。選択済みの設計を再審議しない。独創性のためだけに原案を変えず、比較が必要なら「既存の型から何が変わるか」を説明する。

主案で次を決める。

- 想定プレイヤーの遊びたい動機、役割、目標。
- 中核の操作と、その場で迷う選択肢。主操作ごとに、入力、成立条件、結果、コストまたは制約、フィードバック。
- 報酬、失敗や中断の扱い、やり直し。勝敗がないゲームでは達成・区切り・自由退出の扱い。
- 開始から一巡して再び遊ぶまでのコアループ。他者がいる場合は協力・競争・交流の具体的な影響。
- 条件の違う場面で選択がどう変わるか。単一の最適行動の繰り返しになっていないか。

「プレイヤーAがこう動くと、このルールによってこうなる」という短いプレイ例を添える。設定説明だけで終えない。

## 3. 初回体験と反復をつなぐ

参加直後から最初の象徴的な体験までを秒数つきで描く。通常は最初の60秒程度を使うが、企画の速度に合わせる。読み込み、説明、移動、待機を都合よく時間外にしない。操作可能になる前を含むか明記する。

1ラウンドの始まり・中盤・終わり・再挑戦、または自由滞在型の代表的な1回の活動を示す。ラウンド時間、活動1回の時間、プレイヤーの滞在時間を区別する。

再び遊ぶ理由は中心体験から設計する。上達、状況変化、創作、収集、関係性など、原案に効くものを選ぶ。成長要素を使うなら最初の目標と次の目標、その到達量を定義する。課金や日課は自動で付け足さない。企画に必要なら購入価値と通常の遊びへの影響を説明し、価格・収益は仮説とする。

## 4. 遊びを支配する数値を設計する

単に設定値を列挙せず、数値が原案の感情とルールをどう成立させるか説明する。

中心体験に必要な項目を選び、**初期値、単位、根拠の種別、採用理由、試作で動かす範囲または比較候補**を付ける。ユーザーが固定した値に勝手な調整範囲を設けない。

根拠の種別は次のように使い分ける。

- **ユーザー指定**: 入力された条件。技術的な実現性まで保証された値ではない。
- **設計仮説**: 今回提案する初期値・範囲・目標。検証前の出発点。
- **計算値**: 式と入力値から算出。入力が仮説なら計算結果もその前提に依存する。
- **出典値**: 確認した外部資料の値。URL、確認日、適用条件を添える。
- **実測値**: 提供データや実行結果から観測した値。条件、件数、観測期間を添える。

通常検討する項目は、参加人数と開始条件、中心行動1回の時間、最初の体験までの時間、活動の長さ、主要な距離・速度・個数・頻度、失敗後の復帰、最初の目標までの必要量。該当しない項目を埋めるために新機能を作らない。

**複数の値が関係する部分は、必ず式か具体的な一巡の計算で照合する。** 時間配分の合計、移動距離と所要時間、供給量と達成条件など、企画の成立を左右する関係を優先する。都合のよい成功率を実績として扱わない。

数値の設計・整合確認・試作指標を作る際は、[定量化ガイド](references/quantification.md)の該当節を読む。経済、戦闘、継続率は、その企画で扱う場合だけ使う。計算は利用可能な計算ツールで確認し、存在しない専用ツールを前提にしない。

## 5. Robloxで成立する形に絞る

企画の成立に関係する点を具体的に扱う。

- **操作と視認性**: 対象端末での移動、カメラ、主操作、同時入力、必要なUI。端末未指定ならタッチとPCを暫定対象と明記し、固定条件にはしない。主要動作の入力対応を示す。
- **参加構造**: 1つの遊びに参加する人数、サーバーの想定人数、最少開始人数を区別する。マルチプレイ案では人数不足、途中参加、退出時の挙動を決める。ソロ案に無理にマルチを加えない。
- **共有する結果**: 他者との接触、得点、共同物の状態など、全員で一致させる結果と、各自だけでよい演出を分ける。APIやコードまで決める必要はない。
- **負荷が集中する場面**: 同時に動く物体、NPC、破壊、生成、広い視界など、原案固有の難所を特定する。最大想定時の数と、事前配置・段階変化などの軽量な表現候補を示す。根拠なく「Robloxで問題なく動く」と断言しない。
- **保存**: 持ち越す成果とセッション内だけの状態。保存が核でなければ不要とする。

現行仕様・API・規約・市場・競合について事実を述べる必要がある場合は、その時点で調べる。技術・仕様は公式一次資料を優先する。未確認の事実を企画の成立条件にしない。単なる創作上の初期値に検索由来の権威を付けない。

## 6. MVPと判定方法を作る

最も不確かな中心体験を試せる最小試作を定める。マップ、操作、遊ぶ人数、オブジェクト、画面などを数で示し、後回しにする機能を分ける。原案の核を削った小型版を、同じ仮説の検証と呼ばない。

試作の順序と、各試作で判明することを書く。人員や期間が未指定なら、工数・日程を確定扱いせず、必要作業と依存関係を優先する。見積もる場合は制作経験、既存素材、1日の稼働時間などの前提と幅を付ける。

重要な仮説ごとに、次を組にする。

`確かめたい体験 → 対象者・人数・端末・試行数 → 観測する行動／出来事 → 指標と分母・時間窓 → 仮の合格条件 → 不合格なら変える設計`

楽しさは企画書の採点だけでは検証できない。実際の行動、失敗理由、本人が体験をどう語るかを組み合わせる。小人数テストは問題発見用であり、市場規模・継続率・収益の証明にはしない。NPC・自動試行・計算結果を人間の楽しさや人間同士の協力の証拠に置き換えない。

## 出力

ユーザーの言語と指定形式を優先する。通常は次をまとめ、見出しは企画に合わせて統合してよい。

1. **企画の要約**: 仮タイトル、一文ピッチ、原案の核、指定条件と仮定。
2. **具体的な遊び**: 対象者、役割、操作、ルール、コアループ、象徴的なプレイ例。
3. **体験の流れ**: 初回の時系列、1回の活動、失敗・退出・再挑戦、反復理由。
4. **主要数値**: 値・単位・根拠種別・理由・調整範囲、関係する式と計算結果。
5. **Roblox向け設計**: 対象端末の操作、参加構造、負荷や保存などの成立条件。
6. **MVPと検証**: 作る数量、後回し、試作順、観測方法と仮の合格条件。
7. **判断**: 最も強い点、主要リスク、未確定事項、最初に作って確かめるもの。調査した場合は出典。

依頼が短文でも中身を単なるアイデア紹介に縮めない。一方、求められていない全開発仕様書や大量の代案には拡大しない。短い回答を求められたら説明量を削り、核・主操作・主要数値・最大の未検証仮説は残す。ファイル納品が必要な環境では成果物を保存してリンクし、チャットには要約を返す。

## 完成前の確認

- 原案の核と明示条件が、通常のプレイで実現するか。変更が必要なら黙って置き換えていないか。
- 見た目だけでなく、何を操作し、どんな変化が起こり、どう一巡するか分かるか。
- 人数、時間、供給量、目標量が矛盾せず、単位と計算の前提が追えるか。
- 仮説、計算、出典、実測が識別でき、設計目標を実績や業界標準と呼んでいないか。
- 最小試作が中心体験を検証し、失敗時に変更する設計まで決まっているか。
- 確認していないStudio動作、端末性能、人気、収益、権利関係を確認済みにしていないか。
