# multi-view-valuation

投稿・提示されたゲーム案を、関連性の高い視点から評価・改善する。広い候補から視点を選び、企画の核を生かして「誰に、どんな状況で、どの価値を強く届けるか」を具体化する。

## 入力と範囲

- 会話、指定資料、適用されるプロジェクトの指示から、ゲーム案とユーザーの評価目的を読む。過去の別企画の制約や好みを今回の必須条件にしない。
- 世界観、プレイヤーの行動、ルール、人数、端末、時間構造、想定ユーザー、収益化、制作条件のうち、提示されている情報を使う。企画評価を依頼されただけで全項目の回答を要求しない。
- 案が全くない場合は案の提示を求める。判断を左右する欠落は最小限だけ質問し、それ以外は仮定・条件分岐として進める。対象端末や国を勝手に確定しない。
- ユーザーが明示的に固定した世界観・中心動作・確定仕様・禁止事項を尊重する。原案に書かれているだけのルールは評価時点の基準であり、自動的に変更禁止にはしない。制約による弱点は明示し、制約内の改善を先に考える。中核を変える別案は、必要な場合だけ「方向転換の選択肢」と分ける。
- 既定の成果はチャットでの企画評価と改良案。保存を求められたら指定先へ保存する。評価だけの依頼でコード、正本仕様、公開設定を変更しない。

## 1. 評価の基準になる原案を固定する

最初に短く記述する。

1. コアループ：何をする → 何が起きる → 何を得る／失う → 次に何をする。
2. 核になる魅力：どの行為・出来事を、どんな気持ちよさに結び付けたいか。
3. 条件を「明示された固定条件」「記載済みだが改善可能なルール」「未確定事項」に分ける。指定された成功の意味があれば、到達人数・満足・継続・収益などを区別する。

原案に書かれたこと、設計上の推測、外部資料で確認した事実を混ぜない。後から提案した機能を、原案がすでに持つ長所として採点しない。

例えば「操作と世界観を守る」という指定があっても、原案の脱落・観戦・報酬のルールまで固定したことにはならない。変更可能なルールが主な障壁なら、そのルールの削除・変更も改善候補として検討する。固定かどうか不明なものを推測で固定する場合は、その仮定と判断への影響を示す。

## 2. 関連性の高い視点だけを選ぶ

[視点カタログ](references/viewpoint-catalog.md)の索引を確認し、原案に関係する群を読む。カタログは候補集であり、全項目を評価するチェックリストではない。必要な視点は追加してよい。

### 選び方

まず、原案の行動・制約・期待する価値から候補を出す。ジャンルの既存ユーザーだけでなく、同じ価値を求める隣接層、参加できない層、誘われる人なども、具体的な接点がある場合に候補にする。

各候補について、次を確かめる。

- **接点**：原案のどの行動、ルール、端末条件、利用場面、関係性と結び付くか。
- **判断への影響**：この視点を採ると、ターゲット選択や具体的な設計判断が変わり得るか。
- **重要性**：企画の中心的な価値、参加・理解・継続の重大な障壁、ユーザー指定の目的に関わるか。
- **独自性**：他の視点と同じ主張の言い換えになっていないか。重なる場合は統合できるか。

「どのゲームにも当てはまる」「潜在的にはあり得る」だけでは選ばない。地域展開、配信、課金、VRなどを、企画との接点なく毎回追加しない。反対に、原案が明記した重要な対象や制約を、評価しづらいから省かない。

重要な接点はあるが仕様が未定なら、採用した仮定を明示した**条件付き視点**にする。情報不足だけを理由に視点を増やさない。

### 視点の単位

有用な場合は「誰 × 利用状況 × 求める結果」にまとめる。例：対戦初心者 × スマホで友人に誘われる × 実力差があっても一緒に遊びたい。国名やジャンル名だけを人物像にしない。

- 一人で参加することと、一人用の遊びを求めることを分ける。
- 一回のプレイ時間、最初の満足までの時間、長期的な関与期間を分ける。
- 端末、通信、音、操作能力は、好みとは別の利用条件として扱う。
- 同じ人が複数の視点に属し、場面によって目的が変わり得る。各視点を独立した市場人口として合算しない。
- 関連性と好意的評価は別。企画に不満を持つ可能性が高い相手も、重要な対象なら選ぶ。

深掘りは通常4〜8視点程度で収まるが、件数は目標にしない。単純な案は少なくてよく、複雑な案は必要に応じて増やす。ユーザーが数や視点を指定した場合はその指定を優先する。

選んだ視点にV1、V2などのIDを付け、選定理由を一文で示す。重要そうに見えて外した候補があれば、少数だけ保留・除外理由を示す。全候補の棄却表は作らない。

## 3. 各視点で原案を評価し、改善する

各Vについて以下を具体化する。架空のユーザーの発言を実際の証言として書かない。

| 項目 | 記述する内容 |
|---|---|
| 対象と期待 | 誰が、どんな場面で、何を得たいか |
| 原案の評価 | 強い適合／条件付き適合／弱い適合／判断材料不足。設計上の判断であり実測満足度ではない |
| 魅力と根拠 | コアループのどの行動・結果が期待に応えるか |
| 障壁と根拠 | どの場面で、何が原因で価値を受け取れなくなるか |
| 改善 | 何を追加・削除・調整・並べ替え・伝え直すか。どう効くと考えるか |
| 代償と影響先 | 失う面白さ、他のVへの悪影響、複雑さ、制作・運営負担 |
| 確かめ方 | 何を観察すれば、その改善が有効か判断できるか |
| 確信度 | 高／中／低と理由。評価の良し悪しとは分離する |

「初心者に優しく」「UIを改善」「国際展開する」などで止めず、場面と変更内容まで落とす。例：説明中に試合が進むことが障壁なら、説明の短縮、進行位置の変更、実演などを比較する。必ず新機能を追加するとは限らない。

原案がすでに適合し、変更の利益が小さい場合は「維持」とし、守る理由と未確認点を示す。各視点への迎合や改善案の件数確保を目的にしない。

改善にI1、I2などのIDを付け、対象Vを対応付ける。同じ改善は重複提案せず、複数視点への効果をまとめる。

## 4. 視点間の衝突を解き、改良案にまとめる

視点別の案を全部足したゲームを完成案にしない。

1. **優先する対象**：主対象、相性のよい副対象、今回積極的に狙わない対象を根拠とともに示す。対象の明示指定がある場合はそれを基準にする。
2. **両立と衝突**：複数視点を助ける改善と、片方を助けると他方を損なう改善を分ける。競技性と番狂わせ、短い区切りと長期蓄積などを、実際に衝突する条件まで説明する。
3. **扱いを決める**：採用候補／比較試作／保留／今回は見送り／維持を区別する。すべてを別モードや設定で吸収せず、人口分散・学習負担・保守負担も考える。
4. **優先順位**：核の価値への効果、重大な障壁の解消、根拠の強さ、依存関係、実装・運営負担から「先に試すもの」を絞る。人数・満足・継続・収益・実現性を根拠なく一つの点数へ足し合わせない。
5. **統合した改良案**：採用候補だけを反映した短い企画文を示す。原案から何が変わり、何を守り、何を狙わなくなるかを明確にする。提案段階であることを保ち、未承認の仕様確定にしない。

根拠が拮抗する場合は、有望な方向を少数に絞って比較し、判別できる試作・観察を示す。最大化の意味が不明なまま、収益や総ユーザー数だけを唯一の目的にしない。

## 根拠と検証の扱い

- 概念上の評価は資料だけでも進められる。現時点の市場規模、競合の仕様、国別傾向、Robloxの分類や条件を結論の根拠にする場合は、利用可能な調査手段で確認し、出典と時点を付ける。
- 調査できなければ未検証と明示する。対象国・端末の人口や嗜好、成功確率、売上、継続率を作らない。国籍・性別・年齢から嗜好を決めつけない。
- 市場の人気、ユーザーの発言、制作者の意図、仕様の存在、実プレイの結果は別の証拠。競合の共通要素を成功原因と断定しない。
- 未検証の問題は設計上のリスクとして書き、実際に起きた離脱や不満として書かない。改善後の効果も、測定前は仮説とする。
- 検証案は「対象者・条件・比較する変更・観察する行動・判別したいこと」を付ける。ユーザーテスト、実機検証、公開、継続監視を実施したことにせず、実行は依頼範囲に従う。
- 閾値や所要工数を置くなら、ユーザー指定・既存実績・仮置きを区別する。重大な不明点ほど先に検証し、検証用に最小限の試作を提案する。

## 既定の出力

長さは企画の複雑さに合わせる。次の内容を簡潔にまとめる。

1. **評価の結論**：最も有望な対象と価値、可能性を制限する主要な条件。
2. **原案と前提**：短いコアループ、固定条件、結論に関わる仮定。
3. **選定した視点**：V-ID／誰・状況・期待／原案との接点。必要なら主要な保留・除外理由。
4. **視点別の評価・改善**：V-IDごとの魅力、障壁、I-ID、代償、確信度。表だけで長くなる場合は短いカード形式にする。
5. **統合と優先順位**：I-ID／対象V／変更内容／衝突・負担／扱い／先に確かめること。続けて改良案の短い企画文。
6. **未確認事項と検証**：判断を変え得るものだけ。外部資料を使った場合は該当主張に出典を付ける。

ユーザーが採点を求めた場合だけ、採点基準と対象を定義して評価する。異なる視点を単純平均して成功確率に変換しない。

## 完了前の点検

- 選定した全Vに、原案との具体的な接点と判断上の意味があるか。
- 好意的な相手だけを選び、重要な不適合や参加障壁を消していないか。
- 原案と改善後を混同せず、指定された核・制約を守っているか。
- 各改善が対象Vと因果の仮説につながり、代償と確かめ方を持つか。
- 不要な機能を足さず、維持・引き算・対象を絞る判断も検討したか。
- 統合案が相反する提案を無条件に同時採用していないか。
- 市場データ、嗜好、ユーザー反応、実施済みの検証を捏造していないか。
- 未確定事項を理由に、可能な評価・改善まで止めていないか。
