# 成果物とデータの契約

この資料は成果物の形式を定める。形式が埋まっただけで、市場調査や真偽確認が完了したとは扱わない。

## 1. 保存と正本

指定された作業場所を使用する。既定は `research/roblox/<project-slug>/<YYYY-MM-DD>/`。同名実行があれば別の実行フォルダーを作る。Skillの設置先、元の企画書、ゲームのコードへ無断で出力しない。

- `research.json`：根拠、比較対象、判断、検証状態の正本。
- Markdown：正本の情報から、比較・理由・全体構成を人が読みやすく論述する。
- HTML：正本の参照画面。元資料や判断へ移動できるようにする。
- `research-log.md`：実行した検索、取得、除外、アクセス制約、終了理由。
- `CHANGELOG.md`：条件、根拠、判断、ユーザー承認の変更履歴。

文章上の重要な事実も `C` と `S` で結ぶ。本文にだけ新しい数値や「採用済み」を追加しない。MarkdownとJSONが食い違う場合は、元資料・ユーザー指示を再確認して両方を修正する。

## 2. レポートの最低内容

| ファイル | 含めるもの |
|---|---|
| `00-brief.md` | 実際に読んだ資料、対象者・感情目標、固定・希望・仮説・未決、成功の定義、優先D、調査範囲と能力 |
| `01-market-and-history.md` | 同定済みの候補、選定・除外理由、現在市場、歴史的変化、源流と類似の区別、比較対象、市場機会 |
| `02-competitor-analysis.md` | 初回・コア・ラウンド・セッション・再訪の構造、低人数・共遊、公開指標、観察手段、ユーザーの声、別の成功説明 |
| `03-design-decisions.md` | 現状のレビュー、価値の突出点、捨てるもの、各Dの選択肢と根拠、整合する全体案、自然なフック、未承認事項 |
| `04-growth-and-operations.md` | 獲得と本編の一致、流入別の設計、現行公式確認、課金価値と副作用、通常時とイベント時、制作・運営負荷 |
| `05-validation-and-handoff.md` | 危険な仮説順の試作、測定対象と母数、判断基準、未実施の明示、承認済み仕様と提案の分離、状態遷移・責務・復旧・受け入れ条件 |

`research-only` では架空の自作ゲーム仕様や採用案を作らず、市場機会と検証へつなげる。絞った依頼では不要ファイルを省略できる。その理由と未調査範囲をログに記録する。

## 3. JSONの構造

`assets/research.template.json` を新規成果物の場所へ複製し、記入する。`assets/research.schema.json` はDraft 2020-12形式。各レコードの必須フィールド・許容値はスキーマを正とする。空欄を架空の事実で埋めない。

| 最上位キー | ID | 意味 |
|---|---|---|
| `schema_version` | — | 形式バージョン。現在のパッケージは `1.0.0` |
| `meta` | — | 案件、開始日時、時間帯、モード、深度、範囲、実行能力、制約、未解決、完了状態 |
| `brief` | — | 企画、対象者、感情、条件、資料、制作条件、除外 |
| `sources` | `S001` | 実際に取得した資料、または未取得と明示した参照候補 |
| `claims` | `C001` | `fact / interpretation / hypothesis`、根拠、信頼度の理由、限界、代替説明 |
| `games` | `G001` | 同定、比較群、指標、根拠付きの設計メモ |
| `observations` | `OBS001` | 実機、動画、公式説明、投稿等から確認できたこと |
| `opportunities` | `OP001` | 未充足需要、既存の代替、歴史的資産、障壁、反証、検証 |
| `decisions` | `D001` | 判断の問い、選択肢、推奨と承認の分離、根拠、関連テスト |
| `hooks` | `H001` | 普段の遊びから自然に生じる見せ場の構造 |
| `tests` | `T001` | 仮説、比較、対象者、指標、期間、暫定基準、実施状態、結果 |
| `platform_checks` | `P001` | Discovery、Analytics、課金、Teleport、権利等の今回の公式確認 |
| `risks` | `R001` | 企画・技術・運営・権利上のリスクと対策 |
| `research_log` | — | 検索・取得・除外・制約の記録 |
| `changes` | — | 変更理由、影響ID、ユーザー承認の記録 |

IDは3桁以上で一意にする。選択肢は親Dに属する `D001-O1` 形式。追加調査や改名でも既存IDを再利用し、番号を詰め直さない。`affected_ids` は実在する上表のIDか選択肢IDのみ。ブリーフ全体の変更は説明文へ書き、対応IDがなければ `[]` にする。

レコードの追加項目は任意の `details` オブジェクトへ入れる。例：`games[].details.history` に系譜や `games[].details.session_flow` に状態遷移を記録できる。ただし重要な根拠・数値・承認を `details` だけへ隠さず、定義済みフィールドと結ぶ。`details` 内部の参照や独自項目は自動検証の対象外である。

## 4. 出典と主張

`source` には資料名、発行主体、実在URLまたはローカルパス、公開日、取得日時、該当箇所、閲覧状態、注意点を記す。認証トークン、個人情報、秘密のURLを成果物へ転記しない。

- `accessed`：今回本文を確認した。
- `provided`：ユーザー提供内容を実際に読んだ。
- `snippet_only`：検索抜粋等のみ。本体確認済みと同一にしない。
- `inaccessible`：アクセスを試みたが内容を取得できなかった。

`fact` は直接支える閲覧済み資料を持たせる。`interpretation` は根拠の `C` または `S` を持たせ、代替説明を記す。`hypothesis` は今回の提案であることが分かる表現とし、関連D/Tから検証方法へ到達できるようにする。

`observations` は観察手段と位置を明示する。動画ならタイムスタンプ、文章なら見出し、実機なら条件と記録場所を残す。実際のプレイ時刻が不明なら取得時刻と混同しない。字幕や文章から見ていない映像・音・操作感を作らない。

引用は短く必要な部分に限定する。要約にも出典を付ける。コミュニティ投稿者を個別追跡したり、未成年者の個人情報を収集したりしない。

## 5. 指標と欠損

各 `games[].metrics[]` は独立した観測値。名前・値・単位だけでなく、定義、集計区分、対象集団、取得日時、期間、出典、値の性質、欠損理由、制約を保存する。

| `provenance` | 扱い |
|---|---|
| `public_observed` | 公開画面や取得可能な公開値の観測 |
| `creator_reported` | 制作者が公開した値。対象・時点をそのまま残す |
| `third_party_estimate` | 第三者による推計。手法・誤差・制約を示す |
| `authorized_internal` | ユーザーが閲覧を許可した自作ゲーム等の内部データ |
| `planning_assumption` | 計画用の仮定。実績や公開観測と混ぜない |
| `unavailable` | 非公開、取得不可、定義不明等 |

欠損は `value: null` と具体的な `missing_reason`。取得済みの0は数字の `0` として残す。数字の値があるとき `missing_reason` は `null`。未知の公開日・期間・IDも `null` を使うが、メモで理由を補う。

日時は、分かる範囲で時間帯付きISO 8601を使う。`observed_at` と対象期間は別物。日付しか分からない資料公開日は `published_at` の文字列に元の粒度を残す。古い値を今日のCCUとして書かない。

月間値・累計値・スナップショットを同じ系列として折れ線化しない。履歴グラフを作るなら同一の指標定義・対象・観測間隔を確認する。不足した時点を架空の点で補間しない。

## 6. 推奨とユーザー承認

`recommended_option_id` はAIが推す案、`approved_option_id` はユーザーが実際に承認した案。両者は一致しなくてよい。

- 通常の提案：`status: proposed`、推奨IDを記入、承認IDと承認根拠は `null`。
- 明示的な承認：`status: approved`、承認IDと実在する指示の日時・引用位置等を記録。
- 保留／棄却：`deferred / rejected`。推奨履歴は残し、承認を示唆しない。
- 過去の承認を撤回した場合：現在の承認フィールドを解除し、以前の承認と撤回理由を `changes` に残す。

検証状態も分離する。未実施テストに結果を記入しない。`completed` は実測結果と根拠となる記録が必要。「テストを設計した」ことは「実施した」ことではない。

## 7. ローカルHTML

最低限、ブリーフ、作品比較、観察、市場機会、判断、フック、テスト、根拠、出典、公式確認、リスク、ログ、履歴へ移動できるようにする。

同梱レンダラーは検索とIDリンクを持つ閲覧専用の静的ページを生成する。外部CDN、アカウント、オンライン公開、APIキーは不要。横並びカードは比較の補助であり、人気ランキングの自動評価ではない。文章・時系列・詳細比較の説明はMarkdownにも残す。

JSON変更後は再生成する。検索欄は保存用入力フォームではない。出典リンクを人が開く場合を除き、ページ自身は外部通信を行わない。外部文字列をHTMLとして実行しない。

## 8. 任意の補助スクリプト

Python 3.10以降の標準ライブラリだけで動く。ネットワーク取得やRobloxログインは行わない。下記 `<skill-dir>` と `<run-dir>` は実際のパスに置き換える。スクリプト自体は成果物の内容を調べて埋めない。

```text
python "<skill-dir>/scripts/validate_research.py" "<run-dir>/research.json"
python "<skill-dir>/scripts/render_dashboard.py" "<run-dir>/research.json" --out "<run-dir>/dashboard.html"
```

検証のJSON出力には `--json` を使える。HTMLがすでに存在すると通常は停止する。更新を許可された場合に限り、退避後に `--overwrite` を指定する。JSON正本の上書きやWeb公開はしない。

バリデーターは同梱スキーマに使われているキーワードに対応する検証器で、任意のJSON Schemaの完全実装ではない。構文・必須項目・値の型・ID・参照・欠損・承認・一部状態整合性を確認する。出典が本当に存在するか、閲覧したか、ユーザーが本当に承認したか、数値が正しいか、企画が成功するかは判定しない。

最後に元資料との突合、Markdownとの一致、根拠の限界、HTMLの表示・リンク・検索を可能な範囲で人またはエージェントが確認し、未確認の範囲を報告する。
