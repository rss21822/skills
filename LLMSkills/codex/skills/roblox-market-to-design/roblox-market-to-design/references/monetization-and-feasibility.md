# 収益化・LiveOps・実現性

## 1. 課金は「何を売るか」から始めない

`欲しい価値→欲しくなる場面→購入後の体験→無料利用者への影響→継続・共有への影響` を整理する。
次は候補一覧であり、全採用を要求しない。各商品の実装・販売条件は公式資料を実行時に確認する。

| 欲しい価値 | 候補 | 点検 |
|---|---|---|
| 見せる・自分らしさ | 衣装、演出、エモート、拠点装飾 | 誰に見せるか、視認性、権利 |
| 新しい遊び | 限定コース、追加モード | 無料の核を欠落させないか、友人・人口分散 |
| 所属・支援 | VIP、会員特典 | 実価値、継続提供負荷、差別的体験 |
| 便利さ | 保存枠、整理、移動 | 意図的な不便を販売していないか |
| 継続の目標 | シーズン型報酬 | 制作量、期限、義務感、途中参加 |
| 個別の遊び場 | Private Server等 | 誰が払うか、グループの価値 |
| やり直し・消耗品 | 復活、一時効果 | 負けを煽る圧力、対戦の公平感 |
| 抽選・取引 | ランダム有料報酬等 | 現行の開示・ユーザー別条件、理解可能性、代替 |

名称から商品の実体を決めない。「VIP」がPassなのかSubscriptionなのか、観測できる範囲で確認する。
購入画面、販売場所、商品ID、期間、地域・表示条件を残す。一覧の最高価格を平均支出にしない。売上が不明なら不明のまま収益構造だけを分析できる。

## 2. 限定モード課金とPlaceの分割

二つは別の判断である。
- 商品：何を買うと、どの権利を、いつまで持つか。
- 実装構成：同一Placeか、別Placeか、別のExperienceか。

比較項目：友人の一部だけが所有する場合、低人数、再接続、購入反映、権利のサーバー検証、入場経路、失敗時の復帰、ロード、保存データ、モデレーション。
「入口を置けば課金モードが完成」と考えない。Teleportや関連機能は公式API・テスト条件を再確認する（R12）。市場分析の段階でAPIのコードを生成・適用する必要はない。

## 3. LiveOpsを制作能力へ落とす

| 更新の種類 | 必要な制作 | 確認する問い |
|---|---|---|
| 数値・ルール | バランス、テスト | 新しい選択か、単なる上限追加か |
| マップ・ステージ | レベル設計、アート、負荷確認 | 更新なしでもコアが続くか |
| 装備・キャラ・収集 | 性能、アニメーション、UI、経済 | インフレや不公平を増やさないか |
| イベント | 制作、告知、同接時の運用 | ピークの後に残る価値があるか |
| コミュニティ | 対応、ルール、不正・苦情対応 | 少人数で維持できるか |

「毎週新マップ」等を無料の施策にしない。企画ごとの能力・コスト・代替頻度を比較する。実績不明の工数や人件費は数値化せず、相対的な負荷と調べる項目を示す。

## 4. 少人数・LLM制作の分解

| 領域 | 引き継ぎ内容 |
|---|---|
| コアの未知 | 気持ちよさ、操作、勝敗、人口の成立を試す最小プロトタイプ |
| 共通の構成 | 状態遷移、ロビー、結果、再戦、権利、保存、計測などの仕様 |
| 手作業・調整 | マップ、演出、音、アニメーション、画面、実機調整 |
| 運用 | 更新、バランス、不正、問い合わせ、権利確認、障害 |

LLMで仕様から実装しやすい部分と、人間の検証・制作が必要な部分を分ける。エンジン機能が存在しても、対象端末・人数・負荷で成立する保証にはならない。
通信、物理、所有権、データ永続化、悪用可能性は市場性と別に技術的検証を置く。R13を基に、対象端末を決めた性能検証を計画する。

## 5. リスクと最新方針

音楽・キャラクター・名称・アニメーション・モデルは、仕組みの参照と表現の複製を分ける。Creator Store等にあることだけで、あらゆる利用が許可されるとは判定しない。ライセンス・条件を対象ごとに確認する。
未成年を含む可能性のある市場では、分かりにくい課金、偽の希少性、退場圧力、嫌がらせを成功手段として推奨しない。
有料ランダム報酬はR11、他の安全・広告・コミュニケーション条件は関係する最新公式方針を探す。このSkillは法的な適法性を保証するものではない。
