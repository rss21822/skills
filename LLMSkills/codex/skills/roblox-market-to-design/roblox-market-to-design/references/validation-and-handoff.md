# 検証から実装への引き継ぎ

## 1. 重要度の高い未知から試す

検証の優先順位は、外れたときに失う制作量、根拠の弱さ、試す負担で決める。大きな機能を先に作ることを進捗の代わりにしない。
以下はフェーズ例であり、全てに人数・時間の固定合格値は置かない。

| 段階 | 問い | 最小の材料 | 進む条件の作り方 |
|---|---|---|---|
| 入口 | 何ができるゲームか伝わるか | 企画文、実態に一致する画像・短い試作映像 | 対象者の理解、期待と体験の一致 |
| コア | 報酬抜きでももう一度遊びたいか | 1ルール、1ステージ、必要最小人数 | 意図した行動、再挑戦、面白い/退屈の場面 |
| 初回 | 操作から最初の価値へ届くか | 最小チュートリアルと結果・再戦 | ファネル、困惑箇所、離脱、ロード |
| 社会性 | 友人と遊ぶと価値が増えるか | 参加、合流、途中離脱、観戦 | ソロとの違い、誘う理由、技能差 |
| 継続 | 次回もやる理由が残るか | 少量の進行・変化 | 成熟したコホート、再訪理由、作業感 |
| 収益化 | 価値を壊さず購入理由を作れるか | 説明・無料体験との比較 | 購入理解、公平感、継続への影響 |
| 運営・規模 | 低人数と同時増加に耐えられるか | 負荷・障害・更新の試験 | 対象機の性能、復帰、対応負荷 |

未実施のテストを結果と書かない。観察会・広告・公開・募集は別途許可がなければ計画にとどめる。

## 2. テストカード

```text
T / 対応するD・仮説C
反証したい仮説:
プロトタイプ範囲と、作らないもの:
比較条件（現状維持を含む）:
対象者・端末・人数・流入・バージョン:
指標（分子、分母、単位、集約、欠測）:
観察期間と、まだ確定しないコホート:
判断条件（根拠あり／ユーザー指定／暫定）:
ガードレール（公平感、離脱、エラー等）:
交絡と限界:
結果で変更する判断:
状態（計画／実施中／完了／未実施）と結果の出典:
```

A/Bの因果を主張するには割当・母集団・干渉を考える。友人同士で条件が混じる場合、個人単位の割当だけで独立とは限らない。少人数の定性テストは問題発見には使えるが、統計的なヒット予測にはしない。

## 3. 計測候補

以下は分析の概念名。Roblox組み込みのイベント名や実装コードではない。

| 概念 | 何を数えるか | 注意 |
|---|---|---|
| join | 入場 | 正常ロードと区別 |
| controllable | 実際に操作できる | ロード時間・初回と再入場 |
| first_core_action | 最初の意味ある行動 | ただの移動やクリックと混同しない |
| first_result | コアの初回結果 | 成功・失敗・途中終了 |
| retry_started | 実際の再挑戦開始 | ボタン表示・クリックとは別 |
| friend_join_success | 友人が合流できた | 招待ボタンの表示とは別 |
| meaningful_progress | 進行目標の達成 | AFKや作業増加と分離 |
| purchase_completed | 確認済み購入完了 | 購入画面表示と分離、権利整合 |

R07〜R08でAnalyticsServiceの送信条件、フィールド、集約、制限を確認し、その時点の仕様に合わせる。テスト用イベントを本番実績に混ぜない。高カーディナリティの個人IDや不要な個人情報を解析出力へ出さない。

## 4. Codex実装への引き継ぎ

分析段階では、元仕様・コードを変更せず別のバックログを作る。

```text
判断ID / 推奨案 / ユーザー採用案 / 承認の原文・場所
目的とユーザー価値:
状態と遷移:
UIとユーザー操作:
サーバー側で保証すること:
クライアント側で表現すること:
保存するデータ:
人数不足・切断・再接続・購入失敗等の挙動:
セキュリティ・悪用への対策:
計測とデータ品質:
受け入れ条件:
性能・端末検証:
手作業アセット:
現行確認が必要なAPI:
未承認の代替案:
```

プロトタイプ承認と本番採用も別に記録する。ユーザーが採用していない段階で「実装対象」と断定しない。

## 5. 判定の返し方

結論は「作る／作らない」だけでなく、維持・修正・削除・小さく検証・根拠待ちを使い分ける。どの結果が出たら判断を変えるかを必ず示す。
