# Roblox開発文書からMVP実装

`roblox-astra-dev-docs`の**成果文書**を実行契約として、実際に遊べるMVPを作る。計画やコード生成で止めず、通常のプレイヤー操作で中心体験を成立させ、保存した成果物と検証結果を引き渡す。Codex GPT-6 Astra向けの上流文書を利用するが、モデルや推論設定を変更しない。

## 成果物と完成条件

- 指定されたMVP全体のソース・ワールド・UI・必要な素材。既存の構成と編集正本を維持する。
- Studioで開ける保存済みPlace（必要な数の`.rbxl`または`.rbxlx`）と、再現できる起動・ビルド手順。
- 開発文書の作業状態・証拠・次の再開地点。既存の記録欄を使い、別の仕様書や管理体系を増やさない。
- **完成**は、MVP必須の挙動・端末・人数・検証条件すべてに適切な実測証拠があり、未実装・失敗・必須未検証が残っていない状態。静的確認、ビルド、Studio Play、実機、人間の試遊、公開先の実動作は別の証拠。

一部を確認できなくても作れる範囲は実装・保存する。ただし「実装済み・実機未検証」など残件を明示し、MVP完成へ読み替えない。公開や外部クライアントでの確認が受入条件なら、その工程も完了対象に残す。

## 1. 文書と現物を照合する

1. ユーザー指定のDEV.md、会話中の最新仕様、既存の正本を特定する。Skill本体やテンプレートをゲーム仕様として使わない。文書が存在しない場合は対象文書を求め、ゲームの核を勝手に発案しない。
2. 適用されるAGENTS.md、差分、ソース・Place・Rojo設定、既存の確認コマンドを調べる。コードは現状、DEV.mdは目標の根拠として分ける。完了チェックが付いていても現物・証拠の対象版を確認する。
3. 核、固定条件、数値と単位・出所、対象端末、人数、状態遷移、MVP範囲、必須アセット、除外範囲を引き継ぐ。上流の企画・文書Skillを再実行して設計をやり直さない。
4. DEV.mdの作業順・依存・完了条件を現在の差分へ対応づけ、最初の未完了作業から着手する。文書にない内部命名・関数分割などは既存構成に合わせて決める。成果に影響する補完だけ同じ文書へ短く残す。

ユーザーの新しい指示は文書の旧記述より優先する。核・固定数値・公開先など判断を委ねられていない矛盾は、影響する作業を特定して確認する。関係ない実装は進める。仕様を満たせないときに基準を緩めたり、必須機能をMVP外へ移したりしない。

## 2. 制作と確認の経路を先に確保する

最初の実装前に[Studioと成果物の経路](references/studio-and-artifacts.md)を読む。

- 既存プロジェクトではそのツールチェーンを使う。新規で指定がなければ、利用可能なRojoで必要なServer／Client／Sharedとワールドを構成する。不要な層やフレームワークを足さない。
- Studio正本なら既存Placeを保護した作業コピーを使う。Rojo管理領域をStudioだけで修正して、次の同期で失う構成にしない。
- 利用可能なStudio MCPを検索し、対象Studio・モード・実際のツール引数を確認する。GUI操作が必要なら利用可能なComputer Use Skillを読む。手段が使えるのにユーザーへ全操作を投げ返さない。
- 対象端末・複数Client・外部クライアントなど必要な確認経路を早期に調べる。環境が欠ける場合は該当確認だけを未実施に残し、ローカル実装を続ける。
- 公開が必要な仕様なら、既存の授権と対象Experienceを早期に確認する。公開先未確定でもソースと候補Placeは仕上げられる。

## 3. 入力から結果までを順に完成させる

DEV.mdの各作業を、**実装 → 必要な静的確認・ビルド → Studio操作 → 不具合修正 → 該当部分の再確認**の順で進める。通常の実装判断や作業単位の完了ごとに、続行の確認を求めない。

- 最初に起動・スポーンまたは初期画面・主入力・状態変化・見える反応がつながる一本を作る。足場、カメラ、操作対象、表示の欠落で遊べない状態を先に解消する。
- 次に仕様の成功・失敗・取消・退出・復帰・再挑戦などを埋める。自由滞在型に勝敗や強制ラウンドを追加しない。
- 中心体験と受入条件に必要なUI、ワールド、アニメーション、音、フィードバックを実装する。デバッグ文字列や動かないボタンだけで代替しない。見た目に関する仕様も通常カメラで確認する。
- 主要設定は既存Configなど一つの正本に置く。ユーザー指定・設計仮説・計算値を実測値へ昇格させない。調整を任されている仮説のみ、観測を根拠に変更して記録する。
- 適用する通信・保存・課金・物理・アセットの節だけ[機能ごとの実装と受入](references/feature-acceptance.md)を読む。MVPにないサービスや仕組みは作らない。
- 必須の体験を完成させてから装飾の調整を進める。ただし原案の核である動き・雰囲気・表現を「後で作る素材」として落とさない。代替素材は許される範囲と未達の条件を記録する。
- TODO、固定された成功応答、見せかけの保存、内部状態の直書きで本来の経路を置き換えない。試験用の模擬実装は製品経路と分離し、その試験が証明する範囲を限定する。

無関係な既存変更を取り込んだり戻したりせず、必要なファイルだけ編集する。既存の文字コード・改行・プロジェクト規則を維持する。

## 4. 遊んで、直して、条件と照合する

確認するのは「コードがある」ではなく、DEV.mdが指定した結果。試験ごとに**仕様参照／対象版と環境／入力／期待結果／観測結果／証拠**を残す。既存の受入記録へ追記し、必要なログや画像だけ別ファイルにする。

1. 利用できる既存チェックを実行する。ルール計算、同時要求、保存失敗など壊れると結果に響く箇所は、意味のある境界試験を追加する。文言や実装の丸写しを検査するだけのテストは増やさない。
2. ビルドした内容・同期されたSourceを確認し、実際の入口からStudio Playを開始する。Client・Serverの起動失敗を先に調べる。
3. キー、クリック、タッチなど本来の入力から一巡を通す。内部関数の呼出しだけで操作合格にしない。状態の決定主体と画面反応を対で確認する。
4. 再挑戦や繰返しがあるゲームは次の一巡も操作する。接続・UI・タイマー・オブジェクトが二重化せず、前回の状態が残らないことを確認する。途中参加・退出など仕様にある例外も扱う。
5. 不具合は再現条件と最初の失敗点を特定し、原因を修正して該当試験と影響する回帰確認を行う。表示だけを消したり、試験条件を変えて合格させたりしない。
6. 対象端末・人数・性能・人間の試遊を、要求された層で確かめる。エミュレータ、NPC、単一Client、内部タイマーの値を、それぞれ実機、人間の対戦、複数Client、体感性能の証拠へ置き換えない。

必要な確認が通ったら、変更や未解決の懸念がない限り検証を拡大し続けない。同じ失敗を根拠なく繰り返さず、利用可能な代替経路を試しても進められなければ、失敗箇所・必要環境・次の操作を残す。

## 5. 保存と必要な公開を終える

- 試験用変更を除き、ソースへ意図した変更を戻す。最終候補をビルドまたはStudioからローカル保存し、実ファイルのパス・サイズ・SHA-256を確認する。
- 最終候補を開き、重要な内容と通常の起動・主操作を再確認する。最後にゲームへ変更を加えた場合、その変更に影響する証拠を取り直す。古いビルドのPASSを新しい成果物へ流用しない。
- 上流文書やユーザーが公開・保存先を指定している場合、既存の授権範囲で実行する。一般の「MVPを作る」依頼だけで、新規Experience作成・本番上書き・公開範囲変更・課金支出・Git pushまで承認されたとは扱わない。
- 非公開ステージングへの公開が明示的に依頼され、`publish-roblox-private-staging`が利用可能なら、そのSkillを読んで対象と手段を確認し、授権済みの公開・外部クライアント確認まで進める。Skillの名前を参照しただけで公開権限を新設しない。
- 追加の承認が実際に必要な場合、先に候補Placeと可能な検証を仕上げ、対象ID・変更内容・確認済み範囲を示す。既に承認された操作は確認し直さない。
- ローカル保存、Robloxへの保存、公開バージョン反映、外部クライアント動作を分けて記録する。通信が途切れた公開は現行バージョンを確認してから再実行を判断する。

## 6. 完成監査と再開地点

DEV.mdの**MVP必須事項すべて**を、実装先と適切な層の証拠へ照合する。抜けた項目は実装・確認へ戻す。機能単位のPASSを全体のPASSへ広げない。

- 必須の遊び、主要数値、操作端末、人数、復帰・失敗時挙動、必要素材が満たされているか。
- 必要なPlaceすべてが保存され、記録した対象版と一致し、作業コピーや試験専用入口に依存せず起動できるか。
- 文書の目標、実装現状、検証状態に食い違いがないか。必須未検証を残す場合は完成とせず、その理由・必要な入力・次の未完了作業を記す。

自分が開始したPlayや不要になった同期プロセスだけを終了し、試験用の入力押下・一時設定を解除する。ユーザーの別Studioや他プロジェクトのプロセスは閉じない。

最終回答は**成果物リンク／起動方法／実装した範囲／実施した検証／残る必須事項と次の作業**。完成済みなら残件なしを明記する。未完成なら具体的な不足を示し、実行可能な作業が残っているのに「続けますか」で止めない。
