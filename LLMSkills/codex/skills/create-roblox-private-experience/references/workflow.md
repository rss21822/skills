# 新規非公開Experience作成の実行手順

## 1. 入力と境界

ユーザー指定の種類を `production-private` または `verification-private` として固定する。いずれも公開対象ではない。ローカルプロジェクトのルート、正本ファイル／ビルド手順、Place役割、希望する所有者を特定する。曖昧な候補は質問で解消し、IDを推測しない。既存Experienceの更新依頼ならこのSkillを機械的に適用せず、更新対象を明示して適切な公開手順へ切り替える。

作業前の記録: Git HEADと作業ツリー、ソース／Place対応、既存の本番・検証Universe/Place ID、現在の認証アカウント。既存環境への誤公開を防ぐため、新規作成後のIDと照合する。

## 2. ローカル候補を凍結

プロジェクト登録のビルド・テストを実行し、入口と全サブPlaceの独立した成果物を作る。ビルドで生成される設定とPlace内部の設定を照合する。各成果物のSHA-256、サイズ、検証結果を記録。ユーザーの未関連変更を壊さない。Studioで確認する場合、凍結したローカルファイルを開き、既存のクラウド接続Studio窓と混同しない。

実行時のIDを必要とするコードがあるなら、作成後に新IDを注入して再ビルド・再テスト・再ハッシュする。古いIDのまま公開しない。秘密情報をローカル成果物へ埋め込まない。

## 3. ExperienceとPlaceを作る

Roblox StudioまたはCreator Hubの現在利用可能な正式手段で、指定所有者の下に新規Experienceを作る。作成直後に所有者、Universe ID、入口Place ID、非公開アクセス、非公開オーディエンスを確認する。後続のPlaceを必要数だけ同じUniverse内に作成し、役割とIDを記録する。必要なアセット権限のみ対象Universeへ付与し、他のExperienceの権限を広げない。

作成済みの空Placeや初期テンプレートは完成版と誤認しない。既存の同種Experienceが現れた場合、重複作成や上書きを止め、ユーザーへ選択を求める。

## 4. 新IDで再構築・公開

入口→サブPlaceのTeleport、サーバー間キュー、環境マーカー、永続データ、外部連携の宛先を新Universeに合わせる。検証用は本番用と独立させる。本番用も公開前の非公開状態を維持し、検証用の識別子を流用しない。課金商品やデータ移行は、作成に必要な範囲と明示指示を区別する。

公開前のリリース記録に所有者・Universe/Place ID・入口Place・ハッシュ・公開順・非公開状態・検証結果・失敗時の戻し方を固定する。公開直前にもファイルハッシュと宛先を再確認。マッチ等のサブPlaceを先に、入口Lobbyを最後に公開する。各API/Studio応答を確認してから次へ進む。曖昧な応答はCreator Hub履歴で照合し、盲目的に再試行しない。

## 5. 独立確認と実機

Creator Hubで全Placeの「公開済み」履歴、入口Place、所有者、アクセス／オーディエンス非公開を確認する。API成功だけでは完了にしない。一時資格情報を使った場合は失効・削除して不存在を確認する。

正式なゲームページから、権限を持つアカウントでRoblox Playerに入場。詳細ページの表示、Play押下、実際のロビー描画は別の証拠。複数Placeなら通常のUI操作でTeleportを確認する。Playerの起動不能やPrivateアクセス制限は具体的に記録し、Studio Playで代替したと報告しない。課金テスト・データ削除・一般公開は実施しない。

最終報告には、指定種類、所有者、Experience/Place IDとURL、各公開バージョン、非公開確認、ローカル・クラウド・Playerそれぞれの判定、残課題を記す。
