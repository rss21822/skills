# 作業完了後の自動シャットダウン

## このスキルが解く問題

ユーザーは重い作業をClaude Codeに任せて離席したい。だが「終わったら落として」を素朴に実装すると、
**ターンの終わり = 作業の終わり** と誤解して、実際にはユーザーの返事を待っているだけの状態で電源を切ってしまう。

これは最悪の失敗だ。ユーザーは戻ってきて「質問に答えるつもりだったのに勝手に落ちていて、作業は中途半端」という状態に直面する。
逆に落とし忘れても、被害は電気代だけで済む。**判断に迷ったら落とさない**、が常に正しい非対称性がある。

このスキルの本質は、シャットダウンコマンドではなく「作業が本当に終わったのか、それとも自分がユーザーを待っているだけなのか」を
毎ターン誠実に自問する仕組みにある。

## 2フェーズモデル

シャットダウンは1つの動作ではなく、**予約（ARM）** と **発火（FIRE）** の2フェーズで扱う。

```
ユーザー「終わったら落として」
        │
        ▼
   [ARM] 予約を記録（状態ファイル）＋ 何を作業完了とみなすか宣言
        │
        ▼
   通常どおり作業する（何ターンかかってもよい）
        │
        ▼
   各ターンの最後に [完了ゲート] を通す ──不合格──▶ 落とさず、ターンを終える（予約は維持）
        │合格
        ▼
   [FIRE] 6分猶予つきシャットダウン ＋ 取消手順を表示
```

## フェーズ1: ARM（予約する）

ユーザーが依頼した時点で、以下を行う。

1. **何をもって「完了」とするかを1〜2文で言語化してユーザーに返す。** 例:「TASKS.mdの3件が全部完了して、エラーが残っていない状態を完了とみなして、その後6分猶予で落とします」。
   これは確認のための質問ではなく宣言なので、ユーザーの返事を待たずにそのまま作業に入ってよい。
2. 予約を状態ファイルに書く（セッションが長引いて文脈が圧縮されても予約を見失わないため）:

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<skill>/scripts/shutdown.ps1" -Arm -Reason "TASKS.mdの3件完了後に落とす"
```

3. 予約中であることを、以降のターンで自分に思い出させる。長い作業に入る前には `-Status` で予約の有無を確認できる。

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<skill>/scripts/shutdown.ps1" -Status
```

ARMするのは**ユーザーが明示的に頼んだときだけ**。「あとで見ます」「離席します」程度の発言から勝手に予約してはいけない。

## フェーズ2: 完了ゲート

予約中のセッションでは、ターンを終える直前に必ずこのゲートを通す。
ゲートは「落としてよい理由を探す」のではなく、**「落としてはいけない理由が1つでもあるか」を探す**向きで使う。1つでも該当したら発火しない。

### 落としてはいけない（保留する）条件

- **自分がユーザーの返答を必要としている。** 応答に質問文が含まれている、選択肢を提示した、「〜でよいですか」「どちらにしますか」で終わろうとしている、AskUserQuestion系の確認を出した ── これらは全部「一時中断」であって完了ではない。ここが本スキルの最重要ポイント。
- **承認・許可待ち。** ツール実行の許可、コマンド承認、危険操作の確認待ち。
- **タスクが残っている。** TodoList/TASKS.md等に pending や in_progress が残っている。
- **エラー・失敗が未解決。** ビルド失敗、テスト失敗、例外、コマンドの非ゼロ終了が未対応のまま。
- **自分が途中で止まっている。** 実装が部分的、検証していない、「次はこれをやります」と書いた続きがある。
- **バックグラウンドで何かが走っている。** ビルド、テスト、レンダリング、長時間コマンド、サブエージェントが未完了。
- **ユーザーが直近で予約を取り消した、または新しい作業を投げてきた。**
- **判断がつかない。** 迷ったら保留。落とし忘れのコストは電気代、誤爆のコストは作業消失。

保留したときは、ターンの最後に一行だけ状態を書く。例:「シャットダウン予約は維持中（確認待ちのため保留）」。
ユーザーが戻ってきたときに、なぜまだ電源が入っているのかが分かるようにするため。

### 発火してよい条件

上のどれにも該当せず、かつ ARM時に宣言した完了条件を満たしているとき。
言い換えれば「ユーザーがこの応答を読んでも、返事をする必要がない」状態。

## フェーズ3: FIRE（発火）

発火すると決めたら、まず作業結果の要約を書き、その**あとで**コマンドを打つ。ユーザーは戻ってきてからこの要約を読む。

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<skill>/scripts/shutdown.ps1" -Fire -Delay 360
```

これは `shutdown.exe /s /t 360` を発行し、予約状態ファイルを消す。実行後、ユーザーに必ずこう伝える:

```
作業が完了したので6分後（360秒後）にシャットダウンします。
取り消す場合はこのコマンドを実行してください: shutdown /a
```

### 発火後にユーザーから入力が来たら

猶予6分のあいだにユーザーが何か送ってきた場合、**それが何であれ、最初にシャットダウンを取り消す。**
まだ画面の前にいるということであり、電源を切る前提が崩れているため。

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<skill>/scripts/shutdown.ps1" -Cancel
```

取り消したことを伝えてから、ユーザーの用件に応じる。

## 予約の解除

「やっぱり落とさないで」「シャットダウンやめて」と言われたら、予約解除と発行済みタイマーの取消を両方やる（どちらの段階か分からなくても安全に効く）。

```bash
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<skill>/scripts/shutdown.ps1" -Disarm
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<skill>/scripts/shutdown.ps1" -Cancel
```

## 判断例

**例1 — 発火する**

```
状況: 予約中。3つのリファクタリングタスクが全部完了、テストも通過、未解決エラーなし。
      応答は結果の要約のみで、質問なし。
判断: FIRE。要約 → shutdown.ps1 -Fire → 「6分後にシャットダウンします。取消は shutdown /a」
```

**例2 — 発火しない（本スキルの核心ケース）**

```
状況: 予約中。実装は終わったが「命名をcamelCaseとsnake_caseどちらに揃えますか？」と聞こうとしている。
判断: 保留。ターンは終わるが、これは作業完了ではなくユーザー待ち。
      「シャットダウン予約は維持中（命名方針の確認待ちのため保留）」と添えて終える。
```

**例3 — 発火しない**

```
状況: 予約中。5件中4件完了、5件目でビルドエラーが出て解決できていない。
判断: 保留。エラー内容と試したことを報告して終える。予約は維持。
```

**例4 — 取り消す**

```
状況: -Fire 実行から2分後、ユーザーが「ありがとう」とだけ送ってきた。
判断: まず -Cancel。「まだ操作中のようなのでシャットダウンを取り消しました」と伝えてから応じる。
```

## 実装メモ

- Windowsでは `Stop-Computer` に猶予・取消の概念がないため、猶予つき運用には `shutdown.exe /s /t N` を使う。取消は `shutdown.exe /a`。
- 検証したいだけのときは環境変数 `CLAUDE_SHUTDOWN_DRYRUN=1` を立てる。スクリプトは実際には電源を切らず、実行予定のコマンドをログに書く。
- 予約状態ファイルは `%USERPROFILE%\.claude\auto-shutdown.state`、ログは同ディレクトリの `auto-shutdown.log`。
- スクリプトの詳細な引数は `references/script-usage.md` を参照。
- 本文中の `<skill>` は、このスキルフォルダの実パスに読み替える。ユーザースキルとして置いた場合は
  Git Bash から `$HOME/.claude/skills/auto-shutdown-on-complete`、PowerShell から
  `$env:USERPROFILE\.claude\skills\auto-shutdown-on-complete`。パスに空白が含まれる環境があるので、
  `-File` に渡すときは必ずクォートで囲む。
