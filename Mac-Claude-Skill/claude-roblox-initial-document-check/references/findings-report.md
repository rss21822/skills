# 所見の記録

## 監査報告書の位置づけ

報告書は**状態記録**であり正本ではない。冒頭に明記する。これがないと、後から報告書の記述と正本が食い違ったときにどちらを信じるか分からなくなる。

```markdown
| 位置づけ | 本書は状態記録であり正本ではない。矛盾時は各正本文書が優先する |
| 更新規則 | 監査の再実施時、または所見の状態変化（決定・解消）時に改訂する |
```

## 構成

```markdown
# <PREFIX>_repository_audit.md — リポジトリ監査報告書

| 項目 | 内容 |
| 文書ID / 版 / 日付 |
| 監査対象 | branch、HEAD、対象ファイル |
| 監査方式 | 読み取り専用。実施者 |
| 位置づけ | 状態記録であり正本ではない |
| 発端 | 誰の何という依頼か |

## 1. 総評
（2〜4文。全体の健全性と、実装可能かの結論）

## 2. 重大所見（対処必須）
| # | 所見 | 根拠 | 対処 |

## 3. 軽微所見（本改訂で修正済み）
| # | 所見 | 根拠 | 対処 |

## 4. 観察（対処不要・記録のみ）

## 5. ギャップマップ
| 標準文書 | 状態 | 所在 |

## 6. 決定要求（ユーザー宛て）
| ID | 決定内容 | 選択肢 | 推奨 |

## 7. 実行環境実測
（[FACT] として、実際に測定した環境情報）
```

## 根拠の書き方

**節参照を使う。行番号は使わない。** 改訂のたびに行がずれて、根拠が別の内容を指すようになる。実運用で、監査書自身の改訂によって自分の根拠参照が腐った。

良い: `docs/OVL_WORKFLOW.md §4.2`
悪い: `docs/OVL_WORKFLOW.md:220`

## ギャップマップの「分散所有」

標準的な文書体系に対して何が欠けているかを表にする。ただし**「独立文書が無い＝欠落」ではない**。

| 状態 | 意味 |
|---|---|
| 存在 | 専用文書がある |
| 分散所有 | 独立文書は無いが、既存正本が機能を分担している。**新設しない**（二重正本になる） |
| 部分的 | 一部だけ存在する。何が足りないかを書く |
| 欠落 | どこにも無い。新設が要る |

分散所有の例: 「人間専用作業の一覧」は、運用文書の実行責任表＋キックオフチェックリスト＋進捗記録のブロッカー欄が分担していることがある。ここに `HUMAN_ACTIONS.md` を新設すると、同じ事実が2箇所に生まれる。

## 決定要求

ユーザーが決めないと進めない項目は、**選択肢と推奨を添えて**出す。「どうしますか」だけでは判断材料が足りない。

```markdown
| ID | 決定内容 | 選択肢 | 推奨 |
|----|----------|--------|------|
| D-A2 | P0実行プラットフォーム | (a) Windows機で現仕様のまま / (b) macOSで実施し該当節を改訂 / (c) 両対応 | [PROPOSAL] (b)。実開発機・ツール類が現にmacOSにあり、目的は代替手段で担保可能。ただし(b)採用時も<代替の必須条件>を課す |
```

推奨には `[PROPOSAL]` を付ける。承認前の提案であることを明示する。

## 状態タグ

| タグ | 意味 |
|---|---|
| `[FACT]` | 確認済みの事実。測定方法も書く |
| `[DECISION]` | ユーザーが承認済み |
| `[PROPOSAL]` | AI提案、未承認 |
| `[OPEN] blocking: yes\|no` | 未決。blocking:yes は進捗記録のblocker欄にも登録 |

`blocking: yes` の項目は必ず二重登録する（文書内の注記＋ブロッカー台帳）。片方だけだと、文書を読んだ人と進捗を見た人で認識がずれる。

## 是正の記録

軽微所見をその場で直した場合、何をどう直したかを報告書に残す。改訂した文書側にも改訂履歴を追加する。

正本文書を直すときは、その文書の所有者（多くの場合は実装AI）に依頼するのが原則。指示側が直接編集すると、レビューを経ない変更が入る。ユーザーの明示指示で直接編集した場合は、その差分を次の独立レビュー対象として登録しておく。

## 監査記録の保存

判定に関わらず全巡を保存する。差し戻しの記録にこそ価値がある（何を避けたかが残る）。読み取り専用で走らせた監査は自分で保存できないので、**呼び出し側が本文を改変せず保存する**。ヘッダ（対象・日付・判定）を足すのは構わない。
