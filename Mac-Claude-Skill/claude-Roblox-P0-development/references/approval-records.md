# 承認記録・委任・正本の一元化

P0 は選択の記録が多い。Change Request 1件で6群の選択を確定することもある。**記録の構造を間違えると、後から選択を変えたときに片側更新が起きる。**

## 1. 承認内訳の正本は1箇所

### 原則

**「何を承認したか」の正本は `DECISIONS.md` の決定1件に集約する。** 他の文書からは参照だけを置く。

```
DECISIONS.md の決定（正本）
  ├─ 選択内訳を全件記載
  └─ 本文に「選択内訳の正本は本決定である」と書く

Work Packages       → 「D-n に基づく」と参照
Toolchain           → 「D-n を参照」と参照
CR ヘッダ           → Status: Approved、承認記録は D-n
人間作業台帳        → 承認内容の要約は D-n を参照（内訳を複製しない）
PROGRESS            → 実施の事実だけ。選択内訳は書かない
```

### なぜ複製が危険か

選択が6群あると、複製先が4文書あれば24箇所になる。1つ変えたとき、残り23箇所を全部直せる保証はない。実際に P0 では「状態値の片側更新」が3回再発した。

### 照合での確認

「**選択内訳を正本と宣言している承認記録が1箇所だけか**」を照合依頼に書く。実プロジェクトでは照合が「別の承認記録や選択内訳表は作られておらず、二重正本とは判定しない」と確認した。

## 2. 決定 ID の扱い

### 完全修飾する

同じ `D-n` 体系を複数の文書が独立に使っていると、裸の参照が誤った決定へ解決される。実プロジェクトでは `D-9` が3つの別物を指し、裸参照33件が最終監査まで残って人間の決裁事項へ回った。

**参照は常に完全修飾する。** ID 本体の形式は上流の体系定義が正本なので変えない。足すのは「どの文書の D-n か」を伴わせる規約だけ。

### P0 で新設する決定の採番

P0 では承認のたびに決定が増える。**既存の採番と衝突しない次番を採る。** 番号を予約する場合は、**予約だけで済ませず実際に行を起票する**（実プロジェクトでは「採番候補」と書いただけで台帳に行が無く、照合で Minor になった）。

### fallback の扱い

決定に対応する fallback（`F-n`）を作るかどうかは判断が要る。**未指示で作らない。** validator が「同番 fallback が無い」と警告する場合、それは警告であって不合格ではないことを確認したうえで、作らない旨を報告に書く。

## 3. 委任

### 委任を記録する

Owner が「以降は AI が承認判断してよい」と委任した場合、それ自体を決定として記録する。記録には**対象範囲と対象外**を明記する。

```
対象:   P0 の文書承認と commit 判断

対象外: production の Universe／Place、ID、DataStore、Open Cloud、商品、
        Secrets、権限、binding、publish settings への接触
        全環境の publish、production activation、商品 ID 作成、
        Secrets 設定、Group 権限変更、production DataStore 変更
        （上流 skill が [HUMAN] 操作として定める全項目）
```

**委任されたのは文書承認であって、外部状態を変える権限ではない。** ここを曖昧にすると、AI が publish や商品 ID に手を出す余地ができる。

### 正本側の承認者規定を同期する ★事故った

委任を記録しただけでは足りない。**その委任が適用される工程の正本が「承認者は `[HUMAN]` Project Owner」と書いたままだと、次工程の権限主体が二通りになり、authorized path が実際に止まる。**

実プロジェクトでは、委任の直後に Toolchain の3箇所（契約承認の主体・承認記録表の承認者欄・別 CR の承認主体）が Human 限定のままで、照合が Major と判定した。

**対処**: 委任を記録した便で、**適用工程の正本を全文検索**し、承認者を限定している記述へ委任経路を併記する。

```
既存記述を削除せず、次を足す:

「承認者は [HUMAN] Project Owner、または〈委任の決定 ID〉に基づき委任された AI とする。
  委任による承認の場合は承認記録に同決定を参照として明記する。
  同決定が対象外とする [HUMAN] 専権事項は本委任の対象外のまま変わらない。」
```

**委任の内容を複製せず参照で表す**のが要点。対象外の列挙を各所に書き写すと、また片側更新が起きる。

### 委任下で承認する側の作法

- **判断材料を実測してから承認する**（→ `gate-design.md` §5）
- **委任の範囲外を判断しない**。実測を必要とする決定、承認済み `[DECISION]` の変更を伴うものは、材料を揃えて Owner へ返す
- 承認記録に**委任の決定 ID を参照**として明記する。「AI が承認した」だけでは根拠が辿れない
- 承認の性質を書き分ける: **「照合の承認可」「WP の Verified 遷移」「Owner 承認（または委任承認）」は別の事象**

## 4. 人間作業台帳の同期

### 行を消さない

台帳は「未完了の `[HUMAN]` 作業を集約する」と定義されがちだが、**完了行を消すと監査追跡が切れる**。`Completed` のまま残し、収録規則の側に「完了行を残す理由（監査追跡・gate 充足証明）」を書く。

### closure evidence 欄も同期する

行を `Completed` にする便で、**evidence 欄も現況へ同期する**。承認した時点では「実改訂=未」が正しくても、後の便で完了したら追随させる。追随しないと台帳が失効値になる（→ `rework-catalog.md` D-1）。

過去の記述を消さず、時制を限定して現況を追記する形が安全。

### 起票しない判断も記録する

委任経路で完結した承認について、台帳へ新規行を起票しない判断をした場合、**その判断根拠を進捗記録に残す**。「台帳は `[HUMAN]` 専権・未完了作業の集約であり、委任済み承認は該当しない」のように。書かないと、後から「なぜ台帳に無いのか」が分からない。

## 5. 記録の三層

P0 の記録は3層に分かれる。**混ぜない。**

| 層 | 文書 | 内容 | 性質 |
|---|---|---|---|
| 決定 | `DECISIONS.md` | 何を承認したか。選択内訳 | **正本** |
| 実績 | `CHANGELOG.md` | いつ何を変えたか | 履歴。過去を改変しない |
| 現況 | `PROGRESS.md` | 今どこにいるか。次に何をするか | 現在の宣言。**変わる値を保持しない** |

現況層に「未 push N commit」のような変わる値を書くと必ず失効する。**実測コマンドの結果を正とする**と書く（→ `rework-catalog.md` D-1）。

履歴層に旧値が残るのは正しい。**現況値へ上書きするのは過去の改変**であり誤り。時制を限定し、現在値の正本がどこかを示すのが正しい是正。
