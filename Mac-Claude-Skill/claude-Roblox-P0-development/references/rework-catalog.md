# P0 手戻りカタログ

実プロジェクトの P0（抽出時点で handoff 26便・独立照合16巡・commit 8件）で実際に発生した手戻り14種。各項目は **症状 / 実例 / 検出 / 防止**。

**使い方**: handoff を発行する前にこの一覧を通読し、その作業単位で起こりうるものを handoff の制約条項へ先回りで入れる。巡数が減る。

- B. 承認記録系 … B-1〜B-3

- D. 状態同期系（最も再発した） … D-1〜D-3

## A. gate 設計系

### A-1. 循環 gate ★2回発生

- **症状**: A の承認条件が B、B の前提が A。誰も着手できない。
- **実例1**: 契約節 §2.3 の `[DECISION]` 昇格条件に「実 tree との逐条照合」「project file の build 成功」が入っていた。しかし実 tree を作るのは W0 実装で、W0 は D5 承認が要り、D5 は契約承認を要求する。
- **実例2**: P0 Work Package の `Authorized by` が「D5 承認」だったが、P0 は D5 到達のための前提作業だった。
- **検出**: clean-room 監査が最も強い。「この文書だけを読んで最初の作業を始められるか」を問うと循環が浮く。
- **防止**: **承認を2段に割る。** 「A: 契約としての承認（実体の存在を条件にしない）」と「B: 実装後の適合確認（昇格の前提ではない。未実施を理由に A を差し戻さない）」。gate を分ける（P0 開始承認と D5 承認は別物）。
- **見分け方**: 承認条件に「まだ作っていないものを使う検査」が入っていたら循環を疑う。

### A-2. open の粒度過大

- **症状**: 確定できるものと、計測待ちのものが同じ `[OPEN]` に入っていて、確定済みの分も閉じられない。
- **実例**: 4つの entry file（W0 用2つ、Lobby／Match 用2つ）を1つの open にまとめていた。Lobby／Match は配信方式の実測（FR-3.9）待ちだったため、確定済みの W0 側2つも closure に到達できなかった。
- **検出**: closure evidence を1項ずつ「今これを満たせるか」で評価すると、満たせない項が特定の対象にだけ紐づいていることが分かる。
- **防止**: **closure 条件が違うものを同じ open に入れない。** open を立てる時点で「これは何を待っているか」を対象ごとに書き、待ち先が違えば分ける。
- **注意**: 分割は後からでもできるが、下流文書が「この open が閉じない」を前提に書き始めると被害が広がる。早く分ける。

### A-3. 規定が配線されていない ★照合2巡を要した

- **症状**: 「実装後にこれを検査する」と規定を書いたが、**どの Work Package の完了条件にも入っていない**。規定は存在するが効力がない。
- **実例**: 契約適合検査（B 段）の実施要求を書き、しかも本人が「各 WP への追記が未了の間は、本段の要求は実装 WP の完了を止める効力を持たない」と正直に書いていた。ところがその追記を担うはずの Change Request の改訂 inventory にも Migration procedure にも B が入っておらず、**CR の手順を最後まで実行しても配線されない経路**が残っていた。
- **検出**: 照合依頼に「**経路を最後まで辿って、本当に完了条件へ接続されるか**」と書く。規定の存在確認で止めると見逃す。
- **防止**: 規定を書いた handoff の中で、**その規定を強制する場所（WP の `Automatic tests`／`Evidence output`／`Done definition`）への追記を、同じ CR の改訂 inventory に入れる**。「後で入れる」は入らない。

### A-4. 閉じてはならない open を閉じる／閉じてよい open を残す

- **症状**: closure evidence の一部しか成立していないのに open を閉じる。または、条件が揃っているのに閉じ忘れる。
- **実例**: adapter inventory の open は、client 側 adapter の割当が別 CR へ送られたため、その CR の closure まで閉じてはならなかった。closure evidence へ明示的に「別 CR の closure」を追加して回避した。
- **検出**: closure record から evidence の各項へ**実際に辿れるか**を確認する。「成立した」と書いてあるだけで参照先が無いものは要注意。
- **防止**: closure record に **evidence の項番ごとに何がどこで成立したか**を書く。日付・決定 ID・一致確認の実測値を残す。

## B. 承認記録系

### B-1. 承認内訳の複製

- **症状**: 「何を承認したか」が複数の文書に書かれ、後で選択が変わったとき片側だけ更新される。
- **実例**: Change Request の承認は、選択肢が6群（entry／project file／module／adapter／縮退方式／client adapter）にわたった。これを Work Packages・Toolchain・CR ヘッダ・人間作業台帳へ書き写していたら、確実にずれていた。
- **防止**: **正本は `DECISIONS.md` の決定1件に集約**し、他は参照だけを置く。決定の本文に「選択内訳の正本は本決定である」と書く。
- **効果**: 実プロジェクトでは照合が「別の承認記録や選択内訳表は作られておらず、二重正本とは判定しない」と確認した。

### B-2. 委任と正本の承認者規定の不整合 ★authorized path が止まる

- **症状**: Owner が承認を AI へ委任したのに、正本側が「承認者は `[HUMAN]` Project Owner」と書いたまま。**次工程の権限主体が二通りになる。**
- **実例**: 委任を決定として記録した直後、Toolchain の3箇所（契約承認の主体・承認記録表の承認者欄・別 CR の承認主体）が Human 限定のままだった。照合が Major と判定。
- **検出**: 委任を記録したら、**その委任が適用される工程の正本を全文検索**し、承認者を限定している記述を洗う。
- **防止**: 委任の記録と同じ便で、正本側へ委任経路を**併記**する（既存記述を削除せず「または委任された AI」を足す）。委任の内容は複製せず参照で表し、**対象外事項（production 接触・publish・商品 ID・Secrets・Group 権限・production DataStore）は正本のまま維持する**ことを明記する。

### B-3. 台帳の closure evidence が旧状態のまま

- **症状**: 人間作業台帳の行を `Completed` にしたが、closure evidence 欄が「実改訂=未／validator=未」のまま。
- **実例**: 承認した時点では正しかったが、その後の便で実改訂と validator 取得が完了したのに台帳が追随しなかった。
- **防止**: 台帳の行を更新する便では、**evidence 欄も同時に現況へ同期する**。過去の記述は時制限定で残し、現況を追記する形にする。

## C. handoff 契約系（指示側の誤り）

### C-1. inScope に「状態の正本」が入っていない ★

- **症状**: 「Status を X へ更新せよ」と指示したのに、Status の正本ファイルが inScope に無い。実装モデルは inScope 内のファイルだけを更新し、**正本と運行記録が二分する**。
- **実例**: Work Package の Status 正本は `work_packages.md` の index と詳細節だが、inScope に同ファイルを入れ忘れた。実装モデルは `PROGRESS.md` だけを更新し、照合で Major。
- **検出**: 照合が「正本は `Proposed`、運行記録は `In progress`」と指摘する。文書内 lint では検出できない（正本内の index と詳細節はどちらも旧値で一致しているため）。跨文書検査が要る。
- **防止**: **handoff 発行前に、objective に書いた各変更対象について「この値の正本はどのファイルか」を確認し、inScope に含まれているか検算する。**

### C-2. handoff の指示自体が誤っている

- **症状**: 存在しない規則の適用や、適用対象外の規則を要求する。実装モデルはそれに従って書くので、成果物に虚偽が入る。
- **実例**: adapter の file 名について「path 導出規則から機械的に導出せよ」と指示した。しかし導出規則は論理 module を対象とし、adapter は論理 module inventory に載せない方針を同時に採っていたため、**適用対象外**だった。成果物には「機械的に導出した」という成立しない主張が入った。
- **検出**: 照合が「その主張は現行規則から一意には導出できない」と指摘する。
- **防止**: **成果物を歪めて辻褄を合わせず、契約側の誤りとして直す。** 是正 handoff の冒頭に「§0 handoff 側の誤りの記録」を置き、何を誤指示したかを書いてから是正内容へ入る。これを曖昧にすると、誤った指示が正本に固定される。

## D. 状態同期系（最も再発した）

### D-1. 失効値 ★3回連続で再発

- **症状**: 記録行に、現在形のまま失効した commit hash・Status・件数が残る。
- **実例**: (1) Last Known Good Commit が本文冒頭・現況表・Toolchain の3箇所で食い違う。(2) 詳細節を更新したのに現況表が旧 Status のまま。(3) 「未 push 3 commit」が commit のたびに失効（3→4→5）。**毎回「全文走査した」と報告された後に照合で発見された。**
- **なぜ人手で取れないか**: 是正者は直した箇所を見ており、直していない箇所を探す動機が働かない。照合者も指摘箇所の解消確認に寄る。
- **防止（本質的）**: **記録に「変わる値」を保持する形式そのものをやめる。** 件数と hash を持たず「実測コマンドの結果を正とする」と書けば二度と失効しない。保持してよいのは意図的なスナップショット（LKG のような「その時点で検証した」宣言）だけ。
- **履歴は別扱い**: 履歴行に旧値が残るのは正しい。**現況値へ上書きするのは過去の改変**。時制を限定し、現在値の正本がどこかを示すのが正しい是正。

### D-2. 跨文書の状態不一致

- **症状**: 正本文書と運行記録で同じ WP の Status が違う。文書内 lint では検出できない。
- **実例**: C-1 の帰結。`work_packages` の index と詳細節はどちらも `Proposed` で一致していたため、文書内の索引ドリフト検査は 0 件を返した。跨文書で見て初めて分かった。
- **防止**: `scripts/check_p0_state.py` の跨文書 Status 検査。文書内 lint と併用する。

### D-3. 総則・索引の一律断定

- **症状**: 「本書の全 Work Package の Status は `Proposed` である」のような一律断定が、実態と食い違ったまま残る。索引だけ読む人が着手済みの項目を未着手と誤認する。
- **防止**: 総則には「現在の Status は各 WP の詳細節が正本であり、索引は再掲。食い違えば詳細節を正とする」と書く。一律断定は書かない。docs-creator の lint 規則 `status-index-drift` の `blanket_phrases` が検出する。

## E. 判断の越境系

### E-1. 承認済み決定の侵食

- **症状**: Change Request の選択肢の1つが、承認済み `[DECISION]` の適用範囲を静かに変えてしまう。
- **実例**: 「W0 用に no-op の永続化 port を用意する」案は、承認済み決定「W0 は製品のゲーム進行永続化を作らない」の範囲変更を伴っていた。さらに、その port が従うべき操作集合が2つの正本で食い違っており（一方は3操作、他方は5操作）、どちらに従うか本 CR では決められなかった。
- **防止**: 選択肢を提示する前に、**各案が既存の承認済み決定に触れるかを確認**する。触れるなら「選択するには追加設計が必要」と明記し、**何を決めれば選択可能になるか**を列挙する。投機的に担当を割り当てない。
- **原則**: 選べない案を選択肢として並べると、Owner は選べないことに気づかないまま選ぶ。

### E-2. 根拠のない担当割当の創作

- **症状**: 「この module は誰が作るのか」を埋めるために、実記述の裏づけなく WP を指名する。
- **防止**: 割当は**現行 Work Packages の実記述から根拠3点以上**で提案する。自明な受け皿が無ければ、新設 WP 案を提示するか「Owner の決裁が要る」と書いて止める。**根拠を示せない割当を書かない。**
- **照合での確認**: 「引用された `Objective`／`Create`／`Modify`／実装順序を実文書で検証する」と照合依頼に書くと、創作が露見する。
